这份字幕文件主要解析了 **GitLab CI/CD 的底层执行机制**，重点探讨了 Docker 执行器（Docker executor）的工作原理、作业产物（Artifacts）的存储机制，以及使用 Docker 环境的性能权衡。

以下是内容的结构化总结：

### 1. Docker 镜像的默认行为
*   **现象**：即使在 `.gitlab-ci.yml` 中没有显式指定 Docker 镜像，如果 GitLab Runner 配置了 Docker 执行器，它依然会使用一个**默认镜像**（通常是 Ruby 镜像）来执行 Job。
*   **建议**：虽然系统有默认行为，但**强烈建议不要依赖默认镜像**，而应该在配置中明确指定所需的 Docker 镜像，以确保环境的准确性。

### 2. Job Artifacts（作业产物）的存储机制
*   **疑问**：在 Docker 容器中生成的构建文件（如 `build` 目录或 `car.txt`）既不在代码仓库中，容器销毁后也不复存在，那为什么我们在 GitLab 界面上还能看到并下载这些 Artifacts？
*   **解答**：GitLab 在后台**抽象并接管了 Artifacts 的物理存储**。
    *   用户**不需要也不应该**关心 GitLab 具体把这些文件存在哪里（例如不能自定义存到 Dropbox）。
    *   用户只需在配置中声明哪些文件是 Artifacts，GitLab 会自动处理存储，并且后续的 Jobs 默认就能直接获取和使用这些产物。

### 3. Docker 执行器的性能开销 vs 核心优势
使用 Docker 执行器每次都需要经历“拉取镜像 -> 启动容器 -> 清理仓库”等步骤，这必然带来一定的**性能开销（Overhead）**。但讲师强调，其带来的优势远大于性能损耗：
*   **如何降低开销**：使用轻量级镜像（如 `Alpine`）可以将整个启动和执行过程压缩到仅需 10-12 秒，对整体 Pipeline 性能影响极小。
*   **核心优势（为什么必须用 Docker）**：
    1.  **环境隔离与一致性**：确保 Pipeline 在任何机器（本地或 GitLab 基础设施）上运行结果完全一致，配置具有极强的**可移植性**。
    2.  **并发安全**：隔离环境允许多个 Jobs 同时运行而**互不干扰**，这对于 CI/CD 的稳定性和效率至关重要。

### 4. 课程总结与排查指南
*   本讲座旨在帮助开发者建立对 GitLab CI/CD 整体架构的全局认知。
*   理解 Jobs 是如何在幕后被执行的（如 Docker 容器的生命周期、Artifacts 的流转），能够帮助开发者在 Pipeline 出现异常时，**更有效地通过查看日志来定位和排查问题**。
