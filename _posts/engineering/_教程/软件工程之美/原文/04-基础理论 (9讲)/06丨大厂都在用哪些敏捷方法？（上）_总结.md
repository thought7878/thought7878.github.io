# 《06丨大厂都在用哪些敏捷方法？（上）》总结

> 来源：本专栏第 6 讲 · 基础理论篇

## 一句话结论

大厂敏捷的秘诀是「分而治之」——大项目拆小项目、大服务拆成微服务、大团队拆小小组；落地靠三件事：一切工作围绕 Ticket 的看板管理、基于 Git + CI 的开发流程、每日站立会议。

## 一切工作任务围绕 Ticket 开展

- 从甘特图到看板：白板分「To Do（待选取）/ In Progress（进行中）/ Done（完成）」等栏，工作任务变成五颜六色的即时贴；物理看板演进为电子看板，即时贴变成 Ticket（也有叫 Issue 的）。
- Bug、需求、重构全部提交 Ticket，所有开发相关任务都和 Ticket 挂钩。
- 好处：每个任务状态可跟踪（何时开始、谁在做、做完没）；团队在做什么一目了然；Ticket 与 Backlog（任务清单）结合，可管理整个项目和当前 Sprint 的 Backlog。
- 项目经理看 To Do 剩余量可知还剩多少没完成，看 In Progress 是否有 Ticket 滞留可判断风险、及时介入。

## 基于 Git 和 CI 的开发流程

- 瀑布模型两大烦恼：代码不稳定（都在 master 上开发，上线前设「代码冻结期」）和部署太麻烦（专人部署测试环境，几周才部署一次）——这都不敏捷。
- 解法：Git 分支管理 + 代码审查（Code Review）+ 自动化测试 + CI 自动部署。
  - 不从 master 直接提交，而是基于 master 克隆 branch 开发，完成后提交 PR（Pull Request），其他人可对每一行代码写评论；
  - CI 像一个机器人：每次提交创建干净环境，下载代码、安装依赖、运行全部测试代码，结果反馈在 PR 上（绿色通过、红色失败）；
  - **PR 合并的两个条件：CI 变绿 + 代码 Review 通过**，合并后 master 代码仍稳定；
  - 合并后 CI 自动构建 Docker Image，自动部署到开发/测试环境。

开发流程：To Do → In Progress → 从 master 建分支开发（写实现代码 + 单元/集成测试代码）→ 持续提交 → 创建 PR 邀请 Review → CI 检查代码格式、运行单元测试和集成测试 → 合并 → CI 自动构建部署 → Ticket 移入 Done。紧急任务来不及写测试也要再建 Ticket 跟踪补上。

部署流程：早期运维按文档手动部署（几周一次）；现在 DevOps 写自动化部署工具、开发自己部署生产环境。控制点：部署物是 Docker Image；生产前先在测试环境充分测试；生产部署需审批确认、有 Ticket 跟踪；先部署一部分，监测正常后全量；全程监控报警，可回滚。顺利时整个过程几分钟完成。

## 每日站立会议

- 上班第一件事一起开站会；站着不重要，重点是高效沟通反馈，时间控制在半小时以内。
- 主持：通常由 Scrum Master 负责，也可每周轮值；主要职责是组织会议、控制节奏。
- 三个话题：
  1. **轮流发言**：昨天做了什么、今天计划做什么、有没有障碍；跑题内容记入「问题停车场（Parking lot）」先保证节奏；
  2. **检查最新 Ticket**：甄别优先级，决定放当前 Sprint 还是 Backlog；
  3. **停车场问题**：能会上解决的马上解决，不能的会后讨论或另组织会议。
- 作用：成员相互了解进展、互相支援、及时发现问题和风险；每个人对自己提出的目标会信守承诺。
