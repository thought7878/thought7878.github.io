# 《"一问一答"第2期丨30个软件开发常见问题解决策略》总结

> 来源：本专栏第 20 讲后加餐 · 需求分析篇

## 一句话结论

宝玉针对项目管理、需求分析模块的 30 个高频提问逐一作答，核心策略可归纳为：用机制代替人治（如扑克牌打分）、计划要细粒度早发现、文档会议流程服务于沟通确认、工具解决重复问题。

## 管理与团队

- **No.1 可行性分析形同虚设、老板拍板怎么办？** → 核心是缺少类似扑克牌打分的机制和流程：公平合理、每个人可不受他人影响表达、不用背锅、估错可讨论，项目结束后回顾对比作为下次参考。
- **No.2 架构师是管理岗吗？** → 与管理相通处：都需要大局观、沟通能力、善用流程工具、分而治之；不同处：项目经理对人负责，架构师对架构负责。两者互为补充。
- **No.3 目标不一致怎么办？** → 多一对一沟通；自己创造激励制度——"激励制度并不一定要花钱或者花很多钱，有时候正式的表扬比钱还有价值"。
- **No.4 小公司用制度还是人管？** → 无论大小公司都多用合理制度流程和工具，摆脱对人的过度依赖，但设计流程要充分结合公司特点；小公司老板权力大，要做好隔离措施防止破坏流程。
- **No.5 培养的下属把自己边缘化了？** → 看长远，"我不需要靠一个老板的赏识与否来证明自己"。
- **No.6 老资历技术大牛不服管？** → 一对一沟通了解诉求、安排有挑战任务、充分发挥优势、用"鲶鱼效应"减少不可替代性；负面影响大于贡献可隔离或劝退。
- **No.7 管理者被技术人员瞧不起？** → 自己懂技术、让项目成功证明实力、换位思考尊重技术、帮助他们成长涨薪少加班、多用流程规范少基于人管理。

## 项目计划与进度

- **No.8 开发不紧不慢耽误时间怎么办？** → 计划正是用来防患未然的：5 天的任务若粒度是 5 天，到最后一天才知道延迟；粒度放到半天一天，第二三天就能发现并调整。"至于奖惩制度，只是手段，而不是目的！"
- **No.9 计划会迭代吗？** → 一定迭代，且是从粗到细：先定里程碑，再细化下一阶段；细化要拉上具体参与人一起制定；里程碑定了不要轻易变。
- **No.10 敏捷的项目计划？** → WBS 分解后变成 backlog，打分后估算需要多少 Sprint；里程碑通常几个 Sprint 一个，不会那么密集。
- **No.11 各方不参与计划制定？** → 分析不参与的原因（利益不相关、没发挥空间、说了也不算）；让这事跟绩效挂钩，拉领导支持，里程碑节点务必让相关方参与。

## 会议、文档与流程

- **No.12 业余项目怎么开始？** → 做个小的、做个实用的（自己或身边人能用）、迭代开发第一版只做核心功能。
- **No.13 里程碑要做集成测试吗？** → 取决于里程碑目标（具备联调条件 vs 测试验收通过）；要人力和时间的事都应放进计划。
- **No.14 需求文档和测试用例怎么验收？** → 开需求评审会，开发和测试都要派代表参加；性能测试可同步生产环境真实数据（按比例缩放），或在半夜直接在生产环境做。
- **No.15 流程由谁制定？** → 好流程常由与问题切实相关的人员提出；可参考 Sprint 回顾会议、一对一会议讨论问题并落实推广。
- **No.16 开完会还要找产品确认？** → 会前读文档、记录疑问，会上提出；开会前先了解会议目的并准备。
- **No.17 项目全程有哪些会议？** → 启动会（Kick off meeting，了解目标/里程碑/分工/流程）、瀑布各阶段评审会与说明会、进度报告会（周例会/每日站会）、项目计划会、产品演示验收会（Sprint Review）、项目总结会（Sprint Retrospective）、一对一会议（了解更真实的信息）。
- **No.24 各阶段有哪些文档？** → 立项：原始需求文档、可行性分析报告、立项说明书；需求：原型设计文档、产品设计文档；设计：技术方案、详细设计；开发：代码规范；测试：测试用例、测试验收报告；运维：部署文档、故障报告。
- **No.25 详细设计要多细？** → 2002 年推荐的细化到伪代码级别实践证明不可行（成本接近写代码、压缩程序员创造空间）；推荐不要太细，模块设计交给负责该模块的人，管理者指导。
- **No.26 需要 PRD 和需求规格说明书吗？** → 没有特别标准，瀑布有专门文档，敏捷可能是每个小功能一个 User Story 或独立产品设计文档；目的都是让大家可以讨论、理解需求。

## 工具与架构

- **No.18 各阶段典型工具？** → 需求：Ticket 系统（Jira）、源代码管理（git）、文档工具；设计：Visio/PPT 画图；编码：IDE、Jenkins 持续集成；测试：TestRail、Jira；运维：ELK 日志、Wavefront 监控、PagerDuty 报警。
- **No.19 燃尽图预测有天然偏差？** → 是的，任务复杂度不同，剩下一个任务可能是最难的；宝玉更喜欢看板视图，直观看到当前 Sprint 具体什么任务没完成。
- **No.20 Jira 怎么建任务？** → Ticket 间可建立关联；修改 Sprint 属性切换看板、修改状态切换泳道；同一需求多端开发可克隆（Clone）Ticket。
- **No.21 前后端分离联调等待？** → 服务端先实现模拟接口、客户端自己模拟、或用第三方服务（easy-mock、MockServer、apizza 等）。
- **No.22 风险管理要加时间维度？** → 把时间、范围、成本三要素约束加上即可：创业期人是最大风险（成本约束），发展阶段时间成为约束，技术和架构跟不上效率就成为新风险。
- **No.27 什么是模块？高内聚低耦合？** → 模块是对某类需求的抽象，可从架构层面（UI 层/业务逻辑层/数据访问层）或业务层面看；低耦合指改动互相不受影响（如前后端通过 REST API，API 不变后端用什么语言都行），高内聚指模块内代码关系紧密（如所有用户操作都在用户模块）。

## 敏捷参与与产品

- **No.28 敏捷中产品部门怎么参与产品设计？** → 技术难度高的设计两边多沟通，共同制定技术难度适中又满足需求的设计；开发充分理解产品设计；通过需求评审、分批需求讲解会、每个 Sprint 及时沟通确认。
- **No.29 前后端分离如何提升原型代码重用？** → 快速原型分抛弃型和演化型（类似 MVP）；建议用第三方 API 云服务（Apollo GraphQL、Firebase Firestore），先不考虑后端，产品出来后再迁移。
- **No.30 Windows 和 Linux 易用性差别是产品意识差异？** → 宝玉认为本质是产品定位不同：Windows 是商业产品面向普通用户，Linux 是开源产品面向专业用户。

## 精选留言要点

- **流程规范落地**（Felix）：整理 wiki 目录、简化重点规范、每周重点强调 1-2 个；管理者关键时刻写个小 Ticket，深入了解系统、树立威信。
- **技术转管理**（alva_xu）：管理牵涉"人""工具""流程"三部分；项目经理最大责任是风险管理，控制范围、成本、时间。
- **写不写代码**（dancer 与宝玉思辨）：一线管理可保持写代码以保有技术领导力；宝玉补充"尽可能保持一个合适的比例，团队越大职责越多，写代码比例要越少"。
- **计划的作用**（alva_xu）：计划是有序组织资源以便及时识别变化、应对变化；拆解任务定故事点、找关键路径、设指标看板及时监控。
- **工具化与自动化**（alva_xu）：流程除工具化还要自动化——用 SonarQube 集成 CI 取代 IDE 插件检查，不怕项目组不执行。
- **会议有效性**（青石）：会议要有时间地点人员主题，会前准备、会中有结论（指定干系人）、会后跟踪；没有主题、结果、跟踪的会议都是无效会议。
- **程序员焦虑与软实力**（kirogiyi）：产品意识是软实力，"技术是工具，思维可以变，灵活多变最重要"；综合培养硬实力和软实力的人更有生命力。
