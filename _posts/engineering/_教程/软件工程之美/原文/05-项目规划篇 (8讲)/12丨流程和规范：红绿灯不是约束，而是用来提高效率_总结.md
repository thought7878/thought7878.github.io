
## 一句话结论
`流程规范`就像红绿灯：牺牲一点个体效率换取团队效率，把好的实践标准化、流程化，让大家共享经验，让项目管理从人治走向"法治"。

## 为什么要有流程规范？
| 价值                   | 说明                                                                              |
| -------------------- | ------------------------------------------------------------------------------- |
| **提升团队效率**           | 单个车辆看红绿灯是阻碍，整体看却避免了拥堵；`代码审查`对高手是耽误时间，对团队却降低出错概率，还帮低水平成员学习成长                     |
| **将好的实践标准化流程化，共享经验** | 优秀运动员的动作被研究成标准动作；编程高手的写法沉淀为`代码规范`；`瀑布`、`敏捷开发`落实下来都是一个个`流程规范`（阶段评审、站立会议、计划会、评审会） |
| **从人治到"法治"**         | 过度依赖人的管理，项目经理会成为瓶颈且难保决策正确；靠流程规范，项目可长期井然有序运转（作者经历：项目持续多年、人员换了一批又批，靠积累的流程规范不出问题）  |

> **好的项目管理**，*不需要直接去管人管事，而是管理好计划和流程规范；项目成员不需要按照项目经理的指令做事，而是遵循计划和流程规范*。

**典型场景：需求变更**——有大家认可的变更流程，就不靠项目经理一人决定加不加需求，而是通过流程一起决策。

## 如何制定好流程规范？四个步骤
1. **明确要解决的问题**——如*程序员在生产环境误删数据表*，仅处罚不能防止复发；要靠流程：操作前备份数据库、事先写好 SQL 并审查、测试环境先验证、最后才在生产执行
2. **提出解决方案**——*方法针对特定场景/人，流程规范需有普适性*（高手直接上服务器改代码不能成为规范，"回滚操作"才可以）。可借鉴的成熟实践：
   - `敏捷流程`：看板、站立会议、持续集成
   - `代码规范`：Airbnb JavaScript Style Guide、Google Java Style Guide、.NET Guide 等
   - `源代码管理`：阮一峰的 Git 流程系列、GitHub Flow、GitLab Flow
   - `部署流程`：从每日定时构建演进到`持续部署`（代码合入主分支即触发自动部署）
3. **达成共识，推广执行**——大家认可才能共同遵守；重要规范需严格执行，可配合奖惩制度（如与绩效考评挂钩），否则形同虚设
4. **持续优化，不断改进**——执行中发现不合理就调整；过时的规范要改进甚至抛弃（如有了站立会议，日报就可被替代）

## 将流程规范工具化
任正非《全面提升软件工程能力与实践，打造可信的高质量产品》公开信：

> "软件工程"和"质量工程"需要依靠架构技术，而不是依靠 CMM 和 QA 管理流程。一切工程问题，首先要思考能否通过技术解决，当前技术无法解决的问题，暂时由管理手段代劳，同时不停止寻找技术手段。

实践：*用 ESLint 等工具*自动检测并格式化不合规范代码；*用 CI（持续集成）+ 自动化测试 + Git* 保证代码通过测试才能合入主分支。
