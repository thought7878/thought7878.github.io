> 来源：本专栏第 9 讲 · 项目规划篇

## 一句话结论
`可行性研究`是**项目启动前最关键的一步，从经济、技术、社会三个维度提前论证，能最早发现风险、避免损失**；哪怕结论无法改变决策，事后与结果对比也是宝贵的经验积累。

## 为什么教材上简单的知识点很重要
可行性研究在软件工程教材中仅次于"绪论"，回答"**主要从哪几个方面进行**"只需记住三项：

| 维度      | 关注点                          |
| ------- | ---------------------------- |
| `经济可行性` | **成本与收益，看投入产出比，兼顾短期与长期利益**   |
| `技术可行性` | **技术能否实现，人才储备是否足够，技术风险能否规避** |
| `社会可行性` | **法律**、道德、社会影响等社会因素          |

## 案例：一个从一开始就注定失败的 React Native 项目
- 2015 年 Facebook 推出跨平台移动端方案 React Native，一套 JavaScript 代码可运行于 iOS、Android
- 2016 年某著名大型互联网公司移动部门负责人看好该技术，成立项目组，花大半年将 iOS、Android 产品迁移过去
- 快上线时，法务部门发现 *React Native 的开源协议是 "BSD+专利"*：若对 Facebook 及其子公司提出专利诉讼（无论是否与本协议有关），*用户的全部专利权利自动终止——两家公司存在竞争关系，一旦纠纷必输官司*
- *项目被迫叫停，大量人力财力全打水漂*；2018 年 Facebook 改为友好的 MIT 协议，也为时已晚

*若立项前让法务评估社会（法律）可行性，这笔损失完全可以避免*。

## 为什么软件项目很少做可行性研究？
1. **"因为我们是软件项目，所以我们很特殊"**——*需求和方案早期模糊*，有"先有鸡还是先有蛋"的困境。但这不能成为借口：*需求逐步明确后要继续研究，发现不可行，应及时调整方案或停止项目以止损*。
2. **"老板拍板的项目，明知道不可行也得干"**——分两种情况：负责人决策权大、不容忍异议时，执行者仍应站在专业角度科学反馈（项目失败自己也受损失）；*也可能是老板信息更全面、有战略考虑*（如 2009 年阿里云，反对者占绝大多数，马云、王坚等少数派最终被证明是对的）。
3. **"可行性研究会阻碍创新"**——恰恰相反，它提前过滤不靠谱的创新想法、发现风险。

## 如何做好可行性研究
**"当你决定要做可行性研究，你就已经成功一半了，怎么做，反而是相对简单的部分。"**

以 React Native 项目为例：
- **经济可行性**：10 人 × 10000 元/月 × 半年，加软硬件*成本约 166 万元投入*；上线后*每年收益约 260 万元*，不到一年回本 → *可行*
- **技术可行性**：技术成熟稳定且有成功案例；5 名成员有 RN 经验，其余人员约 3 个月培训可上手；少量老旧安卓机型不支持但占有率极低，可忽略 → *可行*
- **社会可行性**：不违法、无道德和社会负面影响，*但 BSD+专利协议存在法律风险* → **不可行**

结论：与公司法务进一步沟通确认后，及时冻结项目，避免了浪费，还赢得了寻找其他解决方案的时间和机会。

## 延伸建议
- *万事皆项目*：做性能优化，先列成本收益；换工作，最好换算成时薪看长期是否合算
- 重点关注法律风险（如竞业协议可能带来的巨额赔偿）
- 可行性研究结论不明确时，可小范围试点，*先实现最小化可行产品（MVP），验证后再逐步加大投入*

> 哪怕你做的可行性研究不能改变决策，最后项目结束的时候，和当初做的可行性研究做一下对比，也都是非常宝贵的项目经验积累。
