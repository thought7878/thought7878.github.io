
## 一句话结论

技术选型本质是项目决策而非单纯技术选择，必须受制于时间、范围和成本约束，按"问题定义—调研—验证—决策"的科学流程，避开"观点当事实"和"先入为主"两个坑。

## 技术选型就是项目决策

技术选型看似是技术选择，实则是与项目情况密切相关的项目决策，具备三个特点：

| 决策要素 | 说明 |
|------|------|
| 时间/范围/成本约束 | 项目金三角，三因素动态变化，需及时调整技术决策 |
| 可行性和风险 | 如忽略 License 法律风险导致跨平台项目失败；选 React 未预估风险导致项目延迟 |
| 利益相关人 | 兼顾客户成本、产品经理的体验诉求等各方利益 |

常见坑：
- 把听到的观点当事实（React 粉丝只讲优点不讲学习曲线；鼓吹 MongoDB 的可能是软文），决策前至少验证一下；
- 先入为主，有了结论再找证据（偏爱 React 就只收集对 React 有利的数据）。

## 如何做好技术选型？

借鉴工程方法设计流程，分四个阶段：

1. **问题定义**：回答两个问题——为什么需要选型？目标是什么？漫画《The problem is not the tool itself》的教训：MySQL 慢就急着迁 NoSQL，其实只是忘了建索引。很多时候基于现有技术优化即可，不必引入新技术。目标明确才有评判标准（飞信 PC 第二版目标就是提升开发速度，故选 C#）。
2. **调研**：从是否满足目标、满足时间范围成本约束、是否可行、风险是否可控、优缺点五方面分析，筛选后保留 2-3 种方案。
3. **验证**：做小型快速原型。案例：飞信第二版选 C# 时，.Net Framework 打包体积过大，发现 Salamander 可只打包所需 dll，配合 7zip 最终将安装包控制在 10mb 左右，验证可行才拍板。
4. **决策**：召集利益相关人评审调研结果；科学流程不保证决策正确，但能提高正确概率；纠结时负责人要勇于拍板——"有时候迟迟不选择、不拍板才是最坏的结果"；项目结束后复盘总结，完善决策机制。

## 总结

选型要像项目决策一样思考：受制于金三角约束，分析可行性和风险，考虑利益相关人，避开常见坑。流程是：明确目标、充分调研、验证备选、共同决策。选定后不要太纠结，坚定执行。
