# 《35丨版本发布：软件上线只是新的开始》总结
> 来源：本专栏第 35 讲 · 运行维护篇

## 一句话结论
做好版本发布的关键是：发布前合理规划，在用户预期与软件实际之间取得平衡；再用规范的发布流程保障质量，且上线只是新的开始。

## 关于软件版本
版本有两层含义：特定功能集合（产品经理视角）+ 某一次代码构建结果（开发视角）。业界命名规范为「主版本号.子版本号[.修正版本号[.构建版本号]]」：

| 版本号 | 含义 |
| --- | --- |
| 主版本号 | 大功能变化 |
| 子版本号 | 小功能变化 |
| 修正版本号 | 功能不变，修复 Bug |
| 构建版本号 | 一次新构建，通常编译程序自动生成 |

版本定义清晰后，开发知道代码进哪个版本，测试知道在哪个版本验证 Bug。

## 版本发布前，做好版本发布的规划
核心观点：不存在完美软件（Windows、Office、iOS 发布后也要打补丁），关键是**在用户心理预期和软件实际情况之间达到一种平衡**。

| 规划内容 | 要点 |
| --- | --- |
| 发布的功能 | 区分用户必须 / 非必须功能，非必需功能可后续逐步完善 |
| 质量标准 | 用户在意功能高标准（如微博撰写内容时异常丢数据难忍受），不在意可低标准 |
| 发布策略 | 内部用户试用 / Beta 版 / 灰度发布，降低用户预期 |
| 发布计划 | 与客户、市场运营等利益相关方共同确定时间点 |

案例：第一代 iPhone 没有复制粘贴，但界面和触屏出色，照样取得极大成功；Gmail 最初几年一直是 Beta 版。

## 规范好发布流程，保障发布质量
常见风险：发布错版本（拼多多误发测试用无门槛券，被薅走几千万羊毛）、发布前频繁改代码致质量不稳定、发布失败无法回滚。参考流程：

1. **代码冻结**：建 release 分支，只修重要 Bug，使质量趋于稳定；
2. **Bug 分级**：项目负责人 + 产品负责人确认哪些发布前修、哪些发布后修；
3. **候选版本**：每修一个 Bug 生成新 RC（如 1.1 RC1/RC2），与持续集成整合全自动生成，避免人为失误；
4. **回归测试**：每个新 RC 部署测试环境后，重测主要流程 + 确认已修 Bug 未引入新问题；
5. **申请上线**：审批统筹，避免上线随意、与其他部门冲突；
6. **部署发布**：尽量自动化；未自动化则事先写好详细操作步骤照做；
7. **上线后测试**：立即测主要功能，同时监控 CPU、内存、服务出错率，出问题按预案回滚；万不得已不建议马上打补丁，小改动也可能引入新 Bug。

## 软件上线只是新的开始
- 建立用户反馈渠道，收集反馈完善产品；
- 主动监控：App Crash Log、服务器资源、API 出错率、网页响应速度，数据异常时及时回滚或发补丁。
