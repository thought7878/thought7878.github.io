# 《37丨遇到线上故障，你和高手的差距在哪里？》总结
> 来源：本专栏第 37 讲 · 运行维护篇

## 一句话结论
线上故障处理水平是新手与高手的分水岭：高手遵循「先恢复生产减少损失，再定位修复，最后复盘根治」的步骤，大厂则把这套做法制度化为轮值报警、实战演习和日志分析机制，让新手也能高效处理。

## 新手与高手的四个差距
| 新手 | 高手 |
| --- | --- |
| 复杂故障（内存一直涨、CPU 居高不下）不知下手 | 按总结的步骤有条不紊：①评估影响范围 ②试图重现问题 ③临时方案和终极方案 ④风险评估及持续优化 |
| 发现 Bug 就马上写代码打补丁 | 先故障评级，核心业务大面积受影响时当务之急是恢复生产（回滚到稳定版本、重启服务），修复 Bug 其次 |
| 不知如何快速定位 Bug | 用有效手段逐步缩小范围：重现问题、分析错误日志、分析部署间变更代码、内存 Dump 分析、多服务场景配合日志用排除法 |
| 临时方案（如重启）恢复后就忘记 | 从根本分析原因，避免同类故障再次发生 |

金句：**恢复生产、降低损失是第一要务，修复 Bug 是其次的。** 恢复前要尽可能保留日志、故障截图、内存 Dump 供后续分析。

案例：作者项目组每周 Sprint 上线后常故障回滚，深层次原因是上线前测试不充分（3-4 天开发 + 1-2 天测试）；改为在测试环境测试一周后再上线，极少出现线上故障。

## 大厂处理线上故障的流程
1. **故障评级**：按影响范围定级（P0 大面积服务瘫痪需紧急处理，P5 仅体验问题可晚处理）；
2. **马上恢复生产**：用部署回滚、服务降级等临时方案减少损失，第一位；
3. **分析原因，修复故障**；
4. **记录全过程**，分析原因，提出改进方案。

## 值得借鉴的三个机制
- **故障报警 + 轮值机制**：每个服务每周安排两人值班（主 + 备），值班周手机 24 小时开机、笔记本随身；故障时报警系统第一时间呼叫，15 分钟无人响应则层层上传（经理→总监→VP→CEO）。关键是让正确的人（最熟悉服务的开发）第一时间响应。
- **实战演习**：备份恢复方案不演习就可能完全不可行（作者亲历数据丢失）。Netflix 的 Chaos Monkey（混乱猴子）在工作日随机杀死一些服务制造混乱来测试稳定性，即「混沌工程」——像疫苗：注入少量潜在危害以建立免疫力。
- **日志记录和分析工具**：平时开发记录关键日志，搭建 ELK 或 Splunk；给每个请求分配唯一 requestId，经过每个服务都带上并记录输入输出，故障时按 requestId 一次查出问题服务。新功能上线还可配合灰度发布 + 开关控制，出故障立即关闭。
