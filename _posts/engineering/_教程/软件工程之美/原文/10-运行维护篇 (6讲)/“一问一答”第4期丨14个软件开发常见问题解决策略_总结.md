# 《“一问一答”第4期丨14个软件开发常见问题解决策略》总结
> 来源：本专栏「一问一答」第 4 期 · 运行维护篇

## 一句话结论
本期围绕测试、DevOps、线上故障和项目复盘回答 14 个常见问题：质量靠功能/代码/过程三方面共同保障，自动化测试宜按金字塔配比并接入 CI，DevOps 落地从把自动化工具整合进开发流程开始，线上故障先恢复生产再定位根治。

## 模块回顾（开篇）
- 软件质量体现在功能质量、代码质量、过程质量三方面，测试只能保证功能质量；
- 大厂手工测试岗位减少，测试工作转向开发，自动化测试比例越来越高；
- 线上故障处理原则：先恢复生产减少损失，再找原因，最后总结复盘；
- 项目结束后复盘，把好的实践发扬光大，不好的马上停止并改变。

## 一问一答（按主题分组）

### 质量与团队协作
- **问：质量怎么打分、算 KPI 吗？用 sonar 自动检查可以吧？** → 不好量化，工具只是辅助参考。代码质量看满足需求、设计良好、简洁清晰、可维护可测试、安全高性能；过程质量看软件工程和项目管理知识的应用；功能质量看客户满意度。
- **问：开发对测试人员傲慢怎么管理？** → 核心是多合作多相互了解，让开发看到测试的核心价值是测试方案设计（总能从没想到的角度测出 Bug）；可让开发按测试用例实现自动化测试，体会测试不容易。

### 测试用例与自动化测试
- **问：有好用的测试用例模板吗？** → 推荐 TestRail。关键字段：标题、描述、优先级、分类；另含测试类型（功能/性能/回归/冒烟）、自动化状态、先决条件、测试步骤、期望结果。
- **问：TDD 先写测试再写实现，写完还要专门测试测吗？** → TDD 是好的实践但普及率不高；它写的是单元测试，不能保证不出 Bug；开发测自己代码容易遗漏编码时就没考虑到的逻辑。
- **问：全量自动化测试耗时、产生大量历史数据、高覆盖率难写怎么办？** → ①自动化测试金字塔：单元测试约 70%（1 分钟内）、集成测试约 20%（10 分钟内）、端对端约 10%，CI 跑单元+集成耗时 10-15 分钟可接受；②数据库策略：单元测试不访问数据库完全模拟，集成测试用本机/内存数据库并新建或清空，端对端用唯一数据（固定数据+时间戳）连真实测试环境；③不必追求 100% 覆盖，70% 以上就不错，关键是写代码时就让代码方便被测试。
- **问：测试脚本、用例、数据如何配合通过 CI 自动化？** → CI 像流水线传送带：提交代码后启动干净虚机（Docker Container），下载代码配好环境，可添加任务——装依赖、跑模拟服务（内存数据库）、跑单元测试、跑集成测试，全成功则 CI 成功。

### 流程与协作
- **问：非软件公司，需求到运维全是我一个人，怎么做得更好？** → 从工具（源码管理/CI/Bug 跟踪）、开发流程（周期长短、需求确认、技术设计、测试用例、故障处理流程、文档）、技术实践（自动化测试、框架、自动部署）三方面分析改进；一个人缺合作学习机会，可有意识创造——内部跨部门合作、参与开源项目。
- **问：Code Review 是大屏幕一起看还是 GitHub PR？** → 两种都算，形式不同。PR 式应贯穿日常，1-2 人 Review 通过即可，合并还需自动测试通过；大屏幕式人多成本高，适合特殊故障分析、学习研讨。

### 部署与架构
- **问：实时数据采集场景，对方持续推送，部署新版时丢数据怎么办？** → 拆出一个极简独立接收服务，只负责接收数据并存入数据库/消息队列；原服务改为从库/队列读取；更新部署不轻易动接收服务，真要更新就和对方协商暂停推送。
- **问：小版本迭代中 UI 岗位工作量不饱和，问题在哪？** → 若 UI 是必须岗位且完成得好就没问题（效率高好过磨洋工）；若可有可无，可不设岗、外包、用标准 UI 或让前端兼职。

### DevOps 与自动化
- **问：推荐一套小公司快速部署的 DevOps 工具？** → 持续集成用 Jenkins 或 Gitlab CI；日志监控用 ELK（Elasticsearch + Logstash + Kibana）。
- **问：都自动化了，是不是不需要运维和测试了？** → 自动化只是把重复体力活做了；自动化测试仍需测试写用例才有效，自动化部署监控离不开专业运维设计搭建；但低端手工测试和运维岗位会被挤压厉害，大厂招聘中极少。

### 线上故障与日志
- **问（甲方内部系统）：故障处理谁主导？排查要不要标准分析过程？便利性和安全怎么平衡？** → ①主导者要懂技术懂业务（能评级）且能调动开发运维协调；②非应用故障（操作系统/数据库/网络）运维负责，应用服务故障开发负责（只有开发最清楚程序结构），运维配合；③搭建 ELK 日志系统，应用日志放上去，平时不用登服务器即可查异常，特殊情况应允许开发登服务器排查。
- **问：目前只有 nginx 日志，还有哪些日志该放进日志服务？** → 应用程序日志也要放，异常信息、错误堆栈非常有用；如 App 某 API 出错背后连多个服务/数据库，光靠 nginx 日志不够；可参考 requestId 实践。

## 留言精选
- **产品/开发/测试都应对质量负责**（kirogiyi）：产品设计重视需求完整与用户体验，开发是核心决定质量和迭代周期，测试发现问题、监督解决、约束行为；三方紧密合作是质量保障的必备条件。
- **新手用野路子，高手用模型**（纯洁的憎恶）：①给问题评级 ②尽快恢复生产 ③搜集证据、粗调精调缩小范围锁定问题 ④分析原因修复 ⑤沿线索倒带找根源，站在系统和流程高度制定方案防复现。重点：报警+轮值让正确的人第一时间响应、实战演习确保预案可行、日志工具积累日常生产信息。
- **线上故障是 ITIL 要解决的问题**（alva_xu）：流程（事件/问题/变更/服务等级管理）、工具（ticket、CMDB、监控、日志平台）、人员组织（一二三线按严重性分级支持）三方面，也是 DevOps 要解决的问题。
- **复盘会要有效需做准备**（邢爱明）：会前核心人员先书面总结好与不好；主持人需强主导能力，防止复盘会变甩锅会，正面引导讨论解决方案。
- **思辨时刻**：小团队也应加大自动化测试投入，磨刀不误砍柴工；项目负责人是质量总责任人，还要兼顾范围/时间/成本（金三角），质量保障需公司层面支持；瀑布模式下复杂业务仍需要专职测试（业务分析师重点是写清需求文档）；DevOps 自动化没有明确定论，重要的是有应用自动化的意识，把工具整合进开发流程——提交时代自动测试、合并后自动部署、上线后监控报警。
