# 《33丨测试工具：为什么不应该通过QQ-微信-邮件报Bug？》总结

> 来源：本专栏第 33 讲 · 软件测试篇

## 一句话结论

报 Bug 要用结构化的 Bug 跟踪工具而非 QQ/微信/邮件——前者可分类检索、可跟踪、把 Bug 解决过程流程化；同时应借助自动化测试及性能、安全、兼容性等工具发现 Bug，并接入持续集成以最大化价值。

## Bug 跟踪工具

历史：1947 年飞蛾钻入哈佛计算机诞生"Bug"一词；1992 年首个专业 Bug 跟踪软件 GNATS，此后有 Bugzilla、Jira、MantisBT 等。

QQ/邮件报 Bug 的三大问题：

- Bug 不能被有效跟踪，不知是否已修复
- 效率低，频繁打断开发手头工作
- 无法直观了解项目 Bug 状态（修复多少、还剩多少、近期增减）

工具的核心价值：结构化定义 Bug——标题、描述（期望结果、实际结果、重现步骤）、优先级、指派人、状态（New、Open、Rejected、Fixed 等），便于检索（如"所有指派给张三的 Bug"）；贯彻"把好的实践流程化，把好的流程工具化"，Bug 状态背后是一套完整解决流程。

使用注意事项：

- 所有 Bug 统一进 Bug 跟踪系统管理
- 一个 Bug 一个独立 Ticket，不合并（否则一个未验证通过就要 Reopen 整个 Ticket）
- 描述清楚重现步骤，附日志截图
- 不当讨论板：开发与测试争议时，主动拉上相关人当面确认解决

## 自动化测试工具

趋势：Facebook、Google、Amazon 手工测试职位减少，重复执行外包至低成本国家，本土招聘能写自动化测试的测试或开发。作者类比修路：偶尔走几次可不修路（手动测试），频繁通行就该修高速公路（自动化测试）。

建议：测试学基本编程（主要是 API 调用，门槛不高，回报巨大）；项目加大投入、让开发参与；按软件特点选几款工具搭建环境试用。

| 类型 | 代表工具 |
| --- | --- |
| Web 自动化 | Selenium、WebDriverIO、Nightwatch.js |
| 移动端 | Appium（iOS/Android）、Macaca（阿里，多端） |

## 其他测试工具（附录精选）

| 类别 | 工具 |
| --- | --- |
| Bug 跟踪 | Bugzilla、MantisBT、Redmine；Jira、禅道、TAPD、云效 |
| 压力/性能 | JMeter（开源纯 Java）、LoadRunner（HP 商业）、阿里云 PTS、WebPageTest |
| 安全 | Fortify On Demand、Sqlmap（SQL 注入检测）、IBM AppScan |
| 兼容性 | Browsera、Browslering |
| 用例管理 | TestRail、飞蛾（Coding 旗下） |

最大化工具价值：与 CI 集成——如每次构建运行 JMeter 压力测试，性能低于阈值则构建失败，第一时间发现并缩小问题范围。
