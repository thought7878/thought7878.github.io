# 《“一问一答”第3期丨18个软件开发常见问题解决策略》总结

> 来源：本专栏「一问一答」第 3 期 · 开发编码篇

## 一句话结论

本期为架构设计与开发模块的 18 个常见问题答疑，覆盖技术选型、文档、重构、持续集成、自动化测试、Code Review 等主题；核心思想是具体问题具体分析，最佳实践也要看适用场景与团队。

## 架构与实践结合

- **问**：架构思想总是和实际应用结合不好，是实践不够吗？
- **答**：要有不同场景的实践；把看到的架构用原型程序搭一遍、造数据、压测，会更有感觉。

## 项目文档

- **问**：比较规范的文档有哪些，功能分别是什么？
- **答**：必要文档分三类——**设计类**（需求/架构设计，供了解、讨论、评审）、**说明类**（规范、API、配置、操作说明）、**报告类**（验收报告、故障报告）。价值在降低沟通成本；测试用例文档、部署文档等已基本被测试工具和部署脚本替代，可简化合并。

## 技术选型

- **问**：外包团队水平参差，只能选成熟通用技术，长远是否难提升？
- **答**：技术提升与项目选型分开，优先保证项目稳定、低成本运行；用业余项目体验新技术，再逐步引入工作项目、传授同事。
- **问**：开源技术选型经验？
- **答**：朋友推荐 → 搜索备选 → 对比代码质量/有无测试、文档健全度、Issue 处理与最后更新时间、Star 与社区使用情况 → 自己试用。
- **问**：选型大原则？
- **答**：成熟好过新酷、流行好过小众、团队熟悉好过陌生、简单好过复杂、开源好过商业；前提是满足设计目标、成本与时间可控、风险可控。

## 架构师职责与互联网/企业架构对比

- **问**：架构师架构设计后产出哪些"东西"？
- **答**：架构设计文档 + 开发文档（公共 API、最佳实践、规范）+ 脚手架与示例项目 + 开发中答疑、优化架构、代码审查。
- **问**：互联网架构与企业架构的差异？
- **答**：互联网迭代快、用户规模大、业务相对单一；企业应用业务复杂、用户规模小，特点影响架构选择。

## 重构与事务管理

- **问**：重构的要领？
- **答**：先写自动化测试保证能检测回归；老代码保留、写新代码，用开关切换新旧指向，测试通过、部署验证后再删旧代码。
- **问**：事情管理工具？
- **答**：记事本或显示器贴便签；时间跨度长的记 Calendars 加提醒；工作任务建成 Ticket。

## 分支、合并与持续集成

- **问**：提倡主干开发，怎么看？
- **答**：没有唯一解，核心是两点：有一个可随时发布的稳定分支；合并前有代码审查和自动化测试（配合 CI）。
- **问**：多人开发，后提交的会不会覆盖先修的 Bug？
- **答**：是"合并"不是"覆盖"；各自只提交自己改的文件，冲突手动解决后再合并，开发前先拉取 master 最新代码。
- **问**：微服务测试环境互相依赖，新功能难独立交付？
- **答**：微服务应尽量独立；若每个新功能都这样，说明服务划分有问题，需重新思考；确实需要跨服务的大 Feature，则约定协议、分头开发、再联调。

## 自动化测试与 CI

- **问**：成员水平参差，如何推行自动化测试？
- **答**：搭好环境并接 CI → 纳入流程（审查+测试通过才合并）→ 培训（带着写几个、缺了要求补、来不及的建 Ticket）。即"代码审查 + CI + 培训"。
- **问**：测试覆盖率指标？
- **答**：100% 可作理想追求，但要在进度与质量间平衡；前端业务优先保证主要场景的集成测试覆盖，性价比更高，再逐步补单元测试。
- **问**：持续集成怎么理解？
- **答**：狭义指频繁合并主干且合并前自动化测试通过；广义还包括自动部署测试环境（持续交付）或生产环境（持续部署）。

## 其他高频问题

- **问**：生产问题直接回滚，风险是否更大？
- **答**：视情况而定；日常上线有自动化回滚方案，但数据库结构变化又产生新数据时无法直接回滚。
- **问**：推荐写测试的书？
- **答**：《how we test software at microsoft》（《微软的软件测试之道》）；也可参照 GitHub 上类似开源项目（reactstrap、electron-react-boilerplate）照葫芦画瓢。
- **问**：代码审查有工具吗？
- **答**：GitHub PR Review 已很方便（标记修改、按行评论）；Lint 负责代码规范与语法检查，一般集成在 CI 中。
