# 《30丨用好源代码管理工具，让你的协作更高效》总结

> 来源：本专栏第 30 讲 · 开发编码篇

## 一句话结论

源代码管理工具（VCS）是保存文件多个版本、记录修改历史的机制；用好它只需三个原则——频繁提交、每次提交跑自动化测试、提交有人审查，并配以稳定的分支开发流程（如 GitHub Flow）。

## 源代码管理工具发展简史

| 阶段 | 代表 | 特点 |
| --- | --- | --- |
| 无工具时代（1972 年前） | — | 靠口头协调避免冲突，靠手动备份，难知改了什么 |
| 本地版本管理 | SCCS（1972）、RCS | 单文件多版本，无法协作 |
| 集中式版本管理 | CVS（1986）、SVN | 中央服务器存版本库；SVN 2000 年后取代 CVS；强依赖服务器，服务器损坏则历史丢失 |
| 分布式版本管理 | Git | 本地存完整代码库副本，可离线操作、易恢复，现最主流；学习成本略高 |

## 如何选择合适的源代码管理系统

- **项目规模不大、隐私要求不高**：用托管平台（GitHub、GitLab、Coding、码云、阿里云 Code 等），省运维、易与 CI 等第三方服务整合；
- **想要更多控制**：自建——Git Server（免费无 Web 界面）、GitLab 社区版（Web 界面、支持 PR、集成 GitLab CI/Jenkins）、Gerrit（Google 出品，代码评审）。

## 用好源代码管理工具三原则

1. **频繁提交**：每次变更小，便于 Code Review、可迅速定位或回滚；减少合并冲突。提交内容要完整且分拆（前后端功能分两次提交，重构代码单独提交）；
2. **每次提交后跑自动化测试**：测试不通过不能合并，甄别修复问题；
3. **提交的代码要有人审查**：审查前先理解提交要解决的问题、想象自己怎么写；审查意见分三类——**问题**（澄清确认）、**建议**（有更好实现）、**阻塞**（必须修改）。

## GitHub Flow 开发流程

1. 从 master 创建分支（master 保持稳定，不在其上直接开发）；
2. 频繁提交更新（附说明信息，可随时回滚）；
3. 创建 Pull Request（附描述、关联 Ticket）；
4. 代码审查、讨论（修改后继续提交，PR 自动更新）；
5. 持续集成跑自动化测试、部署验证；
6. 合并 master 后删除分支。

常见问题：发布版本从 master 打 Tag（如 v1.0）；打补丁基于 Tag 或 release-v1.0 分支创建 hotfix 分支，修完发布后再 cherry-pick 合并回 master。无论哪种流程，都要保证：有稳定分支 + 合并前有代码审查且自动化测试通过。
