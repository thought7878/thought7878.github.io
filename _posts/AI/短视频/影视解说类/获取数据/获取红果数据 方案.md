## 三条关键实测结论

**1. 全部剧的清单有官方入口，不用签名**
`hongguoduanju.com` 的 sitemap 分成 29 个分片，单片 42,321 条 `/player/{sid}` 链接，合计约 **123 万部剧**。获取 29 个请求就能拿到全部 ID，robots 也允许 `/player/{sid}`（只禁止 `/player/*/*` 单集页）。

**2. 单剧详情一个请求就拿全 + 评论首屏也能拿到**
`/player/{sid}` 返回 197KB，SSR 内嵌 JSON 直接包含：剧名、简介、标签、封面、总集数、付费类型、可看集数、收藏数（实测 962 万）、单集点赞数（155 万）、全部 `vid`、以及**评论 `total_count`（18388）+ 首屏 15 条正文、点赞数、用户名、时间**。这是本次最大的意外收获——评论不必走 App。

**3. hongguo-web 的官网搜索兜底已经失效**
它 README 说 `/search/{kw}` 有 `searchList`，实测返回 37KB 的空壳，字段不存在。说明**这个项目的接口在月级漂移**，不能把它当稳定底座。

## 可行性判定

| 目标 | 判定 |
|---|---|
| 全部剧清单 | ✅ 直接做 |
| 全部剧元数据（123 万部） | ❌ 240GB / 120 万请求 / 保守 3 天，风控必拦 → 改分层：核心 3000 部 + 每日增量 |
| 单剧详细数据 | ✅ 主路径，免签名 |
| 单剧评论 | ⚠️ 首屏 15 条零成本，全量需签名（头部剧 920 请求/剧，只建议 ≤50 部采样） |
| 播放直链 | ❌ 涉及签名 + CENC 技术措施，数据项目别碰 |

## 合规上的关键一点

robots 允许不等于用户协议允许。真正需要留意的是那段没有变的部分：六个签名头（`x-argus` 等）属于明确的技术保护措施，绕过它拿数据，定性和抓公开网页不一样。所以方案里我把路线定在「官网 SSR 优先」，并且明确不做代理池轮换、设备池伪造、验证码打码——这些是定性问题，不是能力问题。

# 红果短剧数据获取可行性方案

> 评估对象：GitHub `sunnysky123/hongguo-web`（Node 版红果网页播放器）  
> 评估时间：2026-10-27　｜　本文所有关键结论均带实测验证标记  
> 结论：**单剧详情 = 高可行；剧集评论 = 部分可行；全部剧全量 = 工程与合规双不可行，需改为分层策略**

---

## 0. 先厘清一个前提：hongguo-web 不是数据采集器

它是「浏览器里看红果」的播放器，核心能力是**取直链 + CENC 解密 + 下载**，数据类接口只覆盖 5 个：

| 能力                        | 上游接口                                                        | 是否签名              |
| ------------------------- | ----------------------------------------------------------- | ----------------- |
| 搜索                        | `GET /reading/bookapi/search/tab/v`                         | 是                 |
| 剧集详情（支持 `series_id` 逗号批量） | `POST /novel/player/multi_video_detail/preload/v`           | 是                 |
| 榜单翻页                      | `GET /reading/bookapi/bookmall/cell/change/v`               | 否（`SIGN_LIST` 可控） |
| 最新 / 筛选浏览                 | `POST /reading/distribution/category/landpage/v`            | 否（可控）             |
| 播放直链                      | `POST /novel/player/multi_video_model/v1/` → `fallback_api` | 是                 |
| 官网兜底                      | `hongguoduanju.com` 的 `/search/{kw}`、`/player/{sid}` SSR    | 免签                |

**它没有任何评论接口**。评论能力需要单独解决，这是本方案里唯一需要新开辟的部分。

上游基础环境（源码已固化）：

- API Host：`api5-normal-sinfonlinea.fqnovel.com`（列表/搜索）、`api5-normal-sinfonlineb.fqnovel.com`（播放）
- 基础 query：`aid=8662`、`app_name=novelread`、`channel=audit`、`device_platform=android`、`version_code=72232`…
- 签名：`x-gorgon / x-khronos / x-ladon / x-argus / x-helios / x-medusa` 六个头，纯本地计算（盐值硬编码在源码里，无外部密钥拉取），另有 `x-ss-stub` = body 大写 MD5、`_rticket` 毫秒时间戳
- 无登录态依赖（设备侧只依赖 `device_id` / `cdid` / `iid`）

## 1. 实测结论：官网 SSR 是被低估的数据源

我用桌面 UA 直接请求了红果官网，得到的事实（2026-10-27 实测）：

| 探测项                    | 结果                                                                   |
| ---------------------- | -------------------------------------------------------------------- |
| `hongguoduanju.com/`   | 200，192 KB，SSR 直出剧卡片                                                 |
| `/category/real-drama` | 200，276 KB，24 条/页，`pagination{total:800,pageSize:24,totalPages:34}`  |
| `/category/*?page=2`   | **翻页有效**，与第 1 页交集 0                                                  |
| `/player/{series_id}`  | 200，197 KB，内嵌完整剧级 + 分集 + **评论首屏**                                    |
| `/search/{kw}`         | 200，37 KB，**body 为空壳，`searchList` 已不存在**                             |
| `/robots.txt`          | `Allow: /`；仅禁 `/player/*/*`、`/series/`、`/query/` 和带特定参数的 `/category` |
| `sitemap.xml`          | 301 → 三个子 sitemap                                                    |

### 1.1 sitemap 就是「全部剧 ID 清单」，而且是官方给的

- `seo-important.xml`：4,000 条 `/detail?series_id=`
- `seo-static.xml`：223 条（分类页 + 静态页）
- `sitemap/hongguoduanju/index1.xml … index29.xml`：单个分片 **42,321** 条 `/player/{sid}`

→ 全站可枚举 URL 约 **29 × 4.2 万 ≈ 123 万部剧**。这是「全部剧」清单的合规入口，一个请求拿 4 万 ID，不需要签名、不需要设备指纹。

## 2. 三类数据 × 可行性判定

### 2.1 全部剧的列表

| 路径                | 覆盖量                                | 请求成本                   | 判定      |
| ----------------- | ---------------------------------- | ---------------------- | ------- |
| sitemap（29 分片）    | ~123 万 ID                          | 29 请求                  | ✅ 清单可全量 |
| 分类页 `?page=1..34` | 4 类 × 800 = 3,264（SEO 上限，实际在架远多于此） | 136 请求                 | ✅ 但只是样本 |
| 榜单 cell 翻页        | 每榜 TOP 数百                          | 数十请求                   | ✅       |
| 逐剧抓元数据            | 123 万 × 1 请求                       | **≈120 万请求 / ≈240 GB** | ❌ 见下    |

**「全部剧数据」的真实成本**：单页 197 KB，123 万页 = 约 240 GB 流量；即使 10 并发、单请求 0.8 s，也要 **27 小时不间断**，且必然触发频控。串行按 260 ms 节流算是 87 小时。

→ **结论：清单可以全量，元数据不能全量。** 必须改成「分层全量」：

- **L1 核心层**：榜单 + 4 个分类页 ≈ 3,000 部，10 分钟内跑完，覆盖真正的头部与在架主力
- **L2 增量层**：每日只抓 sitemap 中新增/变化的 ID + 分类首页新剧（约每天 1,500–3,000 部新剧上线）
- **L3 长尾层**：按需回溯，不做定期全量

### 2.2 单个剧的详细数据 —— 可行性最高

一次 `/player/{sid}` 请求即可拿到 20+ 字段：剧名、简介、标签、封面、总集数、上架/完结状态、付费类型、可看集数、收藏数、单集点赞数、评论总数、全部 `vid`、演员表。**免签、robots 允许、不需要 App**。

需要 App 签名才能补的只有两类：

- 播放直链（`main_url`，有时效性，且被 `spade` CENC 加密）
- 更细的运营字段（投流标记、分账相关、精准完播率等，App 侧才有）

### 2.3 单个剧的用户评论 —— 部分可行

| 目标                | 通道                                                     | 实测/推断                                                                                 | 判定   |
| ----------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------- | ---- |
| 首屏 15 条 + 总评论数    | 官网 SSR                                                 | ✅ 已验证                                                                                 | 高可行  |
| 全量评论（上限 1.8 万条/剧） | App comment 只读列表（`series_id`/`vid` + `offset`/`count`） | 同类项目 `mcp-server-fanqie` 的 `get_comments` 走「官方 commentapi 只读列表」，参数 `count` / `offset` | 中低可行 |
| 评论楼中楼 / 点赞排序      | App comment 子接口                                        | 未验证                                                                                   | 低    |
| 评论用户画像            | 无公开接口                                                  | —                                                                                     | ❌    |

**成本算式**：头部剧 18,388 条，按 20 条/页 = **920 请求/剧**。头部 100 部 = 9.2 万请求。这不是「爬一下」，这是「拿一台机器专职跑」的体量，且每一步都要过六头签名校验。

→ **建议：评论只做「首屏 + 总量」**，全量评论仅在明确研究目标下对 ≤50 部剧做一次性采样。

## 3. 技术路线（分档，按合规风险从低到高）

### 档位 A · 纯官网 SSR（推荐落地）

```
sitemap/index1..29.xml  →  123 万 series_id 清单（去重落库）
        ↓
/category/{4类}?page=1..34  →  基准在架样本 3,264 部 + 榜单校正
        ↓
/player/{sid}  →  剧级 20+ 字段 + vid_list + 评论 15 条 + 社交数
        ↓
增量：每日 diff sitemap + 分类首 3 页 + 榜单 TOP30
```

- 语言：Python（httpx + selectolax/lxml）或 Node（零依赖，照抄 hongguo-web 的 `pickJsonString` / `matchBracket` 平衡扫描逻辑）
- 解析要点：SSR 数据在 `<script>` 内联 JSON，含 `\u002F` `\u0026` 转义，必须按字符串感知的括号平衡扫描，不能用正则抠数组
- 并发：单域名 2–4 并发，全局 ≥300 ms 间隔，随机抖动 ±30%
- 缓存：剧级 TTL 24 h，`vid_list` TTL 6 h，评论 TTL 1 h
- 存储：SQLite（单机）或 Postgres；三张表 `series` / `episode` / `comment`，评论表**不落 `user_avatar`、`user_name` 做哈希化**

### 档位 B · 官网 + 轻量 App 接口（补字段）

只对档位 A 拿不到的字段调用 App 接口，且**只调用免签的两个**（`landpage`、`cell/change`）。签名接口（搜索、批量详情、播放直链）建议仅在「自用播放器」场景使用——这与 hongguo-web 的原始用途一致。

### 档位 C · 完整 App 签名链路（不建议用于数据采集）

需要复刻 `x-gorgon/x-khronos/x-ladon/x-argus/x-helios/x-medusa` 六头算法（约 630 行、含 SM3 + 自研 AesV3 变体 + 手写 protobuf），并且要处理 `_rticket` 抖动（服务端对 branch==1 返回 110001，需最多 32 次重签）。

**技术上能跑通，但这是本方案风险最高的一档**：签名是平台明确的反爬技术措施，规模化使用即从「抓公开数据」跨到「规避技术保护措施」，法律定性会变（见第 5 节）。除此之外，签名算法随版本升级会失效（`version_code` 已在 71332 → 72232 之间变过一次），维护成本是长期负担。

## 4. 反爬与风控：实际会遇到什么

| 层级     | 表现                                             | 触发条件             | 合规应对                      |
| ------ | ---------------------------------------------- | ---------------- | ------------------------- |
| HTTP   | 429 / 5xx                                      | 单 IP QPS 过高      | 降并发、指数退避 `2^n+1` 秒        |
| 业务码    | `110001 / 110002 / 110003`                     | 签名 branch 不匹配、频控 | 重签 + 退避（服务端明确告知，非静默封禁）    |
| 业务码    | `401 / 403 / 8 / 1001` 或含 `token/登录` 字样        | 登录态失效            | 读类接口一般不需要；不要为此引入账号        |
| 验证码    | 返回 verify/captcha 页                            | 行为异常、设备指纹异常      | 停止该 IP，不做验证码破解            |
| 设备指纹   | `device_id/cdid/iid` 与 TLS 指纹（Cronet/TTNet）不匹配 | 高频、UA 与设备参数矛盾    | **不要伪造设备池做轮换**——这是典型的对抗升级 |
| 内容侧    | 搜索 SSR 改版、`vid_list` 字段更名、评论数组结构改动             | 平台发版             | 解析器要「字段缺失即告警」，不能静默写空      |
| robots | `/player/*/*` 禁止                               | 抓到单集页            | 只抓 `/player/{sid}`，不碰单集页  |

**明确不做的事**（不是能力问题，是定性问题）：代理 IP 池轮换、设备身份池伪造、验证码打码、签名算法商品化分发。做到这一步，方案性质就从「数据研究」变成「对抗平台风控」，无论技术上多可行都不建议。

## 5. 合规与稳定性风险

### 5.1 合规（这是真正的天花板，不是技术）

| 风险点     | 具体说明                                                                                                                                           | 建议                                 |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 用户协议    | 字节系产品用户协议普遍禁止「使用自动化程序抓取」，robots 允许 ≠ ToS 允许。robots 只是「不禁止你读」，不构成授权                                                                             | 采集前把使用场景限定为**内部研究/选题分析**，不对外提供数据服务 |
| 技术措施    | `x-argus` 等六头签名、`spade` CENC 加密属于明确的技术保护措施。绕过它获取数据，可能触及《刑法》285 条「非法获取计算机信息系统数据」的构成要件（司法实践中「突破技术措施 + 获取非公开数据」是核心争点）。官网 SSR 不涉及此问题，因为数据本就渲染给所有访客 | **优先走 SSR 档位**；签名链路仅在自用播放场景        |
| 个人信息    | 评论含 `user_name`、`user_avatar`、`create_time`，属可识别信息。规模化收集存储违反《个人信息保护法》最小必要原则                                                                    | 只存评论正文 + 点赞数 + 时间戳；用户名哈希化，不存头像 URL |
| 著作权     | 剧名/简介/封面/视频均为平台或制作方资产。元数据用于分析属合理使用范畴，**转载视频/封面成规模即侵权**                                                                                         | 不下载、不再分发视频；封面做缩略缓存且不公开             |
| 反不正当竞争  | 若产出的数据产品与红果形成竞争关系，第 12 条「妨碍、破坏其他经营者合法提供的网络产品运行」可适用                                                                                             | 不对外售卖数据、不做竞品替代品                    |
| 数据出境/留存 | 单机自用风险最低                                                                                                                                       | 本地 SQLite + 定期清理原始 HTML            |

### 5.2 稳定性

- **接口漂移已被实测证实**：官网搜索 SSR 在一个版本周期内失效。任何解析器都要按「宁可少抓，不可错抓」设计——字段缺失写 NULL 并告警，不要 fallback 到猜测值。
- **sitemap 是唯一稳定的全量入口**，但它的分片数会变（当前 29 个），要动态读 `index.xml` 而不是硬编码。
- **`series_id` 是雪花 ID 单调递增**（实测 7586… → 7699…），这一点可作增量辅助：记录 daily max id，次日从该点往后探测。但探测到未上架 ID 会产生无效请求，需配合分类页交叉验证，不建议单靠它。
- **播放直链有时效**，`spade` 每集单独一套，缓存 100 条左右即可，不做长期落库。

## 6. 可行性总评

| 目标                  | 技术可行性            | 工程成本                        | 合规风险     | 结论                       |
| ------------------- | ---------------- | --------------------------- | -------- | ------------------------ |
| 全部剧的**清单**          | 高（sitemap 29 请求） | 极低                          | 低        | ✅ 直接做                    |
| 全部剧的**元数据**（123 万部） | 中（可跑通）           | 极高（240 GB / 120 万请求 / 3 天+） | 高        | ❌ 改为分层：核心 3,000 部 + 每日增量 |
| 单剧**详细数据**          | 高（1 请求 20+ 字段）   | 低                           | 低        | ✅ 主路径                    |
| 单剧**评论首屏 + 总量**     | 高（含在详情页里）        | 零额外成本                       | 中（个人信息）  | ✅ 脱敏后可用                  |
| 单剧**全量评论**          | 中低（需签名，920 请求/剧） | 极高                          | 高        | ⚠️ 仅限 ≤50 部采样            |
| 单剧**播放直链**          | 高（签名 + 解密）       | 中                           | 很高（技术措施） | ❌ 数据项目不做                 |

**一句话结论**：把「全部剧」理解成「全部剧的清单 + 核心样本的完整明细 + 头部剧的评论样本」，这个方案今天就能落地；理解成「123 万部剧 × 全字段 × 全评论」，技术上要三个月，法律上不建议。

## 7. 实施步骤

### P0 · 合规定档（0.5 天，先做）

明确三件事并落纸：数据用途（内部选题分析 / 不对外服务）、留存范围（元数据 + 脱敏评论正文）、是否触碰签名接口（建议：不碰）。**没定这一档不要写代码。**

### P1 · 清单层（0.5 天）

1. 拉 `sitemap/hongguoduanju/index.xml`，动态枚举分片
2. 并行拉 29 个分片，正则抽 `series_id`，落 `series(id, first_seen, last_seen)`
3. 建每日 diff：新增 ID 数、消失 ID 数（下架监测）

### P2 · 详情层（2 天）

1. `/player/{sid}` 抓取器：UA 桌面 Chrome、Referer 站内、并发 2、间隔 300 ms
2. 解析器：字符串感知的括号平衡扫描 → 定位 `series_episode_info` / `vid_list` / `episodeSocialInfo`
3. 字段映射 20+ 项落 `series_detail` 表，字段缺失写 NULL + 告警
4. 首轮跑 3,000 部核心样本（分类 4×34 页 + 榜单去重），验证成功率 ≥98%、解析失败率 <0.5%

### P3 · 评论层（1 天）

1. 从 P2 结果里取 `reviews` 15 条 + `total_count`
2. 用户名 SHA-256 截断哈希、丢弃 `user_avatar`
3. 建 `comment(series_id, content, digg, ts, user_hash)`，按剧聚合统计（评论量、平均赞、时间分布）

### P4 · 增量调度（1 天）

每日 06:00：sitemap diff → 新增剧详情 → 分类前 3 页 → 榜单 TOP30 → 更新社交数（收藏/点赞/评论总量）。全流程 ≤30 分钟、≤5,000 请求。

### P5 · 观测与止损（0.5 天）

- 指标：成功率、解析失败率、429/110001 计数、单 IP 请求速率
- 熔断：连续 20 次非 200 或 1 小时内 3 次风控码 → 自动停机 6 小时
- 字段漂移告警：任一核心字段连续 50 条为空 → 立刻停抓并人工核对

### P6 ·（可选，需法务签字）签名字段补齐

仅在需要播放直链或 App 独有字段时启动，且复用 hongguo-web 的 `pure-sign.js` 自用，不做规模化采集。
