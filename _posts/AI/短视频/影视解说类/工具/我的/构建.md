### 断点续跑与数据安全

几个刻意的实现细节，出问题时能救命：

- **merge 先写临时文件再原子改名**。基线就在 `dist/` 里时，直接写会把基线截断成空文件再读，读到空数据 —— 这个坑真实踩过。
- **空批次不生成新补丁**。`bootstrap` 收尾补 JSON 格式时用空批次重跑 merge，否则会把当天的 delta 覆盖成空文件。
- **全量缩水 10% 直接失败**。基线下载失败、batch 为空、sitemap 抽风都表现为条目骤减，宁可失败也不发残缺数据；旧产物不会被覆盖。
- **`fetch` 靠 batch 里已有的 id 续跑**，被 Ctrl-C 杀掉直接重跑就接上。

## 增量原理

sitemap 里每个 URL 都带独立 `<lastmod>`，精确到秒。抓取时把它原样写进条目的 `src_mtime`，于是第二天的判定退化成一次比对：

```
sitemap.lastmod !== catalog.src_mtime  →  这剧变了，重抓
sitemap 里有、catalog 里没有            →  新剧，抓
sitemap 里没有、catalog 里有            →  下架，标记删除
其余                                    →  跳过
```

好处是**不依赖任何外部状态文件**：状态就在索引里，索引丢了大不了全量重抓一次，不会出现「状态文件丢了导致永久漏抓」。

抓取时若遇到 `404/410`，说明 sitemap 还挂着但剧已下架，直接记为删除，不浪费重试。

## 自动发布

`.github/workflows/daily.yml`，每天北京时间 03:00（UTC 19:00）执行：

1. 从上次 Release 下载 `catalog.ndjson.gz` 当基线
2. `plan` 拉 sitemap，算出本次要抓的 ID
3. `fetch` 抓详情（并发 12，带 4 小时运行时限保护）
4. `merge` 合并出全量 + 增量 + 清单
5. `verify` 校验 SHA256 / 条数 / 唯一性 / 排序
6. 发布 Release，tag 为 `full-YYYYMMDD`

几个刻意的设计：

- **`concurrency` 串行**：同一天多个 run 并发会互相删 Release，产物 404。
- **`merge` 用 `always()`**：单个分片抓取失败不该阻断整体发布，残缺部分次日补。
- **全量缩水安全阀**：新全量若比基线少 10% 以上直接失败退出。基线下载失败、batch 为空、sitemap 抽风都表现为条目骤减，宁可失败也不发残缺数据。
- **抓取单点失败不算失败**：记录到 `batch.failed.ndjson`，下次重跑自动重试。

首次上线前需要在仓库 Settings → Actions → General 里把 **Workflow permissions** 设为 `Read and write permissions`，否则发不了 Release。
