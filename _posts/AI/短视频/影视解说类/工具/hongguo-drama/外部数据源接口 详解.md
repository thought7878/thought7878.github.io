## 1. 先理解三条主干链路

不理解链路，单个接口的「调用关系」看了也记不住。全项目 44 个接口，最终只服务三件事。

### 1.1 链路一：打开一部剧（解析 → 分集）

```
用户粘贴分享链接 / 点搜索结果
        │
        ▼
  resolveSeriesId (B4)  ──── 本地正则优先，解析不出才出网
        │  得到 series_id（纯数字 或 custom:uuid:id）
        ▼
  fetchEpisodeList  ──── 按前缀分流
        │
        ├── custom: ──▶ custom-source.fetchEpisodeList (C9)
        ├── hema:   ──▶ hema.fetchEpisodeList (C3)
        ├── xifan:  ──▶ xifan.fetchEpisodeList (C6)
        └── 纯数字 ──▶ fetchEpisodeListFresh  ← 【编排器，60s 缓存】
                          │
                          ├─① fetchEpisodeListFromWeb (B2) 官网，无签名，首选
                          │     └─ 内部并发 /player/{sid} 与 /detail?series_id=
                          │
                          └─② 失败则 apiCall → multi_video_detail (A10) App 回退
```

**要点**：`fetchEpisodeListFresh` 本身不是接口，是编排器。真正发请求的是 B2 和 A10。改代码时如果只看到 `fetchEpisodeListFresh` 就以为「这里没网络请求」，会漏掉两条出网路径。

### 1.2 链路二：播放与下载（取址 → 取流）

取址（拿到一个 mp4/m3u8 的 URL）和取流（把这个 URL 的内容读下来）是两个完全不同的阶段，分别由两组接口负责。

```
  fetchPlayUrlSingle (入口)  ──── 按前缀分流 + 30s 缓存
        │
        ├── custom/hema/xifan ──▶ 各自的 fetchPlayUrlSingle (C3/C6/C9)
        │
        └── 纯数字 ──▶ 按清晰度分两条截然不同的路：
              │
              ├── quality === 'auto'  ──▶ fetchPlayUrlFresh（三级降级）
              │       ├─① fetchPlayUrlFromWeb (B3)   官网明文 MP4
              │       ├─② fetchAppPlayUrl (A8)       App 签名接口
              │       └─③ apiCall /multi_video_model/preload (A11) 旧接口
              │
              └── quality !== 'auto' ──▶ fetchAppPlayUrl (A8) 直接一步到位
                                          ✗ 官网通道被主动跳过
        │
        ▼
  得到 { url, spadeA, codec, source }
        │
        ▼
  requestMedia (E1) ── 取流；spadeA 非空则后续 CENC-AES-CTR 解密
        │
        ├── 若 url 是 m3u8 ──▶ remuxHls (E2) ── 落盘分片 + FFmpeg 封装
        └── 若 url 是 mp4   ──▶ 直接流式写入
```

**要点**：这是全项目最关键的一个分叉。`quality` 的值直接决定了走不走官网通道，也决定了要不要解密。细节见 9.5 节。

### 1.3 链路三：发现（搜索与浏览）

```
搜索框输入
   │
   ▼
search-series (IPC) ──▶ searchAtSource ──▶ searchAtSourcePage  ← 分页状态机
   │
   │  第 1 页（可多源竞争）：
   │    ├─ App 搜索 (A3)      若开启且无冷却，且结果标题能匹配 → 采用
   │    ├─ 官网搜索 (B7)      主通道；4xx 时降级 DOM 嗅探
   │    └─ 上新补搜 (A6)      前两者标题匹配不足时补充
   │
   │  第 2 页起（必须固定通道）：
   │    ├─ channel='app' → A3（带 cursor 游标）
   │    └─ channel='web' → B7（带页码）
   │
   └─ 切换来源时：hema (C2) / xifan (C5) / custom (C8)

分类页 / 榜单页点击
   │
   ▼
browse-list (IPC) ── 按来源路由
   ├─ 红果 + 分类 → catalog.browseList (B5)  或 App 目录 (A5)
   ├─ 红果 + 榜单 → catalog.browseList (B6)  或 App 榜单 (A5)

   ├─ xifan       → C4
   └─ custom      → C7
```

**要点**：搜索是**有状态**的 —— 第 2 页必须沿用第 1 页选中的 channel 和 cursor，中途换源会导致重复或漏结果。代码里那句「第 2 页起必须固定第一页选中的通道」就是这个意思。

## 2. A 组详解：红果官方 App API（`*.fqnovel.com`）

这组是「番茄小说 App」的内部接口，需要设备指纹和签名。它们的共同特点是：**能力强（能拿到官网拿不到的高清片源）、但脆弱（签名、设备、版本任何一环漂移就挂）**。

### A1 · `requestJson` — App 系通用传输层

**功能定位**  
一个被所有 App 系接口复用的 HTTP 客户端。它**不关心业务语义**，只负责四件事：拦住不该去的地址、发起请求、把响应解析成 JSON、把错误归一成可判断的错误码。所有「App 接口怎么发请求」的规则都收敛在这一个函数里。

**典型场景**  
不直接对应用户操作，而是隐身在每一次 App 接口调用背后：搜关键词、翻 App 榜单、读观看记录、注册设备、取播放地址，最终都经过它。

**输入参数**

| 参数                                   | 含义与作用                                                                                                                                                                  | 传错的后果                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `url`                                | 完整目标地址。会做四重校验：必须是 `https:`、端口空或 443、禁止 `user:pass@`、域名必须在 `fqnovel.com` / `snssdk.com` 白名单内                                                                            | 命中任一 → `SECURITY_BLOCKED`，请求根本不发出                     |
| `options.method`                     | 决定重定向策略。**POST 遇 3xx 一律拒绝**，因为重定向会把已签名的 body 原样重发到新地址，等于把签名送给陌生服务器                                                                                                     | POST 写了错的路径，得到的是 `SECURITY_BLOCKED` 而不是 404，容易误判成网络问题 |
| `options.headers`                    | 签名头、设备头由上层拼好传进来                                                                                                                                                        | —                                                     |
| `options.data`                       | POST body                                                                                                                                                              | —                                                     |
| `options.preserveLargeIntegerFields` | **这是最容易被忽略但最关键的参数**。番茄的 `vid` 是 19 位数字，超过 JS 安全整数上限（2^53）。直接 `JSON.parse` 会变成 `...000` 结尾的近似值，拿这个近似 vid 去请求播放接口必然失败，而且错误信息完全看不出是精度问题。此参数在解析前先给指定字段的 ≥16 位整数加引号，保住字符串形态 | 漏传 → 播放/下载随机失败，且极难定位                                  |
| `deadline`                           | 绝对毫秒时间戳，不是「多久超时」而是「最晚几点必须结束」。这样多层嵌套调用可以共享同一个预算，不会层层叠加                                                                                                                  | 传相对值 → 嵌套调用时超时失控                                      |
| `signal`                             | AbortSignal，供上层取消（用户切集、关闭窗口）                                                                                                                                           | —                                                     |

**返回结果用途**  
解析后的 JSON object。上层拿它做业务判断：A3 读 `data.tab_data`，A5 读 `data.cell`，A12 读设备号。

**调用关系**

- 上游：A3、A5、A6、A7、A12 全部通过它发请求
- 下游：axios
- 同层：`fetchSiteHtml`（B1）是它的官网对应物，但走 HTML 而非 JSON

**易混点**  
和 `apiCall`（A9）容易混。区别是：`requestJson` **无签名但强安全**（域名白名单、禁 POST 重定向）；`apiCall` **有设备指纹但弱安全**（只拼固定 query，无签名头、无域名白名单、有 3 次重试）。

### A2 · `signedSearchRequest` — 搜索请求签名器

**功能定位**  
**纯构造函数，不发请求**。输入搜索条件，输出一个「已签好名」的 URL 和一整套伪造 App 身份的请求头。它解决的是「如何在服务端看来像一个真实的番茄 App 客户端」。

**典型场景**  
用户开启「App 搜索」开关后在搜索框输入剧名。主进程先调它构造请求，再交给 A1 发出。

**输入参数**

| 参数         | 含义与作用                                                                                                    | 传错的后果         |
| ---------- | -------------------------------------------------------------------------------------------------------- | ------------- |
| `keyword`  | 搜索词。会被截断到 80 字符 —— 服务端对超长 query 直接丢弃，与其报错不如静默截断                                                          | —             |
| `page`     | 页码。**必须 1–50 的整数**，因为服务端用 `offset = (page-1)*20` 计算偏移，非法值会让 `offset` 变负数或溢出                              | 抛 `APP_INPUT` |
| `cursor`   | 翻页游标，含 `search_id`、`passback`、`next_offset`。**这是服务端会话态的延续凭证**，不带就相当于每次都从零开始搜，第 2 页会返回第 1 页的结果            | 翻页重复或结果错乱     |
| `identity` | `{ device_id, iid, cdid }` 三件套。`device_id`/`iid` 必须是纯数字且含非零位，`cdid` 必须是标准 UUID。这些值来自 A12 的设备注册，**不能随便造** | 抛 `APP_INPUT` |

**返回结果用途**  
`{ url, headers }`。URL 给 A1 发，headers 里的 `x-gorgon`/`x-ladon`/`x-argus`/`x-helios`/`x-medusa` 五件套是服务端鉴权的核心。

**调用关系**

- 上游：`hongguo-app-search.searchApp`（A3）
- 下游：无（纯计算）
- 同层：A4、A7 结构完全一致，只是主机、设备版本号、body 处理不同

**易混点**  
三个 `signed*Request` 长得几乎一样，差异全在细节：

|             | A2 搜索            | A4 目录            | A7 账号            |
| ----------- | ---------------- | ---------------- | ---------------- |
| 主机          | `sinfonlinea`    | `sinfonlineb`    | `sinfonlinea`    |
| 设备版本        | 7.2.2.32 / 72232 | 7.3.5.32 / 73532 | 7.2.2.32 / 72232 |
| 设备来源        | A12 注册           | **进程内随机生成，不落盘**  | A12 注册           |
| body        | 无                | 可选               | 无                |
| `x-ss-stub` | 无                | `MD5(body)`      | 无                |

改签名逻辑时**必须三个一起看**，只改一个会导致另外两条链路静默失败。

**最关键的实现细节：签名分支收敛**  
签名算法有 3 个分支（由 `branchOf` 决定走哪个），但服务端只接受分支 0。所以代码用 `_rticket`（毫秒时间戳）从基准值递增，最多试 **128 次**，直到 `branchOf(...) === 0` 才返回。128 次仍不满足就抛错。

这意味着：**签名请求是 CPU 密集型操作**，每次都伴随多轮 SM3 + MD5。高频调用（如快速翻页）会有可感知的延迟。这也是 A5 要加 120s 会话缓存的原因之一。

### A3 · `searchApp` — 红果 App 搜索

**功能定位**  
执行 App 搜索的完整流程：确保设备已注册 → 构造签名请求 → 发请求 → 解析响应 → 归一化成和官网搜索一致的 `results` 结构。它是「App 搜索」这个能力的门面。

**典型场景**

1. 用户在设置里打开「App 搜索优先」，搜索剧名 → 第一页优先走它
2. 官网搜索返回 4xx（被风控）→ 作为备用通道
3. 用户在第 1 页走了 App 通道，点「加载更多」→ 第 2 页必须继续走它

**输入参数**

| 参数         | 含义与作用                                                       | 传错的后果               |
| ---------- | ----------------------------------------------------------- | ------------------- |
| `keyword`  | 搜索词，先过 `cleanTitle` 归一（NFKC + 去多余空白），再限 1–80 字              | 过短/过长 → `APP_INPUT` |
| `page`     | 1–50                                                        | 越界 → `APP_INPUT`    |
| `cursor`   | **第 2 页起必填**。缺失 → `APP_CURSOR`。这是因为服务端分页靠游标而非页码偏移，没有游标就无法定位 | 翻页失败                |
| `deadline` | 默认 `now + 8000`。8s 是刻意压得比较紧的值 —— App 接口只是「优先尝试」，卡住就应尽快让位给官网 | —                   |
| `request`  | 注入点，测试时替换真实请求                                               | —                   |

**返回结果用途**  
`results[]` 直接作为搜索结果列表渲染；`cursor` 被 `main.js` 存进分页状态，下次翻页原样回传；`hasMore` 决定「加载更多」按钮是否可点。

**调用关系**

- 上游：`main.searchAtSourcePage`（第 1 页竞争 / 第 2 页固定通道）
- 下游：A12（设备注册）→ A2（签名）→ A1（发请求）
- 并列：B7（官网搜索）、A6（上新补搜）、C2/C5/C8（第三方搜索）

**易混点**  
和 B7 的区别不只是「源不同」：

|        | A3 App 搜索    | B7 官网搜索        |
| ------ | ------------ | -------------- |
| 是否需要设备 | 需要（A12）      | 不需要            |
| 是否需要签名 | 五件套          | 无              |
| 翻页方式   | 游标（`cursor`） | 页码（`page`）     |
| 失败恢复   | 冷却 2 分钟后不再尝试 | 4xx 时降级 DOM 嗅探 |

**设计意图**：App 搜索能搜到官网没上架的剧（尤其新剧），但依赖签名。所以主流程是「先试 App，标题能匹配就用；匹配不上或失败就回退官网」，并用 `appSearchCooldownUntil` 做 2 分钟冷却，防止签名挂了之后每次搜索都白等 8 秒。

### A6 · `listNewReleases` / `searchNewReleasesDetailed` — 近 7 天上新补搜

**功能定位**  
解决一个具体痛点：**官网搜索对新上架的剧索引滞后**。用户搜一部昨天刚上的剧，官网搜不到，但 App 的上新列表里有。这个接口把「最近 7 天上架」的目录拉下来，在本地做标题匹配。

**三层导出，别调错层**

| 导出                                             | 返回                              | 谁在用                                                          |
| ---------------------------------------------- | ------------------------------- | ------------------------------------------------------------ |
| `listNewReleases(options)`                     | `{ items[], cached, partial }`  | 底层抓取，`searchNewReleases` 的上游                                 |
| `searchNewReleases(keyword, opts)`             | 只返回匹配到的 `results[]`             | 轻量封装                                                         |
| **`searchNewReleasesDetailed(keyword, opts)`** | `{ results[], partial, error }` | **`main.js` 实际调用的就是这个**（因为它需要 `partial` 来区分「全部失败」和「只拿到部分分类」） |


改这个接口时如果只改 `listNewReleases` 而忘了上层封装的字段透传，会出现「明明抓到了但搜索没结果」。

**典型场景**
只在搜索链路里被调用，且需要三个前置条件同时满足：
1. 是第 1 页（翻页不做补搜）
2. `fuzzy !== false`（用户没关模糊搜索）
3. 归一化后的搜索词 ≥2 字（单字或纯标点在上新列表里匹配没有意义）

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `pages` | 默认 2，上限 8。每页 50 条，2 页 = 100 条够覆盖 7 天 | 太大 → 拖慢搜索 |
| `deadline` | 默认 `now + 8000`，会被上层 12s 官方预算进一步收紧 | — |
| `useCache` | 默认 true，60s TTL | — |

**返回结果用途**
`items[]` 被 `mergeNewReleases()` 合并进主搜索结果，并打上 `new_release: true` 标记 —— 前端据此显示「新剧」角标。若该剧是今天上架，另有 `released_today: true`。

**调用关系**
- 上游：`main.searchNewReleasesForSearch` → `searchAtSourcePage` 第 1 页末尾
- 下游：A4 → A1
- 依赖：与 A5 共用同一套签名和设备身份

**这是全项目「防御性设计」最密集的接口，值得单独说**
1. **双分类并行**：真人剧（`short_play`）和 AI 剧（`ai_series`）用 `Promise.allSettled` 并行拉，任一成功即可用，标记 `partial: true`。这样单个分类挂掉不影响整体
|  |  |  |
| --- | --- | --- |
2. **游标防死循环**：`next === null || next <= offset` 立即 break。没有这行，服务端返回相同的 `next_offset` 就会无限请求
3. **只缓存完整非空结果**：空结果不缓存，避免一次失败把后续 60s 的搜索全锁死
4. **30s 全局冷却** + **剩余预算 <900ms 直接跳过**：防止上新补搜拖垮整个搜索响应
5. **`normalized.length < 2` 直接返回**：连请求都不发

**易混点**
和 A5 走同一组端点（`category/landpage/v`），但目的完全不同：A5 是「浏览」，A6 是「搜索的补给」。A6 不返回 `genres`，也不支持 `page` 参数（内部自己翻 2 页），所以**不能替代 A5**。

**典型场景**
用户扫码登录后，点「同步观看记录」→ 把 App 里的追剧进度拉下来，和本地记录合并。

### A8 · `fetchAppPlayUrl` — App 播放地址

**功能定位**
从 App 接口拿**带加密信息的播放地址**。返回的不只是 URL，还有 `spade_a`（内容密钥种子）和 `codec`。这是高清片源的唯一来源。

**典型场景**
1. 用户选了 1080P 下载 → 直接走它（唯一途径）
2. 自动清晰度下官网通道失败 → 作为第二级
3. 自动清晰度下用户中途手动切清晰度 → 重新走它

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `vid` | 分集 ID，`^\d{1,30}$`。**注意是字符串不是数字** —— 19 位会丢精度 | 非法 → 「分集编号无效」 |
| `options.quality` | `auto`/`720p`/`1080p` 等，经 `normalizeDownloadQuality` 归一 | — |
| `options.allowLowerQuality` | 允许降级。默认 false 时，找不到目标清晰度就**报错而不是给个差的** —— 这是「用户明确选了 1080P，就不要偷偷给 720P」的产品决策 | — |

**返回结果用途**
```
{ url, contentKey, codec, source:'app', vid, quality,
  variants: [{ url, contentKey, codec, width, height, ... }] }
```
- `url` → 交给 E1 取流
- `contentKey` → 若非空，取流后必须解密（CENC-AES-CTR）
- `codec` → 前端据此判断是否需要转码（HEVC 在不支持的设备上会黑屏有声）
- `variants` → 兜底候选。当前 `url` 挂了可以换下一个

**调用关系**
- 上游：`fetchPlayUrlFresh` 第二级、`fetchPlayUrlSingle`（非 auto 时唯一通道）
- 下游：A12（设备）→ 签名 → A1
- 并列：B3（官网）、A11（旧接口）

**参数含义里最重要的一个：`quality` 在这里是「过滤器」不是「提示」**
`auto` 时取最高像素档的全部编码；指定清晰度时用 `meetsDownloadQuality` 硬过滤，`allowLowerQuality=false` 则过滤后为空直接抛 `QUALITY_UNAVAILABLE`。这解释了为什么「选了 1080P 却提示没有片源」—— 不是没有片源，是没有**尺寸可确认且满足 1080P 的 H.264/HEVC** 片源。

**异常处理的两个独特点**
1. **唯一重试**：只在首轮 `EMPTY_RESPONSE` 且剩余 ≥8s 时，先调 A12 续期设备身份再重发。因为空响应的常见原因就是设备鉴权失效
2. **多级降级不可逆**：`video_list` 内联优先 → 失败才走 `fallback_api`。反过来不行，因为 `fallback_api` 返回的数据结构不同且没有 `key_seed`

### A9 · `apiCall` — 无签名 App 调用

**功能定位**
一个**更原始**的 App 接口调用器。只拼固定设备指纹 query，不打签名头。用于两个「服务端不强校验签名」的老端点。

**典型场景**
仅在 A8 和 B3 都失败后触发，作为最后的取址手段（A11），以及分集回退（A10）。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `apiPath` | 目标路径，无白名单 | — |
| `body` | POST body | — |
| `retries` | 默认 3。**空响应不重试**（见下） | — |
| `timeout` | 默认 25s | — |
| `deadline` | 绝对时间戳，0 = 不限 | — |

**返回结果用途**
解析后的 JSON。A10 读 `data[seriesId].video_data.video_list`，A11 读 `data[vid].video_model`。

**调用关系**
- 上游：A10、A11
- 下游：axios
- 同层：A1（`requestJson`）

**和 A1 的三个关键差异**

| 维度 | A1 `requestJson` | A9 `apiCall` |
|---|---|---|
| 签名 | 由调用方传入 headers | 无签名，只拼固定 query |
| 域名安全 | 白名单校验 | 无校验 |
| 重试 | 0（外层负责） | 3 次，退避 2s/4s |
| 空响应 | 抛 `EMPTY_RESPONSE` | 同样抛，但**明确不重试** |

**为什么空响应不重试** —— 代码注释写得很直白：`200 + 0 字节` 意味着网关在业务处理前就丢弃了请求，重发同样的请求只会再被丢一次，白白多等 2 秒还给出误导性的「重试中」状态。这个判断很关键：**空响应是确定性失败，不是瞬时故障**。

`err.detail = { status, logid, bytes }` 是排障的关键 —— `logid`（来自 `x-tt-logid`）可以拿去和服务端对账。

**易混点**
`apiCall` 用 `responseType: 'arraybuffer'` + 恒等 `transformResponse`，自己 `JSON.parse`。为什么不直接让 axios 解析？因为 axios 遇到 `200 + 空 body` 会解析成空字符串，无法区分「空响应」和「合法空值」。先拿原始字节，就能精确判断 `buf.length === 0`。

### A10 · App 分集接口（`multi_video_detail/preload/v1`）

> 注意：清单文档里把 A10 标成了 `fetchEpisodeListFresh`，那其实是**编排器**。A10 是编排器里的 App 分支。

**功能定位**
官网拿不到分集时的备用通道。返回完整的 `vid` 列表，让用户至少能播放和下载。

**典型场景**
1. 官网 `/player/{sid}` 和 `/detail?series_id=` 都超时或被风控
2. 该剧在官网只有试看页，分集不全
3. 用户处于「官网整体不可用」的网络环境（部分区域 DNS 污染）

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` | 剧集 ID | — |
| `deadline` | 继承自上层，**与官网通道共享同一个预算** | 超预算直接失败 |

请求体固定三段：`biz_param: DETAIL_BIZ_PARAM`、`dr_scene: "preload"`（告诉服务端这是预加载场景，返回精简结构）、`series_id`。

**返回结果用途**
```
{ series_id, series_title, cover, total,
  episodes: [{ vid, vid_index, title, series_id, series_title, cover }],
  source: 'app' }
```
按 `vid_index` 升序排好。下游拿 `vid` 去取播放地址。

**调用关系**
- 上游：`fetchEpisodeListFresh`（第 495 行 catch 之后）
- 下游：A9 → axios
- 并列：B2（官网分集）

**这个接口的价值在「fail-closed 校验」，不在数据本身**
四道校验，任何一道不过就整体失败：

1. `j.code !== 0` → 「detail API 失败」
2. **必须用请求的那个 key**，不能取 `Object.keys(d)[0]` —— 注释写着 `Never take the first key from an object: a mismatched response must fail closed.`
3. `vd.series_id` 与请求不符 → 抛
4. 任一 `video_list[i].series_id` 与请求不符 → 「备用接口返回了其他剧集的分集」

为什么要这么严？因为如果服务端返回了**另一部剧**的分集，而代码「宽容」地接受了，用户会看到 A 剧的封面配 B 剧的分集，点进去播放的还是 B 剧。这种错误极难在测试中发现，但用户一眼就看出来。

**易混点**
和 A11 都是「preload」端点，但路径不同：
- A10 `/novel/player/multi_video_detail/preload/v1` → 返回**分集列表**
- A11 `/novel/player/multi_video_model/preload/v1` → 返回**单集播放模型**

| `vid` | 分集 ID | — |

调用时固定 `retries = 1`、`timeout = 6000` —— 已经是最后一级了，不值得再等 25 秒。

**返回结果用途**
`{ url, spadeA, codec, source: 'api', vid, userAgent }`。注意 `source` 是 `'api'` 而不是 `'app'`，下游据此区分。

**调用关系**
- 上游：`fetchPlayUrlFresh`（第三级）
- 下游：A9
- 并列：B3、A8

**选流逻辑是这个接口最值得看的部分**
`video_list` 里可能有十几个候选，用三级比较器挑：

1. **编码优先**：h264/avc → 0，h265/hevc → 1，其他 → 2（其他直接丢弃，因为无法播放）
2. **短边分辨率**（次）
3. **总像素**（再次）
4. **码率**（最后）

为什么短边优先于总像素？因为竖屏短剧的价值在高度，一个 `1080×1920` 比 `1280×720` 好得多，但按总像素算前者只是后者的 2 倍多，按短边算是 1.5 倍 —— 这个排序更符合短剧的实际观感。

**易混点**
`spadeA` 字段是 A11 独有的（A8 叫 `contentKey`）。两者语义相同（内容密钥种子），但来源不同：A8 从 `key_seed` 派生，A11 直接读 `encrypt_info.spade_a`。解密代码因此有两个入口。

### A12 · `registerPlaybackDevice` — 匿名设备注册

**功能定位**
**整个 A 组的前置依赖**。没有合法设备号，A3/A7/A8 全部无法工作。它向字节的设备注册服务申请一套 `{ device_id, iid, cdid }`。

**典型场景**
不直接对应用户操作，但会在这些时刻触发：
1. 应用启动后第一次搜索 / 播放 / 读账号
2. A8 返回空响应（设备被标记异常）→ 续期
3. 距离上次续期超过 60s 且上层明确传入 `rejectedDevice`

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `requestJson` | 注入的传输层（生产环境 = A1）。**用注入而非直接 require，是为了测试能完全离线** | — |

请求体构造是本项目最复杂的一段（约 40 字段设备指纹 + gzip + 双层哈希 + AES），核心是让请求看起来来自一台真实的三星 SM-N9860。

**返回结果用途**
`Object.freeze({ device_id, iid, cdid })`。冻结是防止下游意外修改 —— 这三个值一旦被改，所有已签名的请求全部失效。

**调用关系**
- 上游：A3、A7、A8 内部调用 `getPlaybackDevice()`
- 下游：A1
- 同层：无

**三个缓存/退避机制，都是防雪崩的**

1. **单例 Promise**：`registration` 变量持有进行中的 Promise，并发调用共享同一个请求。100 个并发不会打 100 次注册
2. **失败后 10s 共享**：`retryAfter = now + 10000`。失败后 10 秒内所有调用直接拿同一个错误，不再重试。文案里那句「10 秒后重试」就是从这里来的
3. **60s 续期节流**：`refreshAfter`。传入 `rejectedDevice` 时最多每 60s 续期一次；续期失败自动回滚到旧 Promise（保证不会因为续期失败把可用状态也搞坏）

**易混点**
`registerPlaybackDevice`（实际发请求）和 `getPlaybackDevice`（带缓存的入口）是两个函数。业务代码**只应调后者**，直接调前者会绕过所有缓存保护。

## 3. B 组详解：红果官网（`hongguoduanju.com`）

这组是**首选通道**。它们不需要签名、不需要设备号，稳定性远高于 A 组。代价是只能拿到官网公开的内容（部分剧只有试看、部分清晰度不提供），且强依赖页面结构。

### B1 · `fetchSiteHtml` — 官网 HTML 通用抓取

**功能定位**
官网侧的 `requestJson`。最薄的一层封装：设置伪装 UA、Referer、超时，发起 GET，返回 HTML 字符串。**不做解析、不做重试、不做缓存** —— 这些都在调用方。

**典型场景**
不直接对外。B2（分集）、B3（直链）、B4（分享链接）都经过它。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `url` | 目标地址 | — |
| `timeout` | 默认 30s。但实际调用方都传得很小（1.5s / 3.5s / 4s），因为官网页面正常响应在 1 秒内 | 传太大 → 卡住用户 |
| `signal` | AbortSignal，用于对冲时取消输掉的那一方 | 不传 → 输掉的请求会继续跑，浪费流量 |
| `trustedOfficialDns` | 为 true 且同源时套 G2 护栏并强制 `adapter: 'http'`。用于 VPN Fake-IP 环境 | — |

**返回结果用途**
HTML 字符串，交给调用方用正则/状态机解析。

**调用关系**
- 上游：B2、B3、B4
- 下游：axios（可能经 G2）
- 同层：A1（App 侧对应物）

**易混点**
和 B8（`fetchPublicDetails`）看着像但不是一回事。B8 是**自带解析和缓存**的完整接口，B1 只是**搬运 HTML**。B8 甚至不用 B1，自己写了 axios 调用 —— 因为它需要特殊的 302 处理，用 B1 反而绕。

### B2 · `fetchEpisodeListFromWeb` — 官网分集列表

**功能定位**
从官网 SSR 页面里抠出完整分集列表和每个分集的 `vid`。这是打开任何一部剧的第一跳。

**典型场景**
用户粘贴分享链接 → 解析出 `series_id` → 立刻调它拿分集；或从搜索结果点进详情页。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` | 剧集 ID，`^\d{1,30}$` | 非法 → 直接抛错 |
| `deadline` | 绝对时间戳。**所有子请求的预算都从这里派生**，保证总耗时不超过上层给的预算 | — |

**返回结果用途**
```
{ series_id, series_title, cover, total, web_accessible_episodes,
  episodes: [{ vid, vid_index, title, series_id, series_title, cover, web_available }],
  source: 'web' }
```
- `episodes[].vid` → 后续取址的唯一输入
- `episodes[].web_available` → 决定播放时是否优先试官网（false 则直接走 App）
- `web_accessible_episodes` → 前端显示「官网可看 N 集」，提示用户其余集需要 App 片源

**调用关系**
- 上游：`fetchEpisodeListFresh`（第一级）
- 下游：B1（两次并发）
- 并列：A10（App 回退）
- 最终出口：IPC `hongguo-resolve`、`search-resolve`、`refresh-watch-history`、`transcode-for-playback`、`hongguo-download-batch`

**这个接口的精髓是「两路并发 + 三级对冲」，值得逐步拆开看**

**第一步：两个 URL 并发竞速**
```js
Promise.any([
  fetchSiteHtml(`/player/${id}`),
  fetchSiteHtml(`/detail?series_id=${id}`)
])
```
为什么？代码注释解释了：**部分 `/player` 页面由故障 CDN 边缘节点提供**（先挂起再断开），而同一部剧的 `/detail` 路由是健康的。串行试会白等一个超时，并发则取先成功者。

`finally { controller.abort() }` 是关键 —— 赢家返回后立刻掐断输家，避免它在后台继续占带宽。


**第二步：时间分级**
```
0ms    ──▶ 第一轮：两个 URL，1.5s 预算，可信 DNS
600ms  ──▶ 若第一轮还没返回，启动 hedge
            hedge = Promise.any([
                       race(3500, trustedDns=true),   // 可信 DNS 重试
                       race(3500, trustedDns=false)   // 普通 DNS 重试
                    ])
```
1.5s 是「健康页面早该返回了」的阈值；600ms 是「故障 CDN 通常会在这个窗口内暴露」的经验值。两路 DNS 都试，是因为**如果 DoH 端点本身被墙，只信可信 DNS 会让整部分集功能瘫痪**。

**第三步：错误合并**
最终抛出的错误是「{第一条失败原因}；重试失败：{第二条失败原因}」，而不是笼统的「加载失败」。排障时这行文案能直接区分「第一次就超时」和「重试阶段才超时」。

**解析方式**
用 `parseEpisodeListHtml` 从 `window._ROUTER_DATA` 抠 JSON。**括号配平 + 字符串转义状态机**，不是正则 —— 因为 JSON 里可能有任意嵌套和转义引号，正则必然出错。**绝不 `eval`**，即使内容来自「可信」官网。

**易混点**
和 A10 的区别不只是源。B2 返回的 `episodes` 带 `web_available` 标记，A10 返回的不带（App 分集默认可播）。下游的 `fetchPlayUrlFresh` 用这个标记决定要不要跳过官网取址。

### B3 · `fetchPlayUrlFromWeb` — 官网 MP4 直链

**功能定位**
从播放页的 `application/ld+json`（Schema.org 的 VideoObject）里取出**明文的、可直接下载的 MP4 地址**。无加密、无签名、无 `spade_a`。

**典型场景**
`quality === 'auto'` 时的第一选择。用户点播放或下载，若清晰度是自动，先试它。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `vid` | 分集 ID | — |
| `sid` | 剧集 ID，**可空**。为空时先试 `/player/_/{vid}` 让服务端自己解析 | 传错 → 校验不过 |
| `onFailure` | 回调，把每次失败原因收集起来给上层汇总 | 不传 → 最终错误信息缺少 web 这一环的细节 |

**返回结果用途**
`{ url, spadeA: null, codec: '', source: 'web', vid, userAgent, referer }` 或 `null`（全失败）。

- `url` → E1 直接取流，**不需要解密**
- `userAgent` / `referer` → 必须原样带给 E1，官网 CDN 会校验，否则 403

**调用关系**
- 上游：`fetchPlayUrlFresh`（第一级，仅 `quality === 'auto'`）
- 下游：B1（串行两个 URL）
- 并列：A8、A11

**它有一整套「宁可不给，也不给错」的校验**
七个条件全部通过才算成功：

1. `data.vid === vid` — 页面确实是这一集
2. `series_id` 纯数字且与请求一致
3. `publicVideoSeo.available === true` — 官网标记为可看
4. `itemId === vid` — ld+json 里的条目 ID 匹配
5. `VideoObject.url` 指回当前 player 页面 — 防止拿到别的剧的地址
6. `contentUrl` 经 `normalizeVideoUrl` 规范化
7. 规范化后必须过 G1（`isPublicMediaUrl`）— 防 SSRF

**`PREVIEW_ONLY` 这个错误码的用意**
若 `protectedPlayback === true`，说明官网只提供试看片段。此时**立即抛错且不再试第二个 URL** —— 因为第二个 URL 也是同一部剧，同样只会给试看。这个短路省掉一次 4 秒等待。

**易混点**
和 A8 最大的区别：**没有清晰度概念**。官网只给一个 MP4（通常是 720P 左右），无法选 1080P。这就是为什么用户选定高清时这个接口被完全跳过。

### B4 · `resolveSeriesId` — 分享链接解析

**功能定位**
把用户粘贴的任意文本（分享文案、链接、纯 ID）变成干净的 `series_id`。**核心设计原则：能在本地算出来的，绝不出网。**

**典型场景**
用户在首页的输入框粘贴一段从红果 App 复制来的分享文案，或者一个短链。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `shareUrl` | 原始文本，≤8192 字符。支持四种形态：纯数字 ID / `custom:uuid:id` / 含 URL 的任意文本 / 含 `video_series_id=` 或 `"series_id":"xxx"` 的文本 | 超长 → 「分享内容无效或过长」 |

**返回结果用途**
`string` —— 归一化后的 series_id，直接喂给 `fetchEpisodeList`。

**四层解析顺序（顺序本身就是设计）**

| 层 | 条件 | 是否出网 |
|---|---|---|
| 1 | `custom:uuid:id` 形态 | ❌ 本地正则 + `assertEnabled` 校验 |
| 2 | 纯数字 | ❌ 直接返回 |
| 3 | 文本中出现 `series_id=123` 或 `"series_id":"123"` | ❌ **先把所有 URL 从文本里剔掉再匹配** |
| 4 | 以上都不中，取文本里第一个 URL | ✅ 跟跳抓页面 |

第 3 层那个「先剔 URL 再匹配」很讲究：如果整段文本里既有 `series_id=456`（在链接参数里）又有独立写的 `series_id=123`，应该以独立写的为准 —— 因为那才是用户真正想解析的。URL 里的参数交给第 4 层的 `seriesIdFromShareUrl` 去处理。

**出网时的安全约束**
- 手动跟跳，`maxRedirects: 0`，最多 5 跳
- **每一跳的 `Location` 都重新过 `shareHttpUrl` 校验**（协议白名单、禁 userinfo、≤4096 字符、G1 公网校验）
- 25s 总超时
- 响应体 2MB 上限
- 每跟一跳就尝试从新 URL 里解析 ID，命中就提前返回（省掉后续跳转）

**调用关系**
- 上游：IPC `hongguo-resolve`
- 下游：B1 的等价 axios 调用（但独立实现，因为需要手动跟跳）

**易混点**
`seriesIdFromShareUrl` 和 `resolveSeriesId` 是两个函数。前者只从单个 URL 里抠 ID（不出网），后者是完整流程。B3 内部也会调前者做校验，别混。

### B5 · 分类页 `browseList`（官网）

**功能定位**
官网分类页的抓取与解析。支持四个大类和题材筛选、翻页。

**典型场景**
用户点「分类」→「真人剧」→ 选「都市」题材 → 往下滚翻页。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `category` | `real-drama` / `comic-drama` / `ai-drama` / `comic` | 非法 → 走默认值而非报错（**注意**） |
| `genre` | 题材 slug，`^[a-z0-9-]+$` | 含中文或特殊字符 → 「分类参数无效」 |
| `page` | 页码 | — |
| `forceRefresh` | 绕开 120s 缓存 | — |
| `allowTrustedDns` | 由 main 按代理模式注入。**用户开了代理时不能强制直连** | — |
| `proxyLogin`（第 2 位置参数） | 代理 407 认证回调 | 不传 → 需要认证的代理下会失败 |

**返回结果用途**
`results[]`（含 `episode_label`、`completion_status`、`published_at` 等卡片信息）、`genres[]`（题材按钮）、`total`/`totalPages`（分页器）、`pageTitle`（页面标题）。

漫画类返回 `{ success:true, results: [], unsupported: true, emptyMessage }` —— 官网页面对漫画没有结构化数据，**明确告知而不是假装没有内容**。

**调用关系**
- 上游：IPC `browse-list`（`catalogChannel === 'web'` 时）
- 下游：**三路并行**（见下）
- 并列：A5（App 目录）

**三条路的真实关系是「条件分支 + 特定条件下并行」，不是三路并行**
（源码 `catalog.js` `fetchCatalogPage`）

```
if (!net?.request)                    // ① 无 net 环境（浏览器/测试）
    → 纯 axios（或可信 DNS 版），单路

if (!allowTrustedDns)                 // ② 有 net、未启用可信 DNS
    → 只用 net.request，单路

否则（有 net 且 allowTrustedDns）      // ③ 并行对冲
    → Promise.any([
         net.request(...).then(parse),
         可信 DNS axios(...).then(parse)
      ])
```

关键在第 ③ 种：**只有 `.then(parse)` 成功才算赢**，注释写着「a fast CDN error page must not cancel a healthy route」—— 一个快速返回的 CDN 错误页比一个超时更有害，因为它会让系统误以为官网挂了，从而取消掉了本来健康的那条路。

为什么需要 `net`？因为 `net` 走 Chromium 网络栈，能自动继承系统代理和证书配置。用户的代理设置对 `net` 生效，对 Node 版 axios 不生效。

为什么又要在启用可信 DNS 时并行？因为 `net` 在 VPN 的 Fake-IP 环境下会拿到 `198.18.x.x` 被 G2 拦掉，此时可信 DNS 那条路能救回来。

`finally` 里的 `controller.abort()` 是必须的 —— 赢家返回后立刻掐断输家，否则它会继续占带宽（注释同样强调「慢的漫画页不能堵住真人剧」）。

**其他防御**
- 10s 总超时
- `content-length > 8MB` 或累计 > 8MB → 「目录页面过大」
- **每个 URL 独立 `AbortController`** —— 注释：「慢的漫画页不能堵住真人剧」
- 缓存 120s / 容量 32

### B6 · 榜单页 `browseList`（官网）

**功能定位**
B5 的榜单分支。四个热播榜：`hot-drama`、`hot-real-drama`、`hot-comic-drama`、`hot-ai-drama`。

**典型场景**
用户点「热播榜」→ 切到「漫剧榜」。

**输入参数**
与 B5 完全相同（`category` / `genre` / `page` / `forceRefresh` / `allowTrustedDns` / `proxyLogin`），只有两点约束差异：
- `category` 必须从四个榜单值中取（`hot-drama` / `hot-real-drama` / `hot-comic-drama` / `hot-ai-drama`）
- **`genre` 传值即报错**（「无效的目录分类或题材」）—— 榜单不支持题材筛选，代码里 `ranking && genre` 直接判非法

**与 B5 的差异（这是它值得单列的原因）**

| 维度 | B5 分类页 | B6 榜单页 |
|---|---|---|
| 路径 | `/category/{cat}[/{genre}]` | `/rank/{cat}` |
| 是否支持题材 | 支持 | 不支持（`genres: []`） |
| 是否支持翻页 | 支持 | 支持 |
| 额外字段 | — | `rank`（排名）、`heat`（热度） |
| 解析器 | `parseCatalog` | `parseRanking`（双解析器） |

**双解析器的必要性**
榜单页有两个数据来源，可靠性不同：

1. **首选**：`<script data-fn-name="mergeLoaderData">` 的 `data-fn-args` 属性，HTML 实体解码后 `JSON.parse`。校验 `args[0] === 'rank_{category}/page'` —— 确保拿的是本榜单的数据
2. **降级**：SSR 语义 DOM 解析。`<article>` → `<h2 id="rank-title-{id}">` + `/detail?series_id=` 链接 + `<img src>` + `pc-categories` 题材 + 热度正则 + `<span>` 排名

为什么需要降级？因为 React Server Components 的 loader 数据格式会随 Next.js 版本变化，而语义化 HTML 相对稳定。

**返回结果用途**
和 B5 完全同构（`results[]` / `page` / `total` / `totalPages` / `hasMore` / `pageTitle` / `sourceUrl`），差异只有两处：
- 条目多出 `rank`（名次，用于显示「No.1」角标）和 `heat`（热度字符串，直接展示）
- `genres: []`、`total: 0` —— 榜单不分题材也不报总数，翻页靠 `totalPages`

**调用关系**
同 B5。上游 `browse-list`，下游 B1 的等价实现。

**易混点**
用户在 UI 上看到「热播榜保持热度顺序」—— 这条产品规则就落在这里：榜单的 `results` **不排序**，原样保留服务端顺序；而分类页的结果前端会按需重排。改排序逻辑时别改错地方。

### B7 · `searchHongguo` — 官网搜索

**功能定位**
红果官网的搜索接口（`/api/search/result`），未公开但被网页前端使用。**这是搜索链路的主通道**。

**典型场景**
1. 用户输入关键词搜索（App 搜索未开启或失败时）
2. 用户翻到第 2 页且第 1 页走的是官网通道
3. App 搜索返回的结果标题对不上（`hasTitleMatch` 为 false）→ 回退到它

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `keyword` | NFKC 归一后 1–200 字 | — |
| `options.page` | 默认 1，钳制到 1–50 | — |
| `options.timeout` | 默认 10000，下限 1000 | — |
| `options.retries` | 默认 **1**（0–3）。注意不是 3 | 传太大 → 风控加剧 |
| `options.deadline` | 剩余 <1000ms 立即中止 | — |
| `options.cache` | 默认 true，60s TTL | — |
| `options.request` | 注入点 | — |

**返回结果用途**
`{ results[], total, totalPages, page, hasMore, keyword }`。`totalPages` 用于渲染分页器（区别于 App 搜索的 `total: 0`）。

**调用关系**
- 上游：`searchAtSourcePage`（第 1 页主通道 / 第 2 页 `channel==='web'`）
- 下游：axios
- 并列：A3（App 搜索）、A6（上新补搜）、C2/C5/C8（第三方搜索）

**错误分类是这个接口的核心设计**
自定义 `HongguoSearchError{ kind, fallback, cause }`，`kind` 有四类：

| kind | 触发 | fallback | 下游行为 |
|---|---|---|---|
| `timeout` | 超时 | false | 重试 |
| `upstream` | 5xx / 429 | false | 重试，429 报「请求过于频繁」 |
| `format` | 4xx（尤其是 400-499） | **true** | **不再重试，改走 DOM 嗅探** |
| `input` | 参数非法 | false | 直接失败 |

**为什么 4xx 要标 `fallback: true`？**
官网搜索接口被风控时会返回 4xx，但网页本身仍可访问（只是走前端渲染）。所以此时正确做法不是「重试接口」（会继续被拦），而是**改为打开搜索页抓 DOM**。这个降级路径让搜索在接口失效时仍然可用。

**重试策略刻意保守**
`retries` 默认 1（即最多 2 次），退避 `400 × (attempt+1)`。搜索是高频操作，重试太激进会加速触发风控。

### B8 · `fetchPublicDetails` — 公开详情 / 评分 / 评论

**功能定位**
抓取官网详情页的公开数据：评分、点赞、收藏、长评列表、单集评论。**这是唯一能拿到「评论」的接口** —— 官网没有开放评论分页 API。

**典型场景**
1. 用户点开某集的「详情」面板 → 看评分和热评
2. 下载完成后自动导出剧评（`text-export` 的 `reviews` 项）
3. D2（单集评论）全部依赖它

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` | 必填，`^\d{6,30}$`。注意下限是 6 位（比别处严格） | — |
| `vid` | 可选。**传了抓 `/player/{sid}/{vid}`（含单集评论），不传抓 `/detail?series_id=`（只有整剧数据）** | 传错 → 没有单集评论 |
| `options.reviewsLimit` | 默认 50。官网最多给 50 条 | — |

**返回结果用途**
```
{ success, series_id, episode_id, episode_label, completion_status, published_at,
  rating, rating_count, like_count, favorite_count,
  reviews: { total, items: [{ author, avatar, content, created_at, likes, rating }] },
  episode_reviews, episode_like_count, sourceUrl }
```
- `rating` / `rating_count` → 详情面板顶部
- `reviews.items` → 长评列表
- `episode_reviews` → D2 的数据源
- `text-export` 拿它生成 `<剧名>.reviews.json`

**调用关系**
- 上游：IPC `get-public-details`、D2、`text-export`
- 下游：axios（**独立实现，不走 B1**，因为需要处理 302）
- 并列：D1（弹幕）、D2（评论）

**302 特判是这里最特殊的设计**
当某一集被锁定（需付费/会员），官网会 **302 跳到 `pc_locked_episode` 页面**。代码判定三个条件同时成立才认为是「锁定」：

1. `Location` 同源
2. 路径匹配 `/player/{seriesId}/\d{6,30}`
3. `pc_locked_episode === vid`

满足则返回 `{ success:false, source_limited:true, code:'EPISODE_COMMENTS_UNAVAILABLE' }`，而不是当成错误。

**为什么是 302 而不是自定义错误码？**
因为官网就是这么表达的 —— 它不返回 403，而是跳转到「该集需要解锁」的页面。必须解析跳转目标才能区分「这一集锁了」和「整个接口挂了」。

**其他**
- 超时 10s（`timeout` + `AbortSignal.timeout` 双保险）
- **永不抛异常**，全部转 `{ success:false }`
- 缓存 30s / 容量 64，key 含 `reviewsLimit`（防止不同 limit 复用同一份数据）
- `pending` Map 去重并发

### B9 · 扫码登录三接口

**功能定位**
红果账号的网页登录流程。三步：取二维码 → 轮询扫码结果 → 用 Cookie 换昵称。

**典型场景**
用户点「登录」→ 弹二维码 → 手机扫码 → 手机上确认 → 登录成功。

**三个端点的分工**

| 端点 | 作用 | 关键点 |
|---|---|---|
| `/passport/web/get_qrcode/` | 拿二维码图（base64 PNG）和 `loginId` | 返回 `image` 直接给前端渲染，无需二次请求 |
| `/passport/web/check_qrconnect/` | 轮询扫码状态 | 返回 `pending` / `expired` / `signed-in` |
| `/passport/account/info/v2/` | 用 Cookie 换 `{ id, nickname }` | 验证登录态是否真有效 |
| `{redirect_url}`（跳转链） | 吸收跳转过程中的 `Set-Cookie` | 仅允许官网及子域，≤5 跳 |

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `pollLogin(loginId)` | 必须与内存中的会话一致 | 不一致 → 拒绝（防止串号） |
| `next` | 固定为站点根。**不接收外部传入**，防开放重定向 | — |

**返回结果用途**
- `startLogin` → `{ loginId, image, expiresIn }`，`expiresIn` 用于前端倒计时
- `pollLogin` → `{ status }`，`signed-in` 时附 `account`
- `verify` → `{ id, nickname }`

**调用关系**
- 上游：IPC `start-account-login` / `poll-account-login` / `cancel-account-login` / `logout-account`
- 下游：Electron `session.fromPartition('hongguo-account-login').fetch()`
- 依赖：A7（历史同步）必须有这里的 Cookie


**为什么用 `session.fetch` 而不是 axios**
因为需要 **Cookie 罐**。`session.fromPartition` 自带独立 Cookie 存储，`fetch` 会自动带上/吸收 Cookie。用 axios 得自己实现 CookieJar，就是这个文件里那个只做字符串拼接的简化版。

**`finishRedirect` 的必要性，很容易被忽略**
`pollLogin` 成功后，服务端返回的是**一个跳转链**，不是一个直接的 200。`sessionid` 是在跳转过程中的 `Set-Cookie` 里下发的。如果不跟完这条链，拿到的 Cookie 是不完整的 —— 表现为「扫码显示成功但立刻变未登录」。

所以 `finishRedirect` 必须跑，且只允许跳向官网域名（防跳转到钓鱼站）。

**`generation` 计数解决什么**
用户反复扫码、取消、再扫，会同时存在多个 `pollLogin` 的异步链。没有 `generation` 校验，一个早先发出、后返回的「已登录」响应会覆盖用户刚取消的状态。这是扫码登录最典型的竞态。

**易混点**
和 A7 的区别：**B9 管「我是谁」，A7 管「我登录后能看什么」**。B9 用官网 Cookie，A7 用 App 接口 + Cookie。两者共享同一份 Cookie 存储。

## 4. C 组详解：第三方短剧源

三个源（河马 / 西饭 / 自定义）**没有共同基类，靠鸭子类型 + 前缀分发**。它们的价值是「红果没有的剧也能看」，代价是稳定性完全依赖对方站点。

### 4.0 先理解「前缀分发」这个机制

这是理解 C 组所有接口的前提。所有 ID 都带前缀，上层按前缀路由：

```
"8654321"                          → 红果自有
"hema:1234567"                     → 河马
"xifan:jiuzhou:253"                → 西饭
"custom:a1b2-c3d4...:8899"         → 自定义源
```

`hongguo.fetchEpisodeList` / `fetchPlayUrlSingle` 就是三个 `if (startsWith)`：

```js
if (String(seriesId).startsWith('custom:')) return require('./custom-source').fetchEpisodeList(seriesId);
if (String(seriesId).startsWith('hema:'))   return require('./hema').fetchEpisodeList(seriesId);
if (String(seriesId).startsWith('xifan:'))  return require('./xifan').fetchEpisodeList(seriesId);
// 否则走红果双通道
```

**这意味着：第三方源永远不经过红果的双通道降级、不经过 `cachedRequest`、不经过 `failedWebMedia` 惩罚。** 它们是完全独立的支路。

### C1 · `hema.browseList` — 河马分类页

**功能定位**
抓取河马短剧（`www.kuaikaw.cn`）的分类列表。数据来自 Next.js 的 `__NEXT_DATA__`。

**典型场景**
用户在「来源」里切到河马 → 点分类 → 翻页。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `genre` | 默认为 `'0'`（全部）。格式 `^\d{1,30}(?:-\d{1,30}){0,15}$` —— 支持多级题材用 `-` 连接 | 格式不符 → 回退到全部 |
| `page` | 默认 1 | — |
| `forceRefresh` | 绕开 5 分钟题材缓存 | — |
| （第 2 位置参数） | main.js 会传 `authInfo, callback`，但 **hema 的签名里没有这两个参数，被静默忽略** | 改代码时别以为它支持代理认证 |

**返回结果用途**
`results[]`（`series_id` 形如 `hema:1234567`）、`genres[]`（题材按钮）、`hasMore`/`nextPage`。

**`total: 0` / `totalPages: 0` 是刻意的**
河马的服务端不返回总数。所以分页只能靠**正则探测 HTML 里是否存在 `href="/browse/{slug}/{page+1}"`** 来判断还有没有下一页。这是很脆弱的设计 —— 站点改用 JS 无限滚动就失效了。

**调用关系**
- 上游：IPC `browse-list`
- 下游：无独立层，内部 `request()`
- 并列：B5、A5、C4、C7

**一致性校验**
返回的 `data.page`、`data.typeThreeId` 必须与请求一致，否则「河马返回的目录与请求不一致」。防的是缓存串页或服务端 bug。

**易混点**
`maxRedirects: 0` —— 任何 3xx 直接失败。如果河马哪天把 `kuaikaw.cn` 301 到 `www.kuaikaw.cn`，这里会静默全挂。改域名时要记得同步 ORIGIN 常量。

### C2 · `hema.search` — 河马搜索

**功能定位**
河马站的搜索接口。

**典型场景**
用户切到河马源后搜索剧名。

**输入参数**

**返回结果用途**
同 C1，但 `total: Number(data.totalSize)`（有总数）。

**易混点**

### C3 · `hema.detail` — 河马详情（分集 + 播放）

**功能定位**
一个内部函数，同时支撑 `fetchEpisodeList` 和 `fetchPlayUrlSingle` 两个导出。核心是抓 `/drama/{bookId}` 页面解析 `chapterList`。

**典型场景**
1. 用户点进河马的某部剧 → `fetchEpisodeList` 拿分集
2. 用户点播放 → `fetchPlayUrlSingle` **重新拉一次详情**拿播放地址

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` | 必须 `hema:{bookId}`，段数 2，各段纯数字 | 「河马剧集编号无效」 |
| `vid`（播放时） | 必须 `hema:{bookId}:{chapterId}`，段数 3 | 「河马分集编号无效」 |
| `sid`（播放时，可选） | 传入时会校验与 `vid` 属同一部剧 | 不匹配 → 「河马分集不属于当前剧集」 |

**返回结果用途**
- 分集：`{ series_id, series_title, cover, total, episodes[], source:'hema' }`
- 播放：`{ url, spadeA: null, codec: '', source:'hema' }`；锁定则 `{ url:null, locked:true, error }`

**`locked` 的判定语义（三源各不相同，极易搞错）**

| 源 | 判定 | 含义 |
|---|---|---|
| 河马 | `episode.isCharge !== '0'` | 黑名单式：不是 '0' 就算收费 |
| 西饭 | `episode.unlock !== true` | 白名单式：没明确 true 就算锁 |
| 自定义 | `locked===true \|\| points>0 \|\| pwd非空` | 三条件任一 |

**为什么每次播放都重新拉详情？**
代码注释两处强调：`never reuse a cached free/paid decision`、`Always re-read access state`。因为**免费/付费状态会变**（限免活动、会员到期），缓存会导致「昨天能看今天打不开」或「明明付费了还说锁着」。代价是每次播放多一次详情请求。

**取流**
|  |  |  |
| --- | --- | --- |
`httpsUrl(chapterVideoVo.mp4720p) || httpsUrl(chapterVideoVo.mp4)` —— 优先 720P，回退默认。两个都不合法 → 「河马未提供有效 HTTPS 播放地址」。

**`httpsUrl()` 是唯一的安全校验**
只做两件事：必须是 `https:`、不能有 userinfo。**不走 G2 的 DNS 内网拦截**（这是已知缺口，见 9.2）。

**调用关系**
- 上游：`hongguo.fetchEpisodeList` / `fetchPlayUrlSingle` 的前缀分发
- 下游：内部 `request()`
- 并列：C6、C9

**易混点**
`fetchPlayUrlSingle(vid, sid)` 的第 3 个参数（`options`）在 `hongguo.js` 里被传入但**函数签名里没有**，被忽略。也就是说**河马不支持清晰度选择**，只能用服务端给的那个。

### C4 · `xifan.browseList` — 西饭分类页

**功能定位**
抓取西饭（`xifan-api-cn.youlishipin.com`）的分类列表。这是 App 端的 portal 接口，返回 JSON 而非 HTML，稳定性比河马好。

**典型场景**
用户切到西饭源 → 选分类 → 翻页。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `genre` | **必须是内部 `genres()` 产出的 slug**（形如 `{categoryId}-{hex(oppoCategory)}`）。传别的会「西饭题材无效，请重新选择」 | 硬编码题材值 → 全部失败 |
| `page` | `parseInt` 后 `max(1,…)` | — |
| `forceRefresh` | 刷新题材缓存（300s） | — |

**这个 slug 格式为什么要 hex**
`oppoCategory` 是中文名（如「都市」），直接拼进 URL 会有编码问题。转 hex 后变成纯 ASCII，安全且可逆。

**返回结果用途**
`results[]`（`series_id` 形如 `xifan:{source}:{duanjuId}`）、`genres[]`、`hasMore`。

**`total: 0` / `totalPages: 0`**
和河马一样不返回总数，但判断方式不同：`hasMore = result.hasMore === true` —— **直接用服务端给的布尔值**，不需要探测。这是比河马更可靠的设计。

**调用关系**
- 上游：IPC `browse-list`
- 下游：内部 `request()`
- 并列：C1、B5、A5、C7

**错误处理**
内部失败抛 `invalid result`（要求 `data.ret === 0` 且 `data.result` 是非数组的 object），外层统一折叠成「西饭加载超时」/「西饭来源暂不可用」。**不重试**。

### C6 · `xifan.detail` — 西饭详情（分集 + 播放）

**功能定位**
同 C3，但走 JSON 接口 `getDuanjuInfo`。

**典型场景**
1. 用户点进西饭的某部剧 → `fetchEpisodeList` 拿分集
2. 用户点播放 → `fetchPlayUrlSingle` 重新拉一次详情（`Always re-read access state`，理由同 C3）

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` | `xifan:{source}:{duanjuId}`，段数 3，每段 `^[a-zA-Z0-9_-]{1,200}$` | 「西饭剧集编号无效」 |
| `vid`（播放） | `xifan:{source}:{duanjuId}:{episodeId}`，段数 4 | 同上 |
| `sid`（播放，可选） | 校验同剧 | 「西饭分集不属于当前剧集」 |

注意 `source` 段不是数字而是字符串（如 `jiuzhou`），这是和河马最大的 ID 形态差异。

**返回结果用途**
- 分集：`{ series_id, series_title, cover, total, episodes[], source:'xifan' }`
- 播放：`{ url, spadeA:null, codec:'', source:'xifan' }`

**一致性校验**
`result.source === source && String(result.duanjuId) === duanjuId && Array.isArray(result.episodeList)` 三条同时成立。任一不符 → 「西饭返回的剧集与请求不一致」。

**标题冲突处理：一个刻意保守的设计**
`episodeDisplayTitle()` 只对硬编码的 `VERIFIED_TITLE_CONFLICTS` 白名单（目前一条：`xifan:jiuzhou:253` 的 `天龙战神` 应屏蔽 `爱归良辰`）返回空串。

代码注释明确禁止用「看起来像另一部剧」来启发式推断冲突。理由很充分：**误判的代价是用户看不到正确标题**，比漏判更糟。

**调用关系**
- 上游：`hongguo.fetchEpisodeList` / `fetchPlayUrlSingle` 前缀分发；`episodeDisplayTitle` 还被 `main.js` 单独调用
- 并列：C3、C9

**取流**
`httpsUrl(episode.playUrl)`，失败 → 「西饭未提供有效 HTTPS 播放地址」。同样不走 G2。

### C7 · `custom-source.fetchCatalog` — 自定义源目录

**功能定位**
对接用户自己填的苹果 CMS（MacCMS）站点。这是三个第三方源里**唯一受完整安全护栏保护**的 —— 因为 URL 是用户填的，必须假设它可能是恶意的。

**典型场景**
用户在设置里添加一个自己用的资源站 → 在「来源」里选它 → 浏览分类。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `source` | `custom:{uuid}` 或裸 uuid | 「该自定义源已禁用或删除」 |
| `genre` | `^\d{1,30}$`（MacCMS 的 `type_id`） | — |
| `page` | 必填，1–100000 | — |

**返回结果用途**
`{ success:true, results[], page, total, totalPages, hasMore, nextPage, genres[], pageTitle, sourceUrl }`。

`results[]` 渲染卡片；`genres[]` 是 MacCMS 的 `data.class`（最多 500 条，`type_id` 须纯数字），用于渲染题材下拉；`total` / `totalPages` 来自 `data.pagecount`，是**三源里唯一给真实总数的** —— 所以自定义源能显示页码器，河马和西饭只能显示「加载更多」。

**比另两源多两个字段**
`intro`（简介，MacCMS 的 `vod_content`）、`locked`（是否需积分/密码）。

**这是唯一做了「配置漂移」检测的接口**
`check()` 在**四个时点**复查源配置：发起前 / DNS 回调前后 / 重定向时 / 响应后。每次都比对 `assertEnabled(source.id).url` 与当前 `source.url`，不一致就抛「来源配置已变更，请重新加载」。

防的是 TOCTOU 攻击：用户请求发出后立刻删掉源，或把 URL 改成内网地址，此时旧请求还在飞行中。

**为什么错误消息绝不透传远端**
代码注释：`avoid leaking signed URLs`。MacCMS 的错误响应里可能带完整播放地址（含签名），透传给前端等于泄漏。所以只放行以「自定义源」「该自定义源」「来源配置」开头的本地错误，其余全部归一成「自定义源请求失败，请检查公网接口与网络」。

**一个值得注意的实现选择**
`ac` 恒定为 `detail`，目录和搜索都用 `ac=detail`（靠 `pg`/`t`/`wd` 让服务端返回列表），**没有用 MacCMS 惯用的 `ac=videolist`**。这依赖各站对「无 ids 的 detail」的宽容度 —— 兼容性隐患，但不是 bug（改了就挂现有站点）。

**调用关系**
- 上游：IPC `browse-list`（`source: 'custom:uuid'`）
- 下游：内部 `request()` → G2 护栏
- 并列：C1、C4

**取消支持**
`activeRequests: Map<sourceId, Set<AbortController>>`，`cancelRequests(id)` 批量 abort。这是三源里唯一支持取消的 —— 因为用户可能在请求进行中删掉源。

### C8 · `custom-source.searchSeries` — 自定义源搜索

**功能定位**
自定义源的搜索。**签名和另外两源不同**，这是接入时最容易踩的坑。

**典型场景**
用户在「来源」里选中某个自定义源 → 搜索框输入关键词 → 翻页。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `keyword` | trim 后 1–200 字 | 「自定义源搜索词或页码无效」 |
| `{ source, page }` | **注意 `page` 在第二个参数对象里**，不是独立位置参数 | 按 `(kw, page, opts)` 写 → `page` 变 undefined，翻页失效 |

**返回结果用途**
同 C7 的 `pageResult` 结构。

**调用关系**
- 上游：`searchAtSourcePage`（`source.startsWith('custom:')`）
- 并列：C2、C5

**易混点**

// 河马 / 西饭

// 自定义源

### C9 · `custom-source.detail` — 自定义源详情（分集 + 播放）

**功能定位**
MacCMS 的 `ac=detail&ids={vodId}`，解析播放串得到分集列表和直链。

**典型场景**
1. 用户点进自定义源的某部剧 → `fetchEpisodeList` 解析播放串拿分集
2. 用户点播放或下载 → `fetchPlayUrlSingle` 重新 `detail()`（每次重取权限态）

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` | `custom:{uuid}:{vodId}`，段数 3 | 「自定义源编号无效」 |
| `vid`（播放） | `custom:{uuid}:{vodId}:{line}:{episode}`，段数 5，第 4/5 段 `^\d{1,5}$` | 同上 |

**播放串解析是这个接口最复杂的部分**
MacCMS 的 `vod_play_url` 是一坨嵌套分隔符：

```
线路1$$$线路2$$$线路3        ← vod_play_from（线路名）
地址1#地址2#地址3            ← vod_play_url（按线路分组，$$$ 分隔）
名称$地址                     ← 每个分集（$ 分隔）
```

解析规则（每一步都有上限，防恶意站点构造超长串打爆内存）：
- `vod_play_from.split('$$$')` → 线路名
- `vod_play_url.split('$$$').slice(0, 32)` → 最多 32 条线路
- 每条线 `split('#').slice(0, 10000)` → 每线最多 1 万集
- 每个分集 `indexOf('$') >= 1` → 必须有名称和地址
- 地址须过 G1 且 pathname 以 `.mp4` / `.m3u8` 结尾


**线路选择：取集数最多的那条**
`episodes.length` 降序取第一。理由：集数最多的线路通常最完整，其他线路可能是残缺镜像。

**`candidates[]` 是三源独有的字段**
`fetchPlayUrlSingle` 返回 `{ url, format, candidates[] }`。`candidates` 包含「其他线路中同名分集的地址」，供 `withMediaRecovery` 在同一集内换线路重试。

但注意：`prepare-online-play` 只取 `candidates[0]`，且 `withMediaRecovery` 对第三方源只跑 1 轮 —— **候选的实际利用率很低**，属于「有总比没有好」的兜底。

**`format` 字段**
`'mp4'` 或 `'hls'`。这是三源里唯一显式区分格式的 —— 因为 MacCMS 站点两种都可能给，HLS 要走 E2 转封装。

**返回结果用途**
- 分集：`{ ...normalizeItem, total, episodes: [{ vid, vid_index, title, series_id, series_title, cover, locked, source }] }`
|  |  |
| --- | --- |
- 播放：`{ url, format:'mp4'|'hls', source:'custom', spadeA:null, codec:'', vid, userAgent, referer, candidates[] }`

`format` 决定下游走 E1（mp4 直取）还是 E2（HLS 转封装）；`userAgent` / `referer` 必须原样带给 E1，MacCMS 站点的 CDN 通常校验 Referer；`candidates[]` 是同集其他线路的备选地址。

**调用关系**
- 上游：`hongguo.fetchEpisodeList` / `fetchPlayUrlSingle` 前缀分发
- 下游：内部 `request()` → G2
- 并列：C3、C6

### C10 · `testCustomSource` — 源可用性自检

**功能定位**
用户添加或编辑自定义源时，**先试抓一次再保存**。避免存进一个根本用不了的地址。

**典型场景**
用户在「设置 → 自定义源」里填完名称和地址，点「测试」。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `draft` | `{ name, url, id?, enabled? }`，**尚未保存的草稿** | — |

`validateSource` 会做规范化：名称去标签后 1–80 字、URL ≤4096 且过 G1、`pathname === '/'` 时**自动补 `/api.php/provide/vod/`**（MacCMS 的标准路径）、清空 `hash`。

**返回结果用途**
`{ success:true, count: number, genres }` —— `count` 告诉用户「这个源有多少条内容」，`genres` 用于预览分类。

**调用关系**
- 上游：IPC `test-custom-source`
- 下游：内部 `request()`，`draft = true` **跳过 `assertEnabled`**（因为源还没保存）
- 并列：C7（保存后的正式抓取）

**易混点**
和 C7 走完全相同的请求路径，唯一区别是 `draft` 标志：
- `draft = true` → 不做 `assertEnabled`（源可能不存在于 store）
- `draft = false` → 每次都 `assertEnabled` + 配置漂移检测

前端 `CustomSources.jsx` 还在 IPC 外自己包了一层超时 —— 因为用户可能在测试时直接关掉弹窗，不能让请求悬着。

## 5. D 组详解：弹幕与评论

两个接口都是「内容消费的附加层」—— 不影响能不能看剧，但影响社区感。共同特点：**永不抛异常**，失败就安静降级。

### D1 · `fetchDanmaku` / `requestWindow` — 官方分时弹幕

**功能定位**
从番茄的评论接口拉取**按时间轴对齐的弹幕**，归一化成播放器能直接渲染的结构。这是全项目唯一需要**自建匿名身份文件**的接口。

**典型场景**
用户点开某集播放 → 播放器按 90 秒一个窗口向主进程要弹幕 → 主进程聚合后返回。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` | `^\d{6,30}$`，作为 `book_id` | 非法 → 返回失败结构（不抛） |
| `vid` | `^\d{6,30}$`，作为 `group_id`。**弹幕是挂在 vid 上的，不是 series 上** | 传错集 → 拿到别的集的弹幕 |
| `limit` | 默认 3000，1–3000。上限 3000 是硬护栏 | — |
| `fresh` | true 绕缓存。对应界面上的「重试」按钮 | — |
| `transport` / `now` / `random` | **三个测试注入点**，让签名可以完全离线复现 | — |

**`requestWindow` 为什么要单独暴露**
它是「单窗口请求」，是 `fetchDanmaku` 分页循环里的一步。单独导出是为了**单元测试能只测一个窗口的签名与解析**，不必跑完整分页。这是很实用的可测性设计。

**返回结果用途**
```
{ success, source:'official', series_id, episode_id,
  items: [{ time: 秒, text, color: '#RRGGBB', mode: 'scroll'|'top'|'bottom' }],
  total, truncated, partial, error, notice }
```
- `items[].time`（秒）→ 播放器用它决定何时弹出
- `items[].mode` → 滚动 / 顶部固定 / 底部固定
- `partial` → 分页中途失败，前端可提示「弹幕可能不全」
- `notice` → 中文原因，**直接展示给用户**

**调用关系**
- 上游：IPC `get-episode-danmaku`；`text-export` 批量导出
- 下游：`danmaku-sign`（签名）+ `sm3`（摘要）
- 并列：D2（评论）

**签名与 A 组的根本差异（必须分清）**
`danmaku-sign.js` 是**完整实现**：34 轮 Ladon、72 轮 Argus、手写 protobuf 环境包。而 `app-source.js` 里的是**退化实现**（只 base64 时间戳）。

两者不可互换：服务端按 App 版本校验，混用必然失败。这也是为什么这里要独立一套签名代码而不是复用。

**时间戳三兄弟必须同步生成**
`stampMs`（毫秒，进 query 的 `_rticket`）、`stamp`（秒，进 `X-Khronos`）、`nonce`（11 字节，三段投喂不同算法）**必须在同一个函数里一次生成**。

任何一处时间不一致，签名就失效 —— 且表现为模糊的「接口不可用」，极难排查。代码把这三个值放在同一个作用域，就是为了防止被拆开。

**为什么永不抛异常**
因为弹幕是**附加功能**。弹幕接口挂了不该导致整集不能播。所有错误都转成 `success:false` + 中文 `notice`，播放器照常工作。

错误文案还刻意做了**脱敏**：不输出原始异常（可能含签名 URL 和设备指纹），只给用户可理解的描述，如「弹幕接口响应超时（已用官方签名请求），可稍后再试」。

**本机身份文件 `danmaku-client.json`**
弹幕接口需要一个稳定的匿名 `deviceId` / `installId`。文件存在 `%userData%/`，`mode 0o600`，用 `flag: 'wx'` 原子创建（防并发写坏）。

读写失败 → `DANMAKU_IDENTITY_IO` → 「弹幕本机配置读取或保存失败，请检查资料目录权限后重试」。

**注意：这个错误不等于「本集没有弹幕」**。用户会以为是没弹幕，实际是权限问题。这是排查时的一个陷阱。

**分页护栏（六道）**
`MAX_PAGES=40`、`MAX_ITEMS=3000`、`MAX_EMPTY_PAGES=2`、`PAGE_GAP_MS=120`、`nextMs` 必须严格前进、`duration` 上限 24h。

第 5 条最关键：如果服务端返回相同的 `next_offset_time`，没有「严格前进」判定就会无限请求。

### D2 · `fetchEpisodeComments` — 单集评论

**功能定位**
把官网详情页里的**公开评论预览**包装成评论接口。**它不是真正的评论 API** —— 官网没有开放评论分页，这里只是把 SSR 页面里的最多 50 条评论重新包装。

**典型场景**
用户点「本集评论」面板。当 D1（弹幕）不可用时，作为替代的社区内容来源。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `seriesId` / `episodeId` | `^\d{6,30}$` | — |
| `cursor` | **必须为 `null`**。非 null 直接返回 `source_limited` 说明 | 传了 → 明确拒绝而非报错 |
| `limit` | 默认 30，1–30。比 D1 小得多，因为总量就 50 条 | — |

**返回结果用途**
```
{ success:true, series_id, episode_id,
  items: [{ id: 'sha256', content }],
  next_cursor: null, has_more: false, total, source_limited: true, notice }
```

**三个字段恒为固定值，这是设计不是 bug**
- `next_cursor: null`
- `has_more: false`
- `source_limited: true`

它们共同表达一件事：**这是能拿到的全部，没有下一页，不要做无限滚动**。前端据此把「加载更多」按钮置灰。

`cursor !== null` 时直接拒绝，也是同一个意思 —— 与其假装支持分页，不如明确说不支持。

**`id` 用 sha256 而不是点赞数参与**
`sha256([seriesId, episodeId, author, created_at, content])`。**刻意排除点赞数**，因为点赞会变。如果 id 随点赞变化，前端列表每次刷新都会整片重渲染（React key 变化），体验很差。

**调用关系**
- 上游：IPC `get-episode-comments`（额外校验 `senderFrame === mainFrame`）
- 下游：B8（完全依赖）
- 并列：D1

**易混点**
它和 B8 是**同一次请求的两种投影**。B8 返回完整详情（评分、评论、单集评论），D2 只取 `episode_reviews` 并重命名。所以 D2 **没有独立缓存** —— 命中的是 B8 的 30s 缓存。

## 6. E 组详解：媒体流与 HLS

前两组解决「去哪拿地址」，这一组解决「怎么把内容读下来」。两者的失败模式完全不同：取址失败是「404 拿不到」，取流失败是「拿到了但读一半断了」。

### E1 · `requestMedia` — 媒体流读取

**功能定位**
把 `playInfo.url` 的内容以流的形式读下来。这是**唯一真正传输视频字节**的接口。它不解析视频、不解密、不转码，只负责「把字节可靠地搬过来」。

**典型场景**
1. 播放在线视频 → `prepare-online-play` 内部调它
2. 下载任务 → `executeHongguoDownload` 调它
3. 兼容转码 → 先取流再喂 FFmpeg

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `playInfo.url` | 播放地址。校验协议只能 `http:`/`https:`、禁 userinfo | 「无效播放地址」 |
| `playInfo.vid` | 用于 `checkCustomAccess` —— 自定义源的剧每次取流都要复查权限 | 源被删了还在播 |
| `playInfo.source` | **决定走不走 G2 护栏**：`'web'`/`'custom'` 走，`'app'`/`'api'`/第三方不走 | 见 9.2 缺口 |
| `playInfo.userAgent` | 原样带给 CDN。官网 CDN 会校验 UA，不带就 403 | 403 |
| `playInfo.referer` | 同上，更严格。部分 CDN 只认 Referer | 403 |
| `options` | 覆盖 axios 配置（`signal`、`cancelToken`、`Range` 等） | — |

**返回结果用途**
axios `response`，`data` 是流。调用方 `pipe` 到文件或 `MediaSource`。

**调用关系**
- 上游：`executeHongguoDownload`、`prepare-online-play`、`withMediaRecovery`
- 下游：axios（可能经 G2）
- 并列：E2（HLS 走它之外的独立管道）

**重试策略按源区分，这是刻意的不对称**

| 源 | 重试状态码 | 理由 |
|---|---|---|
| `web` | 404 / 410 / 5xx | 官网 CDN 换节点后旧地址会 404，值得重试 |
| 其他 | 403 | 403 通常是 Referer/UA 不对，换 Referer 可能解决 |

更细的是：第 2 次尝试会**翻转 Referer**：
- `app`/`api` 源原本带了 Referer → 删掉
- 原本没带 → 加上 `VIDEO_REFERER`

这解决的是「同一个片源，有时候要 Referer 有时候不要」的历史问题。属实用主义的兼容处理。

**三道内容校验**
1. `content-type` 是 `text/html` / `application/json` → 「片源返回了错误页面」（CDN 常返回 200 的 HTML 错误页）
2. **206 完整性校验**：`content-range` 必须是 `bytes 0-N/N`，即从 0 开始、长度等于总长。否则「视频响应不完整」
3. 失败挂 `mediaRetryable` / `mediaStatus`，供上层决定是否重试

第 2 条是防「看似成功实则残缺」的下载 —— 某些 CDN 会返回 206 但只给前几 KB，如果不校验，用户会得到一个 200KB 的「完整」视频。

**`ERR_WEB_MEDIA_ADDRESS` 的处理**
G2 拦截时抛这个码。处理方式是调 `markWebMediaFailure(playInfo)` 把该 vid 的官网通道**罚停 5 分钟**，然后抛「官网片源地址不安全，正在尝试其他片源」。

注意这是**优先级惩罚，不是可用性否定**。5 分钟后会重新尝试官网（因为问题可能已修复）。

---

### E2 · `remuxHls` — HLS 落盘转封装

**功能定位**
把 m3u8 播放列表**完整下载到本地**再交给 FFmpeg 封装成 mp4。注意：**不是边下边播的 HLS 代理**，是「先全部落盘再转换」的离线管道。

**典型场景**
1. 下载一部 HLS 格式的剧
2. 播放时遇到 HLS 片源，`prepare-online-play` 先转成可 seek 的 mp4
3. 兼容转码前的前置步骤

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `url` | 入口 m3u8，**必须过 G2** | 拦截 |
| `output` | 目标 mp4 路径 | — |
| `ffmpeg` | FFmpeg 可执行文件路径 | 缺失 → 「未找到 FFmpeg，无法准备 HLS 视频」 |
| `signal` / `cancelToken` | 取消 | — |
| `request` | 注入点（测试） | — |
| `checkAccess` | `main.js` 注入 `checkCustomAccess(vid)`，**每下载一个资源复查一次**。本集权限如果中途被收回，立刻停 | — |
| `headers` | UA / Referer 透传 | 403 |
| `onProgress` | 进度回调，≥150ms 节流 | — |
| `tempCapacityBytes` | 暂存上限 | — |

**返回结果用途**
无返回值。成功即产出 `output` 文件；失败会 `unlink` 残留。

**调用关系**
- 上游：`main.prepareHlsFile()` → 下载 / `prepare-online-play` / `transcode-for-playback`
- 下游：E1 的等价 `requestHls`（独立实现，`responseType: 'stream'`）
- 并列：E1（mp4 直取）

**为什么必须先落盘再转封装**
注释写得很清楚：`bundled FFmpeg has no HTTP transport`。打包的 FFmpeg 是精简编译版，没有 HTTP 协议支持。所以只能：
1. 自己把清单、分片、密钥全下到本地临时目录
2. 改写成指向本地文件的清单
3. 让 FFmpeg 用 `-protocol_whitelist file,crypto` 处理本地文件

那个协议白名单还起**安全作用** —— 即使清单里有 `http://` 地址，FFmpeg 也无法发出请求。

**这一组的护栏是全项目最密的（14 条）**

| 类别 | 检查 | 错误 |
|---|---|---|
| 结构 | 循环引用（同一 URL 出现在祖先链） | HLS 清单循环引用 |
| 规模 | `files.size >= 10000` | HLS 清单过大 |
| 体积 | 单清单 >2MB | HLS 清单过大 |
| 格式 | 不以 `#EXTM3U` 开头 | 无效 HLS 清单 |
| 直播 | 有 `#EXTINF` 但无 `#EXT-X-ENDLIST` | 暂不支持未结束的直播清单 |
| 变量 | 含 `#EXT-X-DEFINE` | 不支持含动态地址变量的 HLS 清单 |
| 加密 | `METHOD` 不是 `AES-128`/`NONE` | 不支持该 HLS 加密方式 |
| 密钥 | 密钥文件不是 16 字节 | HLS 密钥长度无效 |
| 地址 | `URI=` 出现次数与 `URI="..."` 不匹配 | HLS 地址格式无效 |
| 内容 | 分片返回 `text/html`/`application/json` | HLS 分片返回了错误页面 |
| 完整 | `content-length` 与实际不符 | HLS 分片下载不完整 |
| 磁盘 | `statfs` 可用 < 需求 + 512MB 预留 | HLS 暂存空间不足 |
| 时限 | 10 分钟总超时 | HLS 准备超时 |
| 转换 | FFmpeg 退出码 ≠ 0 / 输出为空 | HLS 媒体转换失败 |

**多码率只保留最高的一条**
遇到多个 `#EXT-X-STREAM-INF` 时，只保留 `BANDWIDTH` 最大的，其余连同下一行删除。因为下载场景要的就是最高画质，解析多路无意义。

### E3 · `resolveOfficialAddress` — 官网可信 DNS（DoH）

**功能定位**
当本地 DNS 返回的是 **Fake-IP**（常见于 VPN / 代理软件的「增强模式」）时，改用 DNS over HTTPS 拿真实的官网 IP。

**典型场景**
用户开着 VPN 用本应用 → 本地解析 `hongguoduanju.com` 得到 `198.18.x.x` → G1 判定为内网地址直接拦截 → 所有官网接口全挂。

**输入参数**
无（固定域名 `hongguoduanju.com`）。

**返回结果用途**
IP 列表，缓存 ≤60s。

**调用关系**
- 上游：`warmOfficialDns()` 预热、G2 的 `lookup` 钩子
- 下游：`https://1.1.1.1/dns-query`、`https://223.5.5.5/resolve`（`Promise.any` 竞速）
- 并列：系统 DNS

**为什么用两个 DoH 端点竞速**
`1.1.1.1`（Cloudflare）和 `223.5.5.5`（阿里）在国内的可达性不同。任何一个被墙，另一个还能用。`Promise.any` 保证「先回的那个算数」。

**`proxy: false` 是必须的**
DoH 请求必须是**直连**。如果走代理，代理又依赖本地 DNS，就形成循环依赖，永远解不出来。

独立 `httpsAgent` 也是同理：不能复用普通请求的 Agent，否则可能拿到被污染 DNS 打开的 socket。

**失败静默**
`warmOfficialDns()` 内部 `.catch(() => {})`。预热失败不该影响启动 —— 真需要时会再试。这是「预热」而非「必需」步骤。

## 7. F 组详解：应用级接口

这一组和「看剧」无关，是应用的自我维护能力：公告、更新、代理自检。共同特点：**全部可失败、失败后应用照常可用**。

### F1 / F2 · 远程公告

**功能定位**
从 GitHub Raw 拉两份静态 JSON：普通公告和紧急公告。**这是唯一能向所有用户推送信息的渠道**。

**典型场景**
1. 应用启动 / 定时轮询 → 检查普通公告
2. 紧急情况（服务变更、严重 bug）→ 检查紧急公告
3. 用户点「查看公告」→ 手动拉当前公告

**输入参数**

| 方法 | 参数 | 作用 |
|---|---|---|
| `checkAnnouncements` | `{ urgentOnly? }` | `true` 时只查紧急公告 |
| `getCurrentAnnouncement` | 无 | 手动查看 |
| `acknowledgeAnnouncement` | `{ id }` | 标记紧急公告已读。**id 必须在本次进程的 `receivedUrgentIds` 里** —— 防止前端伪造 id 消除未读 |
| `dismissAnnouncement` | `{ mode: 'day'\|'version' }` | 普通公告免打扰：当天不再提示 / 本版本不再提示 |
| `setAnnouncementPreferences` | `{ normalEnabled?, emergencyEnabled? }` | 开关 |

**返回结果用途**
`{ id, title, body, urgent }`。`urgent` 决定用弹窗还是角标。


**调用关系**
- 上游：IPC 6 个通道
- 下游：axios（**直连，不走 G2**，因为 GitHub Raw 可信）
- 并列：F3（更新检查）

**为什么「顶层键数恰好 4 个」这种校验**
公告 JSON 是远程内容，一旦仓库被入侵或账号被盗，恶意内容会推给所有用户。所以校验极严：

| 校验 | 防什么 |
|---|---|
| `Content-Type ∈ {json, text/plain}` | 防返回 HTML 钓鱼页 |
| UTF-8 ≤32KB | 防超大响应打爆内存 |
| 顶层键数**恰好 4 个** | 防塞入额外指令字段（如 `script`、`url`） |
| `active === true` | 服务端的开关 |
| `id` 匹配 `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` | 防路径穿越 / 注入 |
| `title ≤120` 无控制字符、无尖括号 | 防 XSS —— 尖括号在正文里可能被渲染成 HTML |
| `body ≤4000` | 长度上限（允许换行） |

**「恰好 4 个键」是最有意思的一条**：不是「至少 4 个」，是「恰好」。多一个字段就整份作废。理由是公告的 schema 是固定的，多字段说明要么是版本不兼容，要么是被投毒。

**三个防重复机制**
1. **单飞**：`normalRequest`/`emergencyRequest`/`manualRequest` 各持一个 Promise，并发调用共享
2. **generation 计数**：开关变更后旧请求结果作废
3. **紧急公告 5 分钟节流**：`EMERGENCY_INTERVAL_MS`

**易混点**
`checkAnnouncements`（轮询用）和 `getCurrentAnnouncement`（用户主动查看用）是两条独立路径，各持单飞 Promise。轮询的节流不影响手动查看。

---

### F3 / F4 · 更新检查（两级数据源）

**功能定位**
检查 GitHub 上有没有新版本。**核心设计是「配额友好」**：先试 API，失败则降级到网页 302。

**典型场景**
应用启动时自动检查；用户点「检查更新」手动检查。

**输入参数**
无。

**返回结果用途**
|  |  |
| --- | --- |
`{ enabled, release: { version, url } | null, error }`。

`release.url` 会**强制重写**成 `https://github.com/jackotom/hongguo-drama/releases/tag/{tag}` —— 无论 API 返回什么。这是防远程 URL 注入：即使仓库被投毒返回一个恶意 `html_url`，用户点了也只会去自己仓库的发布页。

**调用关系**
- 上游：IPC `check-app-update`
- 下游：axios（直连）
- 后续：结果缓存进 `latestAppRelease`，供 `open-app-update` 和 F5 使用

**两级降级的完整逻辑**
```
① 文件开关关闭 → { enabled: false }，清缓存
② 预览版 / 非主窗口 → { enabled: false, release: null }
③ 代理启动降级中 → { enabled: false, error: '请先修复或明确关闭代理' }
④ GET api.github.com/.../releases/latest
     ├─ 成功 → availableRelease() 比较版本
     └─ 失败 → ⑤ GET github.com/.../releases/latest
                  ├─ 解析 Location 正则（严格锚定本仓库）
                  └─ 不匹配 → 'Unexpected update redirect'
⑥ 全失败 → { release: null, error: '暂时无法检查更新' }
```

**为什么降级能绕过限流**
GitHub API 匿名访问限 60 次/小时（按 IP）。但**网页端点的 302 跳转不消耗 API 配额**。所以 API 被限流后，走网页仍能拿到最新 tag。

代价是需要解析 `Location` 头，且正则必须严格（`^https://github\.com/jackotom/hongguo-drama/releases/tag/(v?\d+\.\d+(?:\.\d+)?)$`），否则一个精心构造的跳转就能把用户引到钓鱼页。

**版本比较的归一化**
`4.8.0` 归一成 `4.8`，然后逐段数字比较。不用字符串比较 —— 否则 `4.10` 会小于 `4.9`。

**没做的事（明确记录，避免误以为有）**
- 不读 `X-RateLimit-*` 响应头
- 没有 429/403 专门分支
- 没有 `ETag` / `If-None-Match` 条件请求
- 结果不持久化（重启即重新请求）

限流实际由「降级到网页」规避，属**可用但非显式**的策略。

---

### F5 · `download-app-update` — 更新包下载与安装

**功能定位**
用 `electron-updater` 拉取 GitHub Releases 上的安装包，并执行安装。这一组是**唯一会修改应用自身**的接口。

**典型场景**
用户检查到新版本 → 点「下载」→ 进度条 → 点「重启安装」。

**输入参数**

| 方法 | 参数 | 说明 |
|---|---|---|
| `download()` | 无 | 版本取自 `latestAppRelease.version`（必须先调 F3） |
| `install()` | 无 | 重启并安装 |

**返回结果用途**
`{ success, state }`。`state.status ∈ idle/checking/downloading/downloaded/installing/error`，`percent` 驱动进度条。

进度经 IPC 事件 `app-update-state` 推送，**做了整数去抖**（只有百分比整数变化才发）—— 否则每秒几十条 IPC 消息会拖慢渲染进程。

**调用关系**
- 上游：IPC 4 个通道
- 下游：`electron-updater` 的 `autoUpdater` + 独立 `netSession`
- 依赖：F3 的结果

**关键开关及其原因**

| 开关 | 值 | 原因 |
|---|---|---|
| `autoDownload` | false | 不偷偷下载几百 MB |
| `autoInstallOnAppQuit` | false | 不在用户不知情时重启 |
| `allowDowngrade` | false | 防降级攻击 |
| `disableDifferentialDownload` | **true** | 公证后重打包导致旧 blockmap 失效，差分下载会失败 |
| `logger` | null | 不写日志（避免泄漏路径） |

**代理是这里的特例**
`download` 前会对 `appUpdater.netSession` 单独调 `applyProxyToSession`。因为 `electron-updater` 用的是**独立的 Session**，不继承主窗口的代理设置。

这也是为什么公告和更新**检查**（F1/F3 用主进程 axios）不遵循应用内代理，而更新**下载**却遵循 —— 前者根本没传 `proxy` 选项。

**版本漂移保护**
下载前比对 `release.version !== expectedVersion` → 「新版信息已变化，请重新检查更新」。防止用户在旧信息下下载到新版本（中间发布了新 release）。

**安装前的四类阻塞**
`installBlocker()` 会检查：进行中的写操作、下载/重试队列非空、合并或视频准备进行中、本地存储异常。任一命中就拒绝安装并说明原因。

**macOS 的特殊处理**
走 `nativeUpdater` 的 `update-downloaded` **一次性监听**（`once`），避免 MacUpdater 遗留监听导致重复触发。失败回落到 `error` 状态。

**支持范围**
预览版、Windows 便携版、非 darwin/win32、mac 运行在 `/Volumes/`（DMG 挂载）或 `/AppTranslocation/`（未移动到应用程序文件夹）→ 一律 `supported: false` 并给中文指引。

### F6 · `test-proxy` — 代理连通性自检

**功能定位**
用**未保存的代理草稿**实测能否出网。用户改完代理设置，点「测试」就能知道对不对，不用先保存。

**典型场景**
用户填了一个代理地址，不确定格式对不对、能不能通。

**输入参数**
代理配置草稿（不是已保存的设置）。

**返回结果用途**
`{ success, ... }`，前端据此显示「连接成功」或错误原因。

**调用关系**
- 上游：IPC `test-proxy`
- 下游：`GET https://www.baidu.com` —— 选百度是因为国内可达性最好，测的是「能不能出网」而非「目标站是否健康」

**易混点**
这是**全项目唯一显式传 `proxy` 选项的 axios 调用**。其他主进程请求（F1 公告、F3 更新检查）都不传，所以它们走系统/环境变量代理，不遵循应用内设置。这个不一致是已知问题（见 9.2）。

## 8. G 组详解：出站安全护栏

这两个不是「数据源」，是**所有出站请求的公共约束层**。它们不返回业务数据，但决定了哪些请求能发出去。

### G1 · `isPublicMediaUrl` — 公网地址静态校验

**功能定位**
纯字符串判断：这个 URL 是否指向一个公网可达的地址。**不发请求，不查 DNS**。

**典型场景**
每一个来自「外部输入」的 URL 都要过它：用户填的自定义源地址、MacCMS 返回的播放地址、官网 ld+json 里的 `contentUrl`、分享链接的每一跳。

**输入参数**
`value: string` —— 待校验的 URL。

**返回结果用途**
`boolean`。`false` 时调用方抛错或跳过该候选。

**调用关系**
- 上游：C7–C10、B3、B4、E1 —— 凡「URL 来自外部输入」都要过它
- 下游：无（不同任何库，纯字符串运算）
- 同层：G2（G1 是它的前置闸门，G2 是它的深度补充）

**六步校验**
1. 能被 `new URL()` 解析
2. 协议只能 `http:` / `https:`
3. 禁止 `username` / `password`（挡 `http://u:p@host`）
4. hostname 去 `[]`、去尾点、转小写
5. 是 IP 字面量 → 走 `isPublicAddress`
6. 是域名 → 必须含 `.`，且不得以 `localhost`/`.local`/`.internal`/`.lan`/`.home` 结尾

**拦截的网段**
- IPv4：`0/8`、`10/8`、`100.64/10`（CGNAT）、`127/8`、`169.254/16`、`172.16/12`、`192.0.0/24`、`192.0.2/24`、`192.168/16`、`198.18/15`、`198.51.100/24`、`203.0.113/24`、`224/3`
- IPv6：必须命中 `2000::/3`，排除 `::ffff:0:0/96`、`2001::/32`、`2001:db8::/32`、`2002::/16`

**它的局限（必须知道）**
只做静态判断，**域名解析到内网 IP 的情况它管不了**。`https://evil.com` 看着完全合法，但 DNS 指向 `192.168.1.1`。

这正是 G2 存在的原因 —— 静态校验是第一道闸，DNS 校验是第二道。

---

### G2 · `webMediaRequestOptions` — 请求选项护栏

**功能定位**
生成一套 Axios 请求选项，把**四类安全约束**注入到实际连接层：DNS 解析拦截、重定向逐跳校验、Agent 隔离、官方域名 Fake-IP 兜底。

**典型场景**
所有「目标 URL 不完全可信」的请求：自定义源、官网目录、HLS 分片、官网取流。

**输入参数**

| 参数 | 含义与作用 | 传错的后果 |
|---|---|---|
| `value` | 目标 URL。**静态校验不过直接抛 `ERR_WEB_MEDIA_ADDRESS`** | — |
| `options.trustedOfficialDns` | 默认 false。为 true 时启用 E3 的 DoH 兜底，且**仅允许 `https://hongguoduanju.com`** | 对非官网域名传 true → 抛错 |

**返回结果用途**
```
{
  maxRedirects: 5,
  httpAgent, httpsAgent,
  lookup(hostname, options, cb),          // DNS 校验钩子
  beforeRedirect(options, response, request) // 逐跳校验
}
```
直接 `{ ...webMediaRequestOptions(url), ... }` 展开进 axios 配置。

**调用关系**
- 上游：`custom-source`（每次请求）、`hls-media`（每个资源）、`catalog`、`hongguo`（官网取流）、`main.requestMedia`（**仅 web/custom**）
- 下游：E3（`trustedOfficialDns` 时）、`dns.lookup`
- 同层：G1（G1 在它内部被调用一次，做静态预筛）

**四个机制逐个说**

**① DNS 校验前置到 socket 解析**
`lookup` 钩子用 `dns.lookup(..., { all: true })` 取全部 A/AAAA 记录，任一为非公网地址就拒绝。

代码注释点明了关键：`a separate preflight permits rebinding` —— **只做请求前的预检会被 DNS 重绑定绕过**。攻击者让域名第一次解析到公网（通过预检），第二次解析到内网（实际连接）。把校验放进 `lookup`，检查的就是**真正要连接的地址**。

**② 重定向逐跳校验**
`maxRedirects: 5`，`beforeRedirect` 里用 `new URL(location, request.url)` 解析后重跑 `isPublicMediaUrl`，并把新 host 注册进 `hosts`，使该跳的 `lookup` 也受约束。

没有这一步，攻击者可以用一个公网 URL 302 跳到 `http://169.254.169.254/`（云元数据端点）。

**③ Agent 隔离**
`getName` 上追加 `:proxy` / `:direct`。防止代理建立的 socket 被直连请求复用 —— 混用会导致 DNS 校验被绕过（代理已经解析过了）。

**④ 官方域名 Fake-IP 兜底**
当本地解析全是 `198.18/15` 或 `198.19/16`（VPN 的 Fake-IP 段）时，对 `hongguoduanju.com` 改走 E3 的可信 DNS。`proxy: false` 强制直连，独立 Agent 防污染。

**⑤ 代理例外**
`lookup` 对非 `hosts` 命中的主机直接放行。注释解释：`their remote DNS remains a trust boundary` —— 走代理时 DNS 在代理侧解析，本地无从校验，只能信任代理。

**这个缺口值得单独强调**
|  |  |  |
| --- | --- | --- |
`main.requestMedia` 只对 `source === 'web' || 'custom'` 注入 G2。**河马和西饭的 mp4 直链不走护栏**，只有 `httpsUrl()` 的「必须 https、无 userinfo」静态校验。

如果上游被投毒返回 `https://10.0.0.1/x.mp4`：
- 静态校验：`https` ✓、无 userinfo ✓ → **放过**
- G2：会拦截 → **但没被调用**

HLS 路径反而安全，因为所有 HLS 都统一走 `remuxHls`，那里每个资源都过 G2。

### 9.2 故障定位速查

| 现象 | 先查 | 再看 | 切入点 |
|---|---|---|---|
| **搜索没结果** | A3 冷却是否生效（`appSearchCooldownUntil`） | B7 是否 4xx 触发 fallback；A6 是否被 30s 冷却跳过 | `searchAtSourcePage` 的顺序 |
| **搜索第 2 页重复** | 第 1 页返回的 `channel` 与 `cursor` 是否被保存 | 是否中途换了源 | `search-series-more` 的参数 |
| **分集列表为空** | B2 的两个 URL 是否都超时 | A10 是否 fail-closed 拒了响应 | `fetchEpisodeListFresh` 的错误合并文案 |
| **拿不到播放地址** | `quality` 是不是 `auto` | auto 才走三级降级；非 auto 直接走 A8 | `fetchPlayUrlSingle` |
| **高清下载全挂** | A8 是否 `EMPTY_RESPONSE` | A12 设备是否被标记异常（10s 冷却） | `fetchAppPlayUrl` 的重试分支 |
| **`200 + 0 字节`** | 签名是否漂移 | 设备是否需要续期 | A9 的 `EMPTY_RESPONSE` 不重试是刻意的 |
| **视频能播但要会员** | `locked` 语义 | 河马 `isCharge !== '0'` / 西饭 `unlock !== true` | 各源 `fetchPlayUrlSingle` |
| **播放黑屏有声** | `codec` 是否 HEVC | 设备是否支持 | `decode-capability` + `transcode-for-playback` |
| **下载文件残缺** | 206 校验是否通过 | CDN 是否返回了部分内容 | `requestMedia` 的 `content-range` 检查 |
| **弹幕一直空** | `DANMAKU_IDENTITY_IO` | 权限问题伪装成「没弹幕」 | `danmaku-client.json` |
| **弹幕部分缺失** | `partial: true` | 分页在第 N 页中断 | `PAGE_GAP_MS` / `MAX_EMPTY_PAGES` |
| **官网全挂但 App 能用** | 是否 VPN Fake-IP | E3 是否可用 | G2 的 `trustedOfficialDns` |
| **自定义源连不上** | G1 是否拦了 | 源站是否公网 | 「自定义源请求失败」的文案 |

### 9.3 新增数据源的检查清单

如果要去接入一个新的短剧源，按这个顺序做（每步都有对应的现有实现可参考）：

1. **定义 ID 前缀**：`{源名}:{...}`，写进 `resolveSeriesId` 的识别分支
2. **实现四个导出**：`browseList` / `search` / `fetchEpisodeList` / `fetchPlayUrlSingle`，签名参考 C1–C3（最规范的是 C4/C6，JSON 接口比 HTML 抓取稳定）
3. **在前缀分发处加分支**：`hongguo.fetchEpisodeList` 和 `fetchPlayUrlSingle` 各加一行 `if (startsWith)`
4. **在 `media-sources.js` 注册**：加入源列表，支持开关
5. **在 `main.js` 的 `browse-list` / `searchAtSourcePage` 加路由**
6. **决定是否过 G2**：如果是用户可配置的地址 → **必须过**；如果是固定域名 → 可选但建议
7. **确认 `locked` 语义**：这是最容易搞错的地方，三源已经三种写法
8. **确认 `format`**：是否可能返回 m3u8（是则要走 E2）
9. **确认清晰度**：第三方一般只支持 `auto`，`playbackQuality()` 会拒绝其他值
10. **错误文案**：绝不透传远端 message，收敛成固定中文

### 9.4 三条完整链路 walkthrough

**场景 1：用户粘贴分享链接，看第 3 集**

```
1. IPC hongguo-resolve("...分享文案...")
2. B4 resolveSeriesId
   ├─ 文本里有 series_id=8654321 → 本地直接返回，零网络
   └─ 只有短链 → 跟跳抓页面（每跳过 G1）
3. fetchEpisodeList("8654321")
   └─ 无前缀 → fetchEpisodeListFresh
      ├─ B2 官网：并发 /player/8654321 与 /detail?series_id=，1.5s 预算
      │   └─ 成功 → 解析 _ROUTER_DATA 得到 60 集
      └─ 若失败 → A10 App：multi_video_detail，fail-closed 校验
4. 用户点第 3 集 → prepare-online-play
5. fetchPlayUrlSingle("9876543", "8654321", { quality: 'auto' })
   ├─ 无前缀 → fetchPlayUrlFresh
   │  ├─ B3 官网：/player/8654321/9876543 → ld+json VideoObject
   │  │   └─ 七道校验全过 → { url, spadeA: null, source: 'web' }
   │  └─ 若失败 → A8 App（带 spade_a）→ A11 旧接口
6. requestMedia({ url, source: 'web' })
   └─ source==='web' → 注入 G2 → 取流 → 写入临时文件
7. 播放器通过 hongguo-stream 协议读本地文件
```

**场景 2：用户直接下载 1080P**

```
1. 下载任务 enqueue
2. fetchPlayUrlSingle(vid, sid, { quality: '1080p' })
   └─ quality !== 'auto' → 直接 A8，跳过 B3
      ├─ A12 确保设备已注册（否则先注册）
      ├─ 凭据签名（128 次分支收敛）
      └─ POST multi_video_model/v1
3. A8 内部过滤
   ├─ need_all_video_definition: true → 服务端给全部清晰度
   ├─ meetsDownloadQuality 过滤出 1080P 的 H.264/HEVC
   └─ 空 → QUALITY_UNAVAILABLE（不降级，除非 allowLowerQuality）
4. 返回 { url, contentKey, codec }
5. requestMedia → 取流（source==='app'，不走 G2）
6. contentKey 非空 → deriveKey → CENC-AES-CTR 解密
7. 写入 mp4
```

**注意第 2 步的分叉**：如果 A8 挂了（签名漂移），这条链路**没有任何降级** —— 用户会看到「本集取源失败（所选清晰度 1080p，未降级）：App：…」。而 auto 模式还能退到官网。这就是 9.5 节说的那个取舍。

**场景 3：用户添加自定义源并搜索**

```
1. 设置里填 name + url → IPC test-custom-source
2. C10 testCustomSource
   ├─ validateSource：G1 校验 url、pathname==='/' 自动补 /api.php/provide/vod/
   └─ request(draft=true) → 跳过 assertEnabled → 返回 count
3. 保存 → IPC save-custom-source
4. 搜索时切到该源 → search-series
5. searchAtSourcePage：source.startsWith('custom:') → C8 searchSeries
   ├─ 注意签名是 (keyword, { source, page })，page 在对象里
   └─ request()：G2 全量护栏 + 四次 check() 配置漂移检测
6. 结果里 series_id = custom:{uuid}:{vodId}
7. 点进详情 → fetchEpisodeList → 前缀分发 → C9
8. C9 detail：ac=detail&ids={vodId}
   ├─ 解析 vod_play_url 播放串
   ├─ 取集数最多的线路
   └─ 地址过 G1 + 必须以 .mp4/.m3u8 结尾
9. 播放 → C9 fetchPlayUrlSingle → 返回 { url, format, candidates }
10. format==='hls' → E2 remuxHls；'mp4' → E1 requestMedia
```

## 10. 附录：接口间最容易搞混的六组

维护时踩坑最多的地方，单独列出来。


**① `requestJson`(A1) vs `apiCall`(A9)**
都发 App 请求。A1 有域名白名单和重定向防护但无重试；A9 无白名单但有 3 次重试。**新代码用 A1**。

**② `fetchEpisodeListFresh` vs `fetchEpisodeListFromWeb`**
前者是编排器（web → app），后者只是 web 那一路。看到「这里没网络请求」的判断错，通常就是混淆了这两者。

**③ 三个 `signed*Request`（A2/A4/A7）**
长得一样但设备版本、主机、body 处理都不同。改一个必须改三个。

**④ 河马 vs 西饭的 `locked` 语义**
河马是黑名单式（`isCharge !== '0'` 算锁），西饭是白名单式（`unlock !== true` 算锁）。写反了会导致「免费剧显示锁定」或「付费剧能播」。

**⑤ `isPublicMediaUrl`(G1) vs `webMediaRequestOptions`(G2)**
G1 是静态字符串判断，G2 注入到连接层做 DNS 校验。**只调 G1 不等于安全** —— 域名可以解析到内网。

**⑥ `registerPlaybackDevice` vs `getPlaybackDevice`**
前者真发请求，后者带缓存。业务代码只应调后者，直接调前者会绕过单例和退避保护。
