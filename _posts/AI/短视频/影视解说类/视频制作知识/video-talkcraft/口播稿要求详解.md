# 口播稿要求详解（video-talkcraft ①）

> 面向初次使用者。SKILL.md 里「① 口播稿」只有三行，但真正的约束散落在 `timestamps_cpu.py`、`voice_trim.py`、`semantic_annotate.py`、`cinematography.md` 四处。  
> 本文把它们合到一处，每条都标**为什么**和**怎么验证**。
>
> 编写日期：2026-11-27 · 对应 skill 版本：2026-11-25 提交

---

## 0. 一句话结论

口播稿不是「文案」，是**机器对齐的输入 + 分镜的语义来源 + 素材的检索线索**三合一。它同时喂给三个环节，所以它的写法被三套机制约束：

```
        ┌─ timestamps_cpu.py ──→ 逐字锚定时间戳（数字写法、标点、字符）
口播稿 ─┼─ voice_trim.py ─────→ 判定哪些是口水词（稿子是唯一真值）
        └─ semantic_annotate.py ─→ 逐句语义标注（词法硬规 → FAIL）
                ↓
         cinematography.md ────→ 分镜切分依据（每句一个信息点）
```

**违反哪一条，坏在哪一环** —— 这是本文的核心。下面每条要求都写清后果。

## 1. 格式要求

### 1.1 支持的格式（三个脚本通用）

| 格式             | 写法                                | 谁在读                                  |
| -------------- | --------------------------------- | ------------------------------------ |
| `.json`        | `{"sentences": ["第一句。", "第二句。"]}` | 全部脚本                                 |
| `.json`        | `["第一句。", "第二句。"]`（纯数组）           | 全部脚本                                 |
| `.txt` / `.md` | **每行一句**                          | `voice_trim.py` / `tts_fishaudio.py` |

`.json` 的 sentence 也可以是对象，取其中的 `text` 字段：

```json
{"sentences": [{"text": "第一句。", "note": "可选备注"}]}
```

### 1.2 `.txt` / `.md` 的解析细节（`voice_trim.py:201`）

```python
return [ln.strip() for ln in raw.splitlines() if ln.strip() and not ln.lstrip().startswith("#")]
```

- **每行一句** —— 不是每段一句
- **空行跳过**
- **`#` 开头的行跳过** —— 这就是 `.md` 能用的原因（`# 标题` 当注释吃掉）

> ⚠️ **代价**：`.md` 里没法写 `#` 开头的口播句。中文口播稿很少这样开头，但知道有这条规则。

### 1.3 空句与非语音字符（`tts_fishaudio.py:57`）

```python
if not sentences or any(not normalized_text(s) for s in sentences):
    raise ValueError('Script must contain nonempty sentences with spoken characters')
```

`normalized_text` 只保留 `isalnum()` 的字符（去标点、去空格、NFKC 归一、casefold）。

**所以每一句都必须至少含一个实义字符**。纯标点的句子（`「」「」`）会直接报错。

## 2. 【硬性】数字一律写汉字

### 2.1 SKILL.md 的原话

> **数字一律汉字**（时间戳按文本逐字锚定，`197747` 无法与"十九万七千"的读音对位）；英文品牌词直接写（中英混合对齐已验证）

### 2.2 为什么 —— 看代码就明白

`timestamps_cpu.py` 的对齐逻辑是**逐字锚定**：稿子里的每个字要跟 ASR 出的每个字配对。

ASR 把"十九万七千"输出成什么？取决于后端：

| ASR 后端  | 听到"十九万七千"会输出               |
| ------- | -------------------------- |
| FireRed | `十九万七千`（汉字，干净）             |
| whisper | `197747` 或 `19万7千`（转阿拉伯数字） |

而你的稿子如果写 `197747`，那么：

```
稿子：  1 9 7 7 4 7     ← 6 个拉丁 token
ASR：   十九万七千        ← 4 个 CJK token
```

**字符数都对不上**，这一句的锚点全部失配 → `match` 暴跌 → 动效挂不上字。

### 2.3 但代码其实做了双向兜底

`timestamps_cpu.py:69` 有一条注释：

```python
# ASR 会把汉字数字转写成阿拉伯数字（"十四天"→"14天"）——逐位映射回汉字当对齐锚
DIGIT2CN = str.maketrans("0123456789", "零一二三四五六七八九")
```

以及 `num2cn()` 把阿拉伯数字串转回中文读法（`14`→`十四`、`7000`→`七千`）。

**意思是**：即使 ASR 输出阿拉伯数字，脚本也会转回汉字再对齐。所以「稿子写汉字」这个要求，**兜底机制覆盖了一部分**。

### 2.4 那为什么还要坚持写汉字？

看 `num2cn()` 的限制：

```python
def num2cn(s: str) -> str:
    """阿拉伯数字串 → 中文读法（≤8 位；'14'→'十四'、'7000'→'七千'），锚点匹配用。"""
    if not s.isdigit() or len(s) > 8 or int(s) == 0:
        return s.translate(DIGIT2CN)
```

| 情况                       | 兜底是否有效                           |
| ------------------------ | -------------------------------- |
| 4 位以内（`2024`）            | ✅ 转成标准中文读法                       |
| 5–8 位（`197747`）          | ✅ 转成「十九万七千」                      |
| **超过 8 位**（`1234567890`） | ❌ 退化成逐位映射 `一二三四五六七八九零`，与实际读法完全不符 |
| **含小数**（`3.5`）           | ❌ `isdigit()` 为 False，整串走逐位映射    |
| **带单位符号**（`50%`、`3x`）    | ⚠️ 部分有效                          |
| **`0`**                  | ❌ 特判返回 `零`（读法确实是"零"，但边界情况多）      |

**结论**：≤8 位的纯整数，代码兜底能救；**超长数字、小数、百分号混排是重灾区**。

而且兜底是「事后修正」，正写汉字是「事前对齐」—— 正写时 `match` 更干净，`ok=false` 的句子更少。

### 2.5 写法对照

| ❌ 别这么写          | ✅ 这样写                       |
| --------------- | --------------------------- |
| `197747`        | `十九万七千`                     |
| `3.5%`          | `百分之三点五`                    |
| `$2000`         | `两千美元`                      |
| `24小时`          | `二十四小时`                     |
| `2024年`         | `二零二四年`（或 `2024年`，4 位数兜底可靠） |
| `iPhone 15 Pro` | `iPhone 15 Pro` ← **例外，见下** |

### 2.6 例外：英文品牌词直接写

SKILL.md 明确说「英文品牌词直接写（中英混合对齐已验证）」。

**为什么英文不用管**：拉丁词在 `timestamps_cpu.py` 里是**整段 token**，不做逐字锚定：

```python
LATIN = re.compile(r"[A-Za-z0-9]")
# words = CJK 逐字 token + 拉丁/数字整段 token（标点跳过）
```

各 ASR 都常拼错拉丁词（「插件」→「差见」），所以代码对拉丁词的处理是「**锚点间线性插值**」—— 不追求精确，容忍度高。

**结论**：中文数字要严格，英文品牌词放宽。`iPhone`、`Claude Code`、`Remotion` 直接写。

> ⚠️ 但注意：**英文里的数字仍然是数字**。`iPhone 15` 里那个 `15`，如果发音是"十五"，稿子写 `15` 就有风险。保守做法：`iPhone 十五` 或 `iPhone 15 Pro`（15 是两位数，兜底可靠）。

## 3. 【硬性】一句一个信息点

### 3.1 原话

> 每句一个信息点，钩子在第一句（数字/冲突）；13 句 ≈ 95s

### 3.2 这条约束的是分镜，不是朗读

`cinematography.md` §4.5 排版预算第 1 条：

> **分镜按语义段落切**，禁止机械一句一镜；每镜只许一个 primary visual job（钩子/定义/数据/流程/对比/结论/CTA 之一）。

### 3.3 「一句一个信息点」的真实含义

**不是**「一句只能有一个名词」，**不是**「一句不能有两句话」。

含义是：**一句只承担一个 primary visual job（画面任务）**。

| ✅ 合格               | ❌ 不合格                          | 为什么                                           |
| ------------------ | ------------------------------ | --------------------------------------------- |
| `每月定投三千，一年下来是三万六。` | `每月定投三千，一年下来是三万六，年化收益超过百分之十二。` | 后者塞了「定投额 + 累计 + 收益率」三个数据，画面要同时放三个数字 → 同屏主体超预算 |
| `他三年前开始做这件事。`      | `他三年前开始做这件事，现在已经有了十二万粉丝。`      | 后者要同时给「时间轴 + 粉丝数」两个视觉任务                       |
| `但这次不是X。`          | `但这次不是X，其实是Y，而且Y还更便宜。`         | 转折 + 揭示 + 数据挤一句                               |

### 3.4 违反的具体后果

**后果一：同屏预算爆**

`cinematography.md` §4.5 第 3 条：

> **同屏预算**：任一时刻主体组 ≤3（字幕/常驻件不计；**降权留守的元素计入**）；第 4 组进场前必须有一组真退场。

一句塞三个信息点 → 一镜要放三个主体 → 要么超预算，要么挤成一团。

**后果二：hero 造型打架**

> **hero 造型一屏一个**：多个数字/大字同屏时只有一个享受 hero 档造型（大字号/色块/换色），其余降行内注——三个数字三种 hero 造型互相抢戏读作凌乱。

**后果三：画面文字和字幕重复**

> **画面文字不照抄字幕**：画面文字是 ≤12 字的提炼，不是口播誊写；与字幕整句重复 = 同一信息双份同屏。

**后果四：审片被判凌乱**

`review-protocol.md` 的 rubric 按「可读性 / 构图 / 信息传达 / 质感 / 事实一致 + 保真 / 词落点」出缺陷清单。「信息传达」这条直接吃这一项。

### 3.5 怎么验证

写完稿子，逐句问自己三个问题：

1. 这一句念完，画面上**主要在讲什么**？（答不上来 = 一句多事）
2. 这一句对应**哪个卡 / 哪张素材**？（答不上来 = 该拆或该配素材）
3. 画面文字能压到 **≤12 字**的提炼吗？（压不下去 = 这句信息量太大）

## 4. 【硬性】钩子在第一句

### 4.1 原话与语义标注的联动

`semantic_annotate.py` 的语义词表里，**「钩子」是第一个语义**：

```python
("钩子", "开场抓注意力的问题 / 反差 / 大数字"),
```

而 `cinematography.md` §4.5 第 2 条：

> **枢轴句归下一镜**："但这次不是X"式转折/否定/设问是下一镜的**第一拍**——切镜点提前到枢轴句起点，旧镜先清场，开题动效（strike-and-replace/设问框）上干净的舞台，不叠在旧话题的满画面上。

### 4.2 「钩子」在词表里的定义

> 开场抓注意力的问题 / 反差 / 大数字

三种典型形态：

| 形态      | 例句             | 对应卡                                                           |
| ------- | -------------- | ------------------------------------------------------------- |
| **大数字** | `十九万七千。`       | `count-badge-title` / `number-slab-pop` / `impact-open-title` |
| **反差**  | `三千家门店，九年关店。`  | `behind-text-title` / `slow-pull-reveal`                      |
| **问题**  | `你有没有想过，为什么……` | `title-demote-to-label`（设问）                                   |

### 4.3 词的提示与软规

`semantic_annotate.py` 的软规里：

```python
({"设问", "钩子"}, re.compile(r"[?？]\s*$|吗\s*[?？]?\s*$|呢\s*[?？]?\s*$")),
```

**句末问号 → 设问或钩子**。

注意：这个正则只认**句末**的问号。句中的问号不触发。

### 4.4 为什么第一句必须是钩子

三重原因：

1. **视觉上**：第一镜是「样板镜」的默认候选（`G0 写一行「样板镜：sNN」`（默认 s01））。第一镜要在几秒内建立视觉语言，第一句是钩子 → 第一镜是重音镜 → 样板镜有代表性。
2. **语义上**：钩子句通常是 `main` 权重（允许进新元素）。`weight=main` 的句是新元素的挂点，第一镜得有一个。
3. **验收上**：**开镜不空台**——

> 镜头开场到第一个动效锚点 >1.5s 的空窗必须有承载画面（真实 b-roll / 上一镜元素延续 / 真素材墙），不许空画布干等词锚。

第一句是钩子 → 词锚来得早 → 空窗短 → 过了这道闸。

### 4.5 反面：钩子放中间

`semantic_annotate.py` 的文档注释记了一个真实的翻车：

> 「我是万里」被当成又一个论点关键词，配了全库能量最低的文字卡（soft-blur-in），库里 P0 级的 `lower-third-nameplate`（人名条）就在货架上、它的「适用」行明写「也用于自我介绍」，却没人在那一刻查到它。

**三位独立评审都判这一镜无缺陷** —— 因为评审 rubric 只核「摆上去的东西对不对」，不核「该摆的东西在不在」。

这就是为什么 ②-1 语义标注是必做环节：**它把「这句在做什么」变成机器可读的东西**，让选卡漏斗多一道过滤。

## 5. 【硬性】事实红线清单

### 5.1 原话

> 先调研核实事实，列"事实红线清单"（不可说错的数字/未验证数据不引用）

### 5.2 这是唯一一条 SKILL.md 说了但没给实现的

我全仓搜过：**「事实红线清单」只在 SKILL.md 出现一次**，没有对应脚本、模板或 reference。

所以**这条要靠人自己执行**。它是这份文档里唯一需要你自己建立工作习惯的地方。

### 5.3 为什么它是硬性

三重机制在盯着它：

**机制一：审片的 P0 定义**

`review-protocol.md`：

> **P0** = 观众必然察觉且伤害理解——事实 / 文字 / 字形错误、不可读、声画错位、元素相撞遮正文、标注指错目标。

**「事实错误」是 P0**，不是 P1。P0 必须修完才交付。

**机制二：素材端的硬性绑定**

`SKILL.md` ③：

> **调研记账**：承载关键事实的来源页逐一截图存档，`sources.md` 里链接与本地截图一一对应（禁止只存链接不留证据）；成片引用时优先用存档截图当画面证据 + micro 阶来源行

**机制三：真图硬规**

> 话题存在可截的真实页面（产品官网/GitHub/文档/画廊）时，成片中的浏览器/页面类镜头**禁止用代码 mock 冒充截图**

也就是说 —— 你口播里说的数字，画面上就该有那张截图撑着。

### 5.4 「事实红线清单」怎么建

建议在写稿前先列一张表：

| 稿件中的说法 | 来源          | 截图存档路径                         | 能不能说错    |
| ------ | ----------- | ------------------------------ | -------- |
| 十九万七千  | 某财报 2025 Q3 | `public/pages/earnings-q3.png` | ❌ 不能     |
| 百分之十二  | 同上          | 同上                             | ❌ 不能     |
| 行业平均   | 未找到出处       | —                              | ⚠️ 改口径或删 |

**规则**：

- **红线** = 出了事要负责的数字（金额、比例、增长率、排名、时间）。写进稿子之前必须有一张截图。
- **灰线** = 未验证但影响不大（"很多人"、"大部分"）。**改成不绝对的说法**，或直接删。
- **不写** = 没查到出处的具体数字。宁可不说。

### 5.5 与 `sources.md` 的联动

`preflight.py --media-only` 会查 `sources.md` 是否存在（不在 → FAIL）。

所以事实核实的产物不只是稿子，还包括：

```
public/pages/xxx.png     ← 截图存档
sources.md               ← 链接与截图一一对应
```

### 5.6 审片时怎么查

审片 rubric 里的「**事实一致**」这一项，评审要看的是：

- 画面上的数字 == 口播里的数字 == 截图里的数字
- 标注指的目标 == 口播说的那个目标

## 6. 【硬性】标点与字符规范化

这一条 SKILL.md 没写，但代码里有明确规则。

### 6.1 规范化链条（`timestamps_cpu.py:97`）

```python
def norm_char(ch: str) -> str:
    """半角化 + 小写 + 繁→简 + 数字归一到汉字；返回 '' 表示不参与对齐（标点/空白）。"""
    ch = unicodedata.normalize("NFKC", ch).lower()
    ...
    ch = t2s(ch).translate(DIGIT2CN)
    if CJK.match(ch) or LATIN.match(ch):
        return ch
    return ""
```

**参与对齐的字符**：CJK（`[一-鿿㐀-䶿]`）+ 拉丁字母数字（`[A-Za-z0-9]`）

**不参与对齐的**：所有标点、空白 → 归一为 `''` → 跳过

### 6.2 实际影响

| 你写的                         | 归一后      | 参与锚定        |
| --------------------------- | -------- | ----------- |
| `，` `。` `、` `！` `？` `；` `：` | `''`     | ❌           |
| `「」` `『』` `《》` `（）`         | `''`     | ❌           |
| `""` `''` `——` `…`          | `''`     | ❌           |
| 全角 `Ａ` `１`                  | `a` `1`  | ✅           |
| 繁体 `會話`                     | `会话`     | ✅           |
| 英文 `Claude`                 | `claude` | ✅（整段 token） |

### 6.3 标点零时长

`make_timing.py` 的 `expand_chars()` 明确：

> Punctuation (including either apostrophe style) has zero duration.

**标点在 timing.json 里占位但时长为 0**。这意味着：

- 标点位置不会产生"空档"，动效锚点可以落在标点上
- 标点不影响对齐

**但标点仍然影响朗读节奏** → 影响预剪的停顿检测 → 影响 ASR 的分句点。

### 6.4 标点的实际建议

| 位置  | 建议            | 原因                           |
| --- | ------------- | ---------------------------- |
| 句末  | 用 `。` `！` `？` | 软规认句末问号 → 设问/钩子              |
| 句中  | 少用长破折号        | `——` 会让 ASR 断句异常             |
| 括号  | 尽量不用          | 括号内容往往不朗读，但稿子写了 = 对齐时多出待匹配字符 |
| 省略号 | 慎用            | `……` 会被规范化为空，但朗读时的停顿是真实的     |

**括号那个坑值得展开**：如果你写 `这个方法（我亲测有效）`，而配音只念了「这个方法我亲测有效」——括号里的字在稿子里但不在音频里 → 那些字符对不上 → 影响 `match`。

**规则**：**稿子 = 会被念出来的字的序列**。不念的东西别写进去。

### 6.5 繁体

繁体在 `norm_char` 里会被 `zhconv` 转简体。所以**写繁体不会导致失败**，但：

- whisper 随机吐繁体是常态 → 有 `zhconv` 兜底，锚点不会大面积丢
- 缺 `zhconv` 时（`ImportError` 分支）繁体段落锚点变少

**结论**：写简体，简体是基准。

## 7. 【硬性】与配音逐字一致

### 7.1 原话（②-0）

> **稿子是真值，宁漏勿错**：只剪 ASR 里**稿子没有的插入段**——全由口水词表拼成的（filler）、等于紧邻稿文的结巴 / 重说（repeat）；ASR 听错稿子里的字永不剪（剪它就剪掉了那个字的真实发音）；稿外改了措辞的重说只报告，`--cut-unmatched` 才剪。

### 7.2 稿子为什么是真值

`voice_trim.py:264` 的 `detect_with_script()` 用 `difflib.SequenceMatcher` 对齐「稿子字符」与「ASR 字符」，然后按 opcode 分三类处理：

| opcode    | 含义              | 处理                             |
| --------- | --------------- | ------------------------------ |
| `equal`   | 一致              | 跳过                             |
| `replace` | **ASR 听错稿子里的字** | **只报告，不剪**（`kind: "mismatch"`） |
| `insert`  | 稿子里没有的多说段       | 判定是否 filler / repeat → 可剪      |

**`replace` 不剪**是硬设计：

> 剪它就剪掉了那个字的真实发音

举例：稿子写「插件」，ASR 听成「差见」。如果按 ASR 剪，就等于告诉剪辑器「把这段真实发音的『插件』删掉」—— 结果成片里那个字消失了。

**所以稿子必须准确** —— 稿子错一个字，那一声的音频就会被当成「多余的」。

### 7.3 三种不一致的后果

| 情况                  | 后果                                                                      |
| ------------------- | ----------------------------------------------------------------------- |
| **稿子有、配音没有**        | 该段被当 `insert`，若不在口水词表内则**只报告不剪**（默认）。但 `match` 掉分 → 标 `ok=false` → 人工听核 |
| **配音有、稿子没有**（口误、多说） | 被判 `insert` → 若全由口水词组成 → **剪掉**（这是预期的）                                  |
| **稿子和配音都错**         | 无法自动发现。靠人工核对                                                            |

### 7.4 怎么验证

```bash
# 预剪 dry-run，看报告
python3 scripts/voice_trim.py audio/raw.wav script.json --dry-run --words-out audio/asr_words.json
```

报告里会列出：

- `filler` —— 口水词（可剪）
- `repeat` —— 结巴重说（可剪）
- `mismatch` —— **ASR 听错稿子里的字（不剪，但要查）**

**`mismatch` 条目是最有价值的**：它直接告诉你「音频里这一处和稿子不一致」，你去听一遍就能发现稿子写错了还是音频念错了。

### 7.5 无稿时的降级

```python
# 无稿时只剪**整 token 文字恰为**保守词表（嗯 / 呃 / 额 / um…）的口水词
# ——按规范化文字精确比对、不认同音（五≠唔、饿≠呃）
```


注意「不认同音」：五 ≠ 唔，饿 ≠ 呃。宁可漏剪不可错剪。

**所以强烈建议始终带稿子。**

## 8. 稿子的下游用途（为什么值得多花时间）

写稿不是只为朗读。稿子同时是：

### 8.1 素材检索词（`entities`）

```json
{"entities": ["三千家门店", "九年", "某品牌"], "need": ["量化", "证据"]}
```

`SKILL.md` ③：

> **素材清单从 ②-1 的语义标注生成，不靠拍脑袋**：`need` 是 `证据` 的句去截真页 / 找出处，`身份` 要头像与账号信息，`量化` 要图表或数据源，`entities` 里的人名 / 品牌 / 地点 / URL 就是检索词。

**稿子里写清楚实体，素材采集就自动有方向。** 写得含糊（"很多商家"），素材清单就是空的。

### 8.2 选卡候选（`sem`）

```json
{"sem": ["钩子", "数据"], "weight": "main"}
```

`card_match.py` 用 `sem` × 素材行 × 卡索引出候选表。

**26 词封闭词表**（`cards_index.py` 的 `VOCAB`，唯一来源）：

| # | 语义 | # | 语义 | # | 语义 |
|---|---|---|---|---|---|
| 1 | 钩子 | 10 | 设问 | 19 | 机制 |
| 2 | 论点 | 11 | 金句 | 20 | 选择 |
| 3 | 例证 | 12 | 标题 | 21 | 过程演示 |
| 4 | 数据 | 13 | 引用 | 22 | 章节 |
| 5 | 对比 | 14 | 自我介绍 | 23 | 转场 |
| 6 | 列举 | 15 | 介绍他人 | 24 | 强调 |
| 7 | 定义 | 16 | 号召 | 25 | 氛围 |
| 8 | 步骤 | 17 | 时间地点 | 26 | 结尾 |
| 9 | 转折 | 18 | 空间叙事 | | |

**词表封闭** = 不在表内的词会被 `semantic_annotate.py --stats` 判 FAIL。

### 8.3 分镜边界

`semantic_annotate.py --sync-shots` 按 SHOTBOOK 标题的起止秒回填每句归属哪一镜。

**漏了这一步** → `card_match` 每镜都是「无 main 句」→ `preflight` 的语义覆盖整段空转 → 直接 FAIL。

### 8.4 字幕（`Subtitles` 组件）

`template/components/components.tsx` 的字幕轨是 **whole-clause hard cut**（整句硬切），由 `timing.json` 的字符级时间戳驱动。

## 9. 自检清单

写完稿子，逐条过：

### 9.1 格式

- [ ] 文件是 `.json`（`{"sentences": [...]}`）或每行一句的 `.txt`
- [ ] 每句至少含一个实义字符（不是纯标点）
- [ ] 句末标点规范（`。` `！` `？`）

### 9.2 数字

- [ ] **所有中文数字写成汉字**（`十九万七千` 不是 `197747`）
- [ ] 超 8 位数字、小数、百分号混排**全部汉字化**（`百分之三点五` 不是 `3.5%`）
- [ ] 英文品牌词直接写（`Claude Code`、`Remotion`）
- [ ] 英文里的两位数以内数字可以保留（`iPhone 15`），三位以上建议汉字化

### 9.3 结构

- [ ] 每句一个 primary visual job（能回答「这镜主要在讲什么」）
- [ ] 第一句是钩子（大数字 / 反差 / 问题）
- [ ] 句长适中（能一口念完、不需要换气）
- [ ] 括号里的补充说明**不写进去**（不念的东西别写）

### 9.4 事实

- [ ] 列了事实红线清单
- [ ] 每个红线数字有来源 + 截图存档路径
- [ ] 未验证的数字已改口径或删除
- [ ] `sources.md` 计划好（每条来源一行，对应本地截图）

### 9.5 与配音

- [ ] 稿子 = 会念出来的字（不多不少）
- [ ] 计划做 `voice_trim.py --dry-run`，检查 `mismatch` 条目
- [ ] 计划做 `semantic_annotate.py --stats`，看 `论点` 占比不过半

### 9.6 长度

- [ ] 初次做片：**90–120 秒 / 12–16 句**（SKILL.md 参考值 13 句 ≈ 95s）
- [ ] 超过 193 秒要意识到 FireRed ASR 会分 75s 段（不影响质量，但要预分段）

## 10. 常见问题

| 症状 | 根因 | 处理 |
|---|---|---|
| 某句 `match` < 0.9 | 数字写成阿拉伯 / 稿子与配音不一致 / 长句含多信息点 | 看 `timestamps.json` 的 `words`，对比 `text` 找断点 |
| 整段 `match` 暴跌 | 缺 `zhconv` 或 `pypinyin` | 装上重跑 |
| `voice_trim` 报告大量 `mismatch` | 稿子和配音对不上 | **去听**。改稿子（改配音）或改稿（真值是稿子） |
| `semantic_annotate --stats` 报 FAIL | 词法硬规触发（如「数量词 → 数据」没标 `数据`） | 补 `sem`；真不该标就加 `exempt`（理由 ≥4 字） |
| `--stats` 报 `论点` 占比超半 | 什么都标成论点 | 论点是兜底档，把具体的挑出来 |
| `preflight` 报「每镜无 main 句」 | 漏跑 `--sync-shots` | 跑 `semantic_annotate.py --sync-shots` |
| 首镜被评审判「视觉平淡」 | 第一句不是钩子 | 第一镜重写，钩子句提上来 |
| 画面文字和字幕重复 | 画面文字照抄了口播句 | 压成 ≤12 字的提炼 |
| 审片报 P0「事实错误」 | 数字没有核实 | 回事实红线清单，逐条对截图 |

## 11. 一份合格的稿子长什么样

对照检查（示例，非模板）：

```json
{"sentences": [
  "三千家门店，九年关店。",
  "这不是经营不善，是租金。",
  "月租从每平两元涨到四十元。",
  "每卖一件衣服，倒贴七块。",
  "二〇二四年，行业倒了四成。",
  "所以问题从来不是需求。",
  "是位置。",
  "第一批关店的，租金最高。",
  "第二年才轮到期租低的。",
  "位置差的那批，反而撑到了最后。",
  "我把三百家的数据拆开看了。",
  "存活率，和地段高度相关。",
  "不是百分之多少的问题。",
  "是差几倍的问题。",
  "这就是我说的结构性风险。",
  "关注我，下一条讲怎么找对位置。"
]}
```

对照 26 词语义标注，会是这样：

| 句 | sem | weight | need |
|---|---|---|---|
| 三千家门店，九年关店。 | 钩子、数据 | main | 量化 |
| 这不是经营不善，是租金。 | 转折 | main | 对比 |
| 月租从每平两元涨到四十元。 | 数据、对比 | main | 量化 |
| 二〇二四年，行业倒了四成。 | 数据 | sub | 量化 |
| 问题从来不是需求。 | 转折 | main | 强调 |
| 是位置。 | 金句 | main | 强调 |
| 存活率，和地段高度相关。 | 论点 | main | 量化 |
| 关注我，下一条讲怎么找对位置。 | 号召 | main | 无 |

**16 句，约 105 秒。** 数字全汉字、钩子在第一句、每句一个信息点、CTA 在最后。
