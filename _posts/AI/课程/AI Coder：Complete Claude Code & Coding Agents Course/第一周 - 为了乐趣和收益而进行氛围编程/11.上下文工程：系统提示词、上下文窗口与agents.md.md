### 上下文窗口
[06:41]
There is, of course, this idea of a context window, which is to say that an LLM has a limit to how many tokens can be fit in this context before it runs out of room. Because an LLM is designed to be able to look back over a number of different tokens as it’s forming its predicted next tokens, and each LLM can only look back so far—they’re only large enough to look back a certain amount of tokens. And if you try and pass in more tokens than its maximum context window, it will fail. That is considered a failure. It can’t handle it, and it will be an error.

It’s the maximum number of tokens that it can examine in its input in order to predict the next tokens. That’s sometimes just called the `context window` or the `context window limit`—it is the maximum size of this context that’s passed in. And so it needs to fit within this context window. And that’s something which many of us agonize over constantly. People obsess over this context limit—the fact that you can’t go over. But in fact, it’s worth keeping in mind that in a lot of cases, just having too much in the context, even if you’re not yet at the limit, can still cause performance to degrade.

And I’m using performance there not in the speed sense—not performance like we sometimes hear people say—I’m talking about the accuracy, the quality of the results. That kind of performance can start to degrade. You get poorer results, you start to lose coherence. It starts to forget things as you fill up the context more and more. So even if you’re not yet at the limit—even if you haven’t filled up the context window—you might start to see degrading performance if you’re shoving too much into the context. And conversely, you tend to get the best performance at the very start of your conversation when the context is super empty and it’s only got a little bit to pay attention to. So that’s something to be very cognizant of.

#### 压缩
It’s not just a binary: have you got too much? It fails. There’s also a sense of “less is more” when it comes to filling up the context, okay?

Now, I’ve been saying that the LLM fails when the context window gets filled up. And you’re probably thinking, “Well, I don’t think it fails—I think it does compacting.” You’ve probably experienced compacting before. That’s actually a feature built into things like Claude Code, which is that rather than allowing it to fail, it detects when the context window is almost filled up, and it runs this process that essentially looks back at the whole conversation history, summarizes it, and replaces everything with a little summary of what was there before—freeing up lots of space in the context history—in the conversation history. And this is something which is very common, and it’s also something which is feared by people like you and me a lot, because it changes the game suddenly.

The challenge with compacting is that we are trusting the LLM to do a good job of figuring out what’s important and what’s not important from the conversation history. And often it does a good job, but sometimes it doesn’t. Sometimes it misses an important thing that we care a lot about—something we told it about during the conversation—that gets removed when it’s summarizing. As a result, the LLM appears to forget something that we’ve told it, or it makes the same mistake twice, which is super frustrating. And because of this, people have tended to fear the compactor. They don’t like it when it compacts. And often you’ll find that people—and I do this a lot myself—rather than let it compact, I will look at what’s happened before. I will stop the agent, and then I will rewrite my file like AGENTS.md that I mentioned before, and then start it up again fresh, making sure that I’ve kept careful note of everything that’s happened that it needs to know about. So people do tend to fear the compacting process and like to stop it, refresh it, and rewrite it.

这不仅仅是二元的：你是不是放太多了？它会失败。在填充上下文方面还有一种“少即是多”的感觉，好吗？

现在，我一直在说当上下文窗口被填满时， LLM 会失败。你可能会想，“嗯，我不认为它会失败——我认为它会进行`压缩`。”你以前可能经历过压缩。*这实际上是内置于 Claude Code 等东西里的一个特性，即它不会允许失败，而是检测到上下文窗口几乎被填满时，运行一个过程*，基本上**回顾整个对话历史，对其进行总结，并用之前内容的简短摘要替换所有内容——释放上下文历史中——对话历史中的大量空间**。这是非常常见的，也是像你我这样的人非常害怕的，因为它会突然改变游戏。

压缩的挑战在于，我们信任 LLM 能够很好地从对话历史中找出什么重要、什么不重要。它经常做得很好，但有时不行。有时它会漏掉我们非常关心的一个重要事项——我们在对话中告诉过它的某件事——在总结时被删掉了。结果，LLM 似乎忘记了我们告诉过它的事情，或者它犯了同样的错误两次，这超级令人沮丧。正因为如此，人们往往害怕压缩器。他们不喜欢它压缩的时候。你经常会发现人们——我自己也经常这样做——不是让它压缩，而是会回顾之前发生的事情。我会停止智能体，然后重写我之前提到的像 AGENTS.md 这样的文件，然后重新开始，确保我仔细记下了所有它需要知道的事情。所以人们确实倾向于害怕压缩过程，喜欢停止它、刷新它并重写它。
