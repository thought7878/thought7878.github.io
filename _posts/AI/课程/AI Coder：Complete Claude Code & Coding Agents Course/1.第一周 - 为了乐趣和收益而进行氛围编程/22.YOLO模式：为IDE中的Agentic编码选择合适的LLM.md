# 总结
这段内容主要回顾了前一天体验的四款 AI 编码工具及其底层模型，并给出了*选择模型和 YOLO 模式的实用建议*。

1. 今日安排  
- 第 1 周第 4 天，项目日，将选择一款工具在 YOLO 模式下完成实际项目。

2. 工具回顾与区别  
- **Cursor**：由 Anysphere 公司开发，是 VS Code 的一个 fork（分支版本），界面类似但独立。  
- **GitHub Copilot**：作为 VS Code 的扩展插件使用，不是 fork，而是给原版 VS Code 添加 Copilot 功能。  
- **Codex**：同样以 VS Code 扩展形式使用，但更常见的用法是命令行 CLI（下周会深入学习）。  
- **Antigravity**：Google 出品的 IDE，也是 VS Code 的 fork，独立应用。

3. 底层模型回顾  
- **Composer**：Cursor 内部使用的专有模型，属于“快速前沿”类别，速度快、成本低，上下文约 20 万。  
- **Claude Haiku 4.5**：Anthropic 最快的模型，可能被 Copilot 自动选用，上下文约 20 万，性能略强于 Composer。  
- **GPT-5.2 Codex**：Codex 使用的特殊版本，专门为代码生成优化，上下文 27.2 万，是最强模型之一。  
- **Gemini 3 Pro**：Google 的顶级模型，上下文窗口高达 100 万，虽然单项能力可能略逊于 GPT-5.2 Codex，但长上下文带来额外优势。

**4. 选模型的经验法则**  
- **优先选聪明的模型，而不是快的模型**：耐心等待高质量结果，比反复修复快速但错误的输出更高效。  
- **设定预算，并选预算内最强的模型**：使用便宜模型往往因额外迭代和时间浪费反而花费更多。  
- **小模型需要更详细的提示和更多监督**：如果使用免费或开源小模型，*要像写详细规格说明书一样给出指令，并加强过程管理*。  
- **YOLO 模式只适合顶级模型**：GPT-5.2 Codex、Gemini 3 Pro、Claude Opus 4.5 等前沿模型可以放心 YOLO；快速或低端模型建议*逐步执行、逐步审批*，避免最后得到一堆无意义输出。
