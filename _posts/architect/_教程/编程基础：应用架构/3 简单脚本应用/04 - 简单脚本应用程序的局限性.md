# 原文
Simple script applications, like for one we just saw, are excellent starting points for learning programming concepts. They're easy to write and execute, making them perfect for beginners. However, simple scripts come with several limitations that can become significant as your needs grow or applications become more complex. Let's dive into some of these limitations to understand when this type of application might no longer be the best choice. 

像我们刚才看到的那样简单的脚本程序，是学习编程概念的绝佳入门起点。它们易于编写和运行，非常适合初学者。然而，简单的脚本存在诸多局限性，随着需求的增加或应用变得愈加复杂，这些局限性可能会愈发突出。让我们深入探讨其中的一些局限性，以弄清在哪些情况下这类应用可能已不再是最佳选择。

Simple scripts are designed for small, specific tasks. As soon as the scope of the project grows, such as needing to handle more users or larger data sets, or more complex workflows, a single script quickly becomes inadequate. Scaling a script to meet these demands typically requires refactoring the code into a more modular, organized structure, often evolving into a multi-file or even module application without clear separation of concerns like the user interface. From the business logic, it's challenging to repurpose code for different applications or extend functionality without significant rewriting. This lack of organization can lead to spaghetti code, where the logic becomes tangled and difficult to follow, increasing the chances of introducing errors. 

简单的脚本旨在完成小型的特定任务。一旦项目规模扩大，例如需要支持更多用户、处理更大规模的数据集，或应对更复杂的业务流程，单个脚本便很快显得力不从心。*为满足这些需求而对脚本进行扩展时，通常需要将代码重构为更加模块化、结构化的形式，进而演变为一个多文件的多模块的应用程序*，但其中往往缺乏对用户界面等关注点的清晰分离。从业务逻辑层面来看，在不进行大量重写的情况下，很难将代码复用于不同应用或扩展其功能。*这种缺乏组织性会导致“意大利面式代码”，使程序逻辑变得错综复杂、难以理解，从而增加引入错误的风险*。

Everything in a simple script is often tightly coupled, which makes testing a challenge. Unit testing ensures independent components work together as expected, and it's harder to implement this effectively in a single monolithic script. Without proper testing, it's difficult to verify the reliability of the application as it grows or changes. 

*简单脚本中的所有内容往往高度耦合，这使得测试变得颇具挑战*。单元测试能够确保各个独立的组件按预期协同工作，而在单一的大型脚本中，要有效地实现这一点则更为困难。如果没有充分的测试，随着应用规模的扩大或功能的变更，其可靠性将难以得到有效验证。

Simple scripts generally don't support data persistence, meaning they can't save any data once the program ends. For example, in our guess the number game, if the user closes the application, all progress and data is lost. There's no capability to store data across sessions, which limits the application's functionality. If you need to retain information over time, such as saving user scores, preferences, or any other kind of state, implementing persistence usually requires using databases, files, or other storage solutions which go beyond the scope of a simple script. 

简单的脚本通常不支持数据持久化，这意味着程序结束后无法保存任何数据。例如，在我们的猜数字游戏中，如果用户关闭了应用程序，所有进度和数据都会丢失。应用程序不具备跨会话存储数据的能力，这在一定程度上限制了其功能。如果您需要长期保存数据，例如存储用户分数、偏好设置或其他状态信息，实现持久化通常需要使用数据库、文件系统或其他存储方案，而这已经超出了简单脚本的范畴。

These scripts are typically designed for single user interaction, lacking support for multiplayer environments or concurrent processing. This makes them less suitable for scenarios where multiple users or processes need to interact with the application at the same time. As your projects grow, it becomes necessary to move beyond the simple scripts and adopt more sophisticated programming practices such as modular design, enhanced security measures, and data persistence. Understanding these limitations is key for knowing when it's time to evolve from a simple script to a more comprehensive application architecture.

这些脚本通常面向单用户交互设计，缺乏对多人环境或并发处理的支持。这使得它们不太适用于多个用户或进程需要同时与应用程序交互的场景。随着项目的规模不断扩大，有必要超越简单的脚本，采用更为成熟的编程实践，例如*模块化设计、强化安全措施以及数据持久化。理解这些局限性，是判断何时该从简单的脚本过渡到更完善的应用架构的关键*。
