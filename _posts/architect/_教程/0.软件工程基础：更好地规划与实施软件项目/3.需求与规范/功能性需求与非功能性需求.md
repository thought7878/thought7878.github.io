这份字幕文件详细讲解了软件工程中的需求两大核心分类：**功能性需求（Functional Requirements）** 与 **非功能性需求（Non-Functional Requirements, 简称 NFR）**，并深入剖析了*非功能性需求的三个子分类*。

以下是内容的详细总结：

## 一、 核心概念对比

### 1. 功能性需求（Functional Requirements）
* **定义**：描述系统**应该做什么（What the system should do）**，即程序的具体功能和操作。
* **核心特征**：关注程序**如何与周围的世界交互**（改变、移动数据或让用户执行某项操作）。
* **案例**：
  * 表单能够收集数据、发送数据、防御恶意输入。
  * 将表单数据从前端发送到后端服务器。

### 2. 非功能性需求（Non-Functional Requirements, NFR）
* **定义**：描述系统需要达到的**目标、标准或约束条件**，即系统“应该做得多好”或“受什么限制”。
* **核心特征**：它不是程序直接执行的动作，而是**对功能性需求施加的约束（Constrain us）**。它不一定直接与外部世界交互，但强制系统必须具备某些属性。
* **案例**：
  * **时间约束**：表单数据必须在 **500毫秒内** 提交到服务器。
  * **安全约束**：传输的数据必须使用 **AES-256 加密**。
  * **架构约束**：数据在到达主服务器前，必须先经过 3 个不同的服务器。

---

## 二、 非功能性需求（NFR）的三大子分类

讲师进一步将*非功能性需求细分为以下三个层级：*

### 1. 产品需求（Product Requirements）
* **定义**：产品本身必须具备的属性，或客户对产品实现方式的硬性规定。
* **案例**：客户强制要求 **“程序必须使用 Java 语言编写”**。
  * *解析*：用 Python 或 JavaScript 同样能实现功能，但客户为了后期自己维护，指定了语言。这不影响功能，但属于必须遵守的产品约束。

### 2. 组织需求（Organizational Requirements）
* **定义**：由开发团队所在的公司、机构或客户的内部政策、标准和规则所决定的需求。
* **案例**：
  * **安全政策**：军方或公司内部规定，所有数据流转必须使用 AES-256 加密。
  * **开发流程**：公司规定 **“项目必须使用 Scrum（敏捷开发）方法论”** 进行开发。这属于组织层面的强制要求，无需工程师讨论，直接作为需求记录。

### 3. 外部需求（External Requirements）
* **定义**：来自系统外部的强制力，包括*法律法规、行业标准或市场趋势*。
* **案例**：
  * **法律法规**：欧盟法律（如 GDPR 等数据保护法）强制要求数据点之间必须使用 SSL 加密。如果不遵守，产品将无法在欧洲销售甚至面临诉讼。
  * **市场趋势/用户体验**：业界趋势要求 **“网页必须在 2 秒内加载完毕”**。虽然这不是法律，但如果不满足，用户就会流失。为了保持市场竞争力，这必须作为外部需求被纳入。

---

## 三、 核心总结：如何快速区分两者？

讲师在最后给出了一个*非常实用的判断标准：*

* **功能性需求 = 交互与动作**：程序如何与外部世界交互？它改变了什么？移动了什么？用户能因为它而完成什么操作？（例如：发送邮件、上传视频）。
* **非功能性需求 = 约束与属性**：它不直接产生交互动作，但它**约束**了系统，强制我们*必须以某种特定的标准、速度、安全性或技术栈去实现那些功能*。（例如：邮件必须在1秒内发出、视频必须加密、必须用Java开发）。

在实际编写需求文档时，*这两者有时会交织在一起*（看起来有些模糊），但*将它们拆分开来，有助于开发团队明确“要做什么”以及“必须满足什么底线标准”*。
