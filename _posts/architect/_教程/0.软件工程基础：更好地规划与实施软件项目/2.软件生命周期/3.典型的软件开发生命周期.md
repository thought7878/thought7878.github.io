
这份字幕文件主要讲解了**软件开发周期（Software Development Cycle）的五个核心步骤**，并强调了**遵循这一结构化流程对于交付可靠软件的重要性**。

以下是内容的详细总结：

## 核心主题
**软件开发不仅仅是写代码，而是*需要遵循一套严谨的工程化步骤*（类似于建造桥梁）**。这五个步骤**确保了团队目标一致、技术选型合理，并*能有效避免后期的灾难性返工***。

## 软件开发周期的五大步骤

### 1. **需求**（Requirements）—— “做什么？” (The What)
* 核心目标：*明确我们要构建什么，确保所有团队成员、客户对最终产品的形态、目标用户和规模有完全统一的认知*。
* 重要性：如果缺乏明确的需求，团队成员会朝着不同的方向努力，导致项目最终分崩离析，*导致产品实现了也没价值，导致后面4步的工作全白费*。

### 2. **设计**（Design）—— “怎么做？” (The How)
* 核心目标：**设计、规划如何实现需求**。包括`技术选型`、`服务器架构设置`、`前后端分工`等。
* 常见误区：很多人明确需求后*直接跳入编码（实现阶段），这是非常危险的*。如果*不提前验证设计，可能会在开发完成后才发现架构不支持*（例如设计了8台服务器但实际只能跑2台），**导致必须推倒重来**。

### 3. **实现**（Implementation）—— “动手构建”
* 核心目标：**将设计、规划转化为实际的产品**。
* 执行方式：*在所有人达成共识后，将工作分解为具体的任务和里程碑，分配给团队或个人进行实际的编码和构建*。

### 4. **验证**（Verification）—— “测试与核对”
* 核心目标：**回答关键问题：“我们构建的东西，是我们（和客户）想要构建的吗？它是否正常工作？”**
* 重要性：绝不能因为时间紧迫而草率跳过测试。*未经充分验证的代码可能会在几年后引发严重的数据偏差或安全漏洞*，**导致后期修复成本极高**。

### 5. **维护**（Maintenance）—— “持续优化与修复”
* 核心目标：修复上线后的 Bug、进行微调，**来保持系统正常运行**（如服务器和技术栈更新）。
* 循环特性：如果要开发新功能，通常需要*重新回到“需求”阶段，开启新一轮的循环*。
* 痛点：如果**前期没有做好需求、设计和文档记录，维护阶段将极其痛苦**，新程序员可能需要**花费数月时间才能理解代码库**。

## 关键洞察与课程预告
* **不要走捷径**：*跳过“设计”和“验证”看似节省了前期时间，但会在后期（维护阶段）成倍地增加修复成本和项目失败的风险*。
* 后续课程方向：本课程接下来*将对这五个步骤进行深入剖析*，并详细介绍**如何将它们组合起来**的不同**软件开发模型**（如 `V模型`、`Scrum 敏捷开发`、`瀑布模型`等）。

---

### 五个阶段概览

| 阶段                        | 核心问题        | 要点                                                               |
| ------------------------- | ----------- | ---------------------------------------------------------------- |
| **1. 需求（Requirements）**   | 我们**做什么**？  | 明确产品定义，确保团队所有人对最终产品的理解一致（服务器数量、目标用户等），避免各做各的、最终分崩离析              |
| **2. 设计（Design）**         | 我们**怎么做**？  | 确定技术选型、服务器架构、前端方案等。**很多人跳过此步直接写代码**，结果发现技术不兼容，只能推倒重来             |
| **3. 实现（Implementation）** | 动手构建        | *将任务分配给团队或个人，按里程碑推进开发*                                           |
| **4. 验证（Verification）**   | 做的是否**正确**？ | 即测试：是否符合需求？是否满足客户期望？输入是否产生正确输出？**时间紧时最容易被跳过**，但会埋下隐患（数据泄露、数据偏差等） |
| **5. 维护（Maintenance）**    | 持续运营与迭代     | 修 bug、小幅调整、服务器更新、技术升级。若需开发新功能，则回到需求阶段重新走一遍周期                     |

---

### 关键警示

- **跳过设计** → 可能在实现后才发现技术路线不通，被迫从零开始
- **跳过测试** → 隐藏 bug 可能数年后才爆发，造成安全漏洞或数据污染，修复成本极高
- **缺少文档** → 新成员需要数月才能上手代码库，维护极其困难

So let's jump into the software development cycle—the way that we engineer software. There are a bunch of different ways that you can do it, and these are usually called models. That's how you actually implement these five steps. These five steps are usually crucial to getting a piece of software up to standards that are very reliable. You'll also notice that these can be applied to really any engineering practice. Like in the last lecture, when I talked about building a bridge, this could be used for that as well. We would go over requirements, design, implementation, verification, and maintenance—all with a bridge. So if we want to think about it like that as we go through this, it might make it stick a little bit better.
The first thing we want to talk about is something called requirements. The requirements are pretty simple. They answer the question: what are we building? What are we going to build? We want to be able to get that to a point where no one will be able to dispute what we're building.
What I mean by that is we don't want a group of eight people building this all with a different idea of what the end product is going to be. We don't want one person thinking that it's going to use eight servers, while another thinks it's just going to be a local server. One thinks it's going to be used mainly by businesses, while someone else thinks it's going to be used mainly by consumers. That would be a big problem if you're trying to get a whole bunch of people to work together on a project. Everyone would build in a different direction, and it would fall apart.
So with requirements, what we're trying to nail down is the what—what are we building? And there's a whole bunch of different little steps within each one of these phases. And that's what this entire course is going to be about: jumping into these. So this is just a top-down view, and then we're going to do a deep dive a little bit later.
So anyway, requirements come first. Second is design. Design is the how—how are we going to build it? What are we going to use? What sort of technologies are we going to put together? How is the server going to be set up? How is the front end going to be set up? Should the front end do this or that? That's where design comes in, and design is very important.
A lot of people skip this step. A lot of people will do the requirements, but then they won't actually go on to design. They'll just sort of jump straight into implementation. So they'll be like, "Okay, we kind of have a good idea of what we want to build—let's jump into implementation." And that can be dangerous because there are still some variables out there, and there are still some things that we want to make sure work before we implement them.
For example, let's say that you built an eight-server giant masterpiece—or at least you think it's a masterpiece. And then when you click the play button and you finally get it running, you realize, "Oh, this doesn't work with eight servers. It only works with two servers. It only works with this sort of technology. I'm going to have to restart from the very beginning." That's the sort of thing you want to work out in the design portion.
After design, we jump down into implementation, and everyone knows what implementation is. Implementation is—you just build the thing. So you've done all the planning, everyone's on the same page, and now you're going to divvy it up. Maybe you have teams, maybe it's just a group of three people, maybe it's just yourself, and you're just going to divvy it up into certain tasks and milestones. But the implementation part is the building part. You're going to build the product. You're going to create what you have set out to create. And then the next step is verification.
So with verification, what we're doing is something called testing. We are trying to figure out a crucial question here: is what we built what we wanted to build? This oftentimes involves a couple of different things. For example: is what we built what we wanted to build? Is what we built what our client wanted us to build? Is what we built working properly? Is the input going in creating the proper output? And this is why testing comes into play. Usually with testing, you need to know the requirements—you need to know what it was supposed to do—and then you can test against that. Does it do what it was supposed to do? So this is a very important step.
And this is another one that's oftentimes sort of forgotten. If there's a time crunch, people say, "Oh no, don't worry about testing. We'll just do some quick major tests and then we'll move on." And that can be a big problem because then you have those giant bugs in your program. Maybe they don't manifest themselves for a couple of years, and then it leads to a giant data security breach. Or maybe it's just something very small over time. Maybe all the data going into the database is off by one, and it can sort of skew your data, and then it'll cost a whole lot later on in the maintenance phase to fix it. So verification and testing are important, and we'll cover some techniques on that and some of the ways that you should be testing.
Then finally, we have maintenance. And this is that end of the cycle where you're going to be fixing bugs. You're also going to be maybe doing more testing, maybe implementing some other things, maybe redesigning things. Maintenance is sort of the way this cycles back. A lot of times, if you're developing an additional feature, for example, you would actually cycle all the way back to requirements and then start this process over. But the maintenance cycle is typically just fixing bugs, making little adjustments to keep it more in line with the requirements, keeping it running, doing server updates, and updating this technology or that technology.
So maintenance is important, and maintenance can be very difficult if you don't go through all of these steps. There could be a ton of bugs if you skip these, especially if there's no documentation. If you didn't write anything down—if you didn't actually have this whole plan written out—then it can be very difficult, because you can't really bring in other programmers easily. It'll take them six months to learn the codebase, et cetera. But anyway, this is the top-down view of the typical software development cycle.

What's the best way to do it? Do you do it like a V, where you sort of put some of these on each side? There are things called Scrum and the Waterfall method—we'll go over all of that. But the software development cycle is really good to know, and you're going to be seeing it a whole lot.
