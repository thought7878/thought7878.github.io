
这段字幕主要讲解：**如何为系统设计 API（应用程序编程接口）**，包括 *API 的定义、分类，以及设计良好 API 的最佳实践*。

## 核心主题
本节课介绍系统设计中 **API 的作用**：API 是系统**对外提供的接口契约**，让客户端应用可以在不了解系统内部实现的情况下***调用系统能力***。

---

## 一、什么是 API？

`API`，全称 `Application Programming Interface`，即`应用程序编程接口`。

在系统设计中，当我们明确了功能需求之后，可以**把系统看作一个“黑盒”：**
- 系统*有特定的行为*；
- 系统*有定义良好的接口*；
- 外部应用*通过这个接口使用系统*。

因此，**API 本质**上是：
> 系统实现者与系统使用者之间的*一份契约*。

在大规模系统中，API 通常是**通过网络远程调用的（Web API）**。

**调用 API 的客户端**可能包括：
- 移动端应用；
- 网页浏览器；
- 其他公司的后端系统；
- 公司内部的其他系统；
- *同一系统内部的不同组件*。

---

## 二、为什么需要 API？

良好定义的 API 有*几个重要好处：*

### 1. 客户端无需了解内部实现
客户端只需要知道如何调用 API，而不需要知道系统内部是如何设计和实现的。

### 2. 支持并行开发
一旦 API 定义完成，客户端就可以提前开始集成开发，而不必等待整个系统实现完成。

### 3. 帮助设计系统结构
API 定义了用户可以访问的端点和操作路径，因此也能帮助架构师更好地规划系统内部结构。

---

## 三、API 的三种分类

### 1. Public API：公开 API
面向公众开放，*任何开发者都可以调用*。

最佳实践是要求用户先注册或申请访问权限。这样可以：
- 控制谁在使用 API；
- 了解调用方式；
- 提高安全性；
- 封禁违反规则的调用者。

### 2. Private API：私有 / 内部 API
*只在组织内部开放*。

它可以让公司内部其他团队**复用系统能力，提高效率**，同时避免把系统直接暴露给外部。

### 3. Partner API：合作伙伴 API
这类 API *类似公开 API，但不是对所有人开放*，而是*只对与平台有商业合作关系*的公司或用户开放。

例如：
- 已购买产品的客户；
- 已订阅服务的用户；
- 签署了合作协议的合作伙伴。

---

## 四、设计良好 API 的最佳实践

### 1. 封装内部实现
API *应该完全封装系统的内部设计和实现细节*。

如果调用者必须了解系统内部逻辑才能使用 API，那么这个 API 设计就是不成功的。

**好的 API 应该做到：**
- *隐藏内部实现*；
- 与内部设计解耦；
- 允许未来修改内部结构而不破坏已有客户端。

---

### 2. 易于使用，避免误用
好的 API **应该简单、清晰、容易理解**，并且尽可能避免被误用。

常见做法包括：
- 获取某类数据或执行某类任务*只提供唯一方式*；
- *使用清晰、描述性强的命名*；
- *只暴露用户需要的资源和操作*；
- *保持整个 API 风格和结构一致*。

---

### 3. 尽量保证操作幂等
`幂等操作`是指*同一个操作执行一次和执行多次，产生的结果和影响相同*。

例如：
- “更新用户地址”*是幂等操作*；
- “给用户余额增加 100 美元”*不是幂等操作*。

**幂等性在分布式系统中非常重要：** 因为网络请求可能失败、超时或丢失；如果接口是幂等的，客户端就可以安全地重试，而不用担心产生重复副作用。

---

### 4. 使用分页处理大量数据
**当 API 返回大量数据时，不应该一次性返回所有结果**。

例如：
- 邮箱页面不会一次加载所有历史邮件；
- 搜索引擎不会一次返回所有匹配结果；
- 电商网站不会一次展示所有商品。

分页机制允许客户端：
- *指定每页返回数量*；
- *指定偏移量*；
- 逐步请求下一批数据。

这样可以**避免响应过大，提高客户端性能和用户体验**。

---

### 5. 对耗时操作使用异步 API
**有些操作需要很长时间才能完成，例如：**
- 生成大型报表；
- 分析海量日志；
- 压缩大视频文件。

这类操作不适合让客户端一直等待。

**更好的方式是使用异步 API：**
1. 客户端发起请求；
2. 系统立即返回一个任务 ID 或标识符；
3. 客户端通过该 ID 查询任务状态；
4. 任务完成后再获取最终结果。

**这样客户端不会被阻塞，也可以继续处理其他任务**。

---

### 6. 对 API 进行版本控制
**API 可能需要随着业务发展进行修改**。  
有些修改可能是**不向后兼容**的。

**因此，API 应该显式标注版本，例如：**
- v1；
- v2；
- v3。

**版本控制的好处是：**
- 客户端知道自己使用的是哪个版本；
- 平台可以同时维护多个版本；
- 可以逐步废弃旧版本；
- 减少破坏性变更带来的影响。

---

## 五、课程总结

本节课主要讲了三部分内容：

### 1. API 的定义
API 是系统提供给其他应用的接口契约，使调用方可以在不了解内部实现的情况下使用系统。

### 2. API 的分类
API 主要分为：
- Public API：公开 API；
- Private API：内部私有 API；
- Partner API：合作伙伴 API。

### 3. 良好 API 的设计原则
**设计优秀 API 时应遵循以下原则：**
- 封装内部实现；
- 保持简单易用；
- 操作尽量幂等；
- 大数据结果使用分页；
- 长耗时任务使用异步处理；
- 显式进行 API 版本控制。


# 2

这是一段关于系统设计中 **API（应用程序接口）设计** 的课程字幕。本节课主要讲解了 API 的定义与作用、API 的三大分类，以及设计高质量、易用且健壮 API 的核心最佳实践。

以下是详细的内容总结：

## 一、 什么是 API 及其作用？
* **定义**：在明确功能需求后，系统可被视为一个具有特定行为和良好接口的“黑盒”。这个接口就是 **API (Application Programming Interface)**，它是**系统实现者（工程师）与系统使用者（客户端应用）之间的契约**。
* **特点**：在大型分布式系统中，API 通常通过网络被远程调用。
* **调用者**：
  * **前端客户端**：移动应用、Web 浏览器。
  * **外部/内部系统**：其他公司的后端系统，或公司内部的各个微服务/组件。
* **定义良好 API 的好处**：
  1. **解耦与易用**：客户端无需了解系统内部设计和业务逻辑，即可直接调用并增强自身业务。
  2. **并行开发**：API 定义完成后，客户端无需等待系统开发完毕，即可开始集成开发。
  3. **指导内部架构**：API 定义了系统的端点和路由，有助于规划和设计系统的内部结构。

---

## 二、 API 的三大分类
根据目标受众和业务场景，API 通常分为三类：
1. **公开 API (Public APIs)**
   * 面向公众开放，任何开发者均可调用。
   * **最佳实践**：要求用户注册（获取密钥/Token），以便控制外部使用情况、提高安全性，并能封禁违规用户。
2. **私有/内部 API (Private/Internal APIs)**
   * 仅限公司内部使用。
   * 允许公司内其他团队复用系统能力以创造更大价值，同时避免将系统直接暴露给外部。
3. **合作伙伴 API (Partner APIs)**
   * 类似公开 API，但仅对**具有业务合作关系**的公司或用户开放（如签订了客户协议或购买了订阅服务）。

---

## 三、 设计良好 API 的六大最佳实践

### 1. 完全封装与抽象 (Encapsulation & Abstraction)
* **核心**：隐藏内部设计与实现细节。如果客户端必须了解内部实现才能使用，API 就失去了意义。
* **解耦**：API 必须与内部实现完全解耦，确保未来随时可以修改内部架构，而不会破坏与现有客户端的契约。

### 2. 易用性与防止误用 (Ease of Use & Prevent Misuse)
* **单一途径**：获取特定数据或执行任务只提供一种方式，避免多种冗余方法。
* **命名规范**：为操作和资源使用清晰、描述性的名称。
* **最小暴露**：只暴露用户需要的信息和操作，绝不超纲。
* **一致性**：在整个 API 中保持设计模式和命名的一致性，降低学习成本。

### 3. 幂等性 (Idempotency)
* **定义**：无论操作执行一次还是多次，对结果的影响都相同。
  * *幂等示例*：更新用户地址。
  * *非幂等示例*：将用户余额增加 100 美元（执行多次会导致余额错误增加）。
* **为什么重要**：网络通信是不可靠的（消息可能丢失、响应可能丢失、服务可能宕机）。由于客户端无法确定失败的具体原因，**幂等操作允许客户端安全地重试**，而不用担心产生副作用（如重复扣款/加钱）。

### 4. 分页 (Pagination)
* **场景**：当响应包含极大数据集时（如邮件列表、搜索结果）。
* **问题**：如果不分页，一次性返回所有数据会导致客户端崩溃或极差的用户体验。
* **机制**：允许客户端指定每次响应的最大数据量（Limit/Size）和偏移量（Offset）。如果需要下一段数据，只需增加偏移量即可。

### 5. 异步 API (Asynchronous API)
* **场景**：处理耗时极长的操作（如生成大数据报告、日志聚合、压缩大视频），且这些操作无法像分页那样提供有意义的部分结果。
* **问题**：客户端被迫长时间阻塞等待，无法进行其他操作。
* **机制**：
  1. 客户端发起请求后，系统**立即返回响应**（通常包含一个任务标识符/ID）。
  2. 客户端使用该标识符**轮询或跟踪**操作的进度和状态。
  3. 操作完成后，客户端获取最终结果。

### 6. API 版本控制 (API Versioning)
* **动机**：虽然理想情况下内部修改不应影响 API，但现实中有时被迫进行**不向后兼容**的破坏性修改。
* **机制**：显式地对 API 进行版本化（如 v1, v2），并让客户端明确知道自己使用的版本。
* **好处**：允许系统同时维护多个 API 版本，从而可以平滑地、逐步地弃用旧版本，并与仍在使用旧版本的客户端进行沟通迁移。

---

## 四、 课程总结
本节课系统性地介绍了 API 设计的基础知识：
1. **API 是系统与外部交互的契约**，使得客户端能在不了解内部实现的情况下使用系统。
2. 根据受众不同，API 分为**公开、私有和合作伙伴**三类。
3. 优秀的 API 设计必须遵循六大原则：**封装抽象、简单易用、支持幂等重试、提供分页、支持异步长任务、以及显式的版本控制**。这些实践能显著提升系统的健壮性和开发者的使用体验。
