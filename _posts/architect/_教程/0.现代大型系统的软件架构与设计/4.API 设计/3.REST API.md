这段字幕主要讲解：**REST API 的基本概念、设计原则、与 RPC 的区别，以及如何一步步设计一个 REST API。**

---

## 一、什么是 REST API？

REST 全称是：

> **Representational State Transfer，表述性状态转移。**

它来源于 Roy Fielding 在 2000 年提出的论文。

REST 不是协议，也不是标准，而是一种：

> **用于设计 Web API 的架构风格和最佳实践集合。**

遵循 REST 架构约束的 API 通常被称为：

> **RESTful API。**

REST API 的目标是让 API：

- 更容易被客户端理解；
- 更容易被客户端使用；
- 更有利于构建高性能、可扩展和高可用的系统。

---

## 二、REST API 与 RPC API 的区别

### 1. RPC 更面向方法
在 RPC 风格中，系统通过一组方法暴露给客户端。

如果要扩展功能，通常就是：

> 增加更多方法。

例如：

```text
createUser()
updateUser()
deleteUser()
getUser()
```

RPC 的核心抽象是“方法”。

---

### 2. REST 更面向资源
在 REST 风格中，系统的核心抽象不是方法，而是：

> **资源，Resource。**

客户端通过请求某个命名资源，获得该资源当前状态的表示。

例如：

```text
/users
/users/123
/movies
/movies/456/reviews
```

REST 的核心思想是：

> 客户端操作资源，而不是直接调用远程方法。

---

## 三、资源状态表示

REST API 返回的不是资源本身的内部实现，而是：

> **资源当前状态的表示，Representation。**

例如，一个新闻网站的首页资源，客户端请求后可能得到：

- 页面标题；
- 文章列表；
- 图片。

但这只是首页资源的一种表示形式。  
在系统内部，这个资源可能由多个数据库表、文件、外部服务共同组成。

客户端不需要知道这些内部实现细节。

---

## 四、REST API 的动态性：HATEOAS

与 RPC 不同，REST API 可以更动态。

REST 中有一个概念叫：

> **Hypermedia as the Engine of the Application State**  
> 超媒体作为应用状态引擎，简称 HATEOAS。

意思是：服务器返回资源状态时，可以同时返回一些链接，告诉客户端接下来可以做什么。

例如，客户端请求当前邮件列表，服务器不仅返回邮件数据，还可以返回：

- 查看某封邮件的链接；
- 删除邮件的链接；
- 标记已读的链接；
- 获取下一页邮件的链接。

这样客户端可以根据响应中的链接继续推进操作，而不是提前把所有操作都写死。

---

## 五、REST 如何帮助实现高性能、高可用和可扩展性？

### 1. 无状态，Stateless
REST 要求服务器：

> 不保存客户端的会话状态。

每个请求都应该独立完成，服务器不需要依赖之前的请求上下文。

好处是：

- 更容易水平扩展；
- 可以把请求分发到任意服务器；
- 客户端不需要绑定到某一台机器；
- 提高系统可用性和扩展性。

例如：

```text
客户端第一个请求 -> 服务器 A
客户端第二个请求 -> 服务器 B
```

只要系统无状态，客户端就不会感知差异。

---

### 2. 可缓存，Cacheable
REST 要求响应必须明确或隐含地标记为：

- 可缓存；
- 不可缓存。

好处是：

- 客户端可以直接使用缓存数据；
- 减少不必要的网络请求；
- 降低服务器负载；
- 提高性能。

---

## 六、REST API 中的资源组织方式

在 REST API 中，每个资源都通过：

> **URI，统一资源标识符**

来命名和访问。

资源通常以层级结构组织，使用斜杠 `/` 表示层级关系。

资源主要分为两类：

| 类型 | 含义 | 示例 |
|---|---|---|
| 简单资源 | 单个资源对象 | `/movies/123` |
| 集合资源 | 一组相同类型的资源列表 | `/movies` |

例如，一个电影流媒体服务可以这样组织资源：

```text
/movies
/movies/123
/movies/123/directors
/movies/123/actors
/movies/123/actors/45
/movies/123/actors/45/profile-picture
```

其中：

- `/movies` 是电影集合；
- `/movies/123` 是某一部电影；
- `/movies/123/actors` 是该电影的演员集合；
- `/movies/123/actors/45` 是某个演员；
- `/movies/123/actors/45/profile-picture` 是该演员的头像资源。

资源状态的表示形式可以是：

- JSON；
- XML；
- HTML；
- 图片；
- 二进制数据；
- 链接；
- 可执行代码，例如浏览器中的 JavaScript。

其中最常见的是：

> **JSON。**

---

## 七、REST 资源命名的最佳实践

### 1. 使用名词命名资源
资源应该用名词，而不是动词。

例如推荐：

```text
/users
/orders
/products
```

不推荐：

```text
/getUser
/createOrder
/deleteProduct
```

因为动作通常由 HTTP 方法表达，而不是放在 URL 中。

---

### 2. 区分集合资源和简单资源
集合资源通常使用复数形式，简单资源通常使用单数概念。

例如：

```text
/movies
/movies/123
/actors
/actors/45
```

其中：

- `movies`、`actors` 是集合；
- `movies/123`、`actors/45` 是具体资源。

---

### 3. 使用清晰、有意义的名称
资源名称应该容易理解，避免让调用者困惑。

应避免过于宽泛的名字，例如：

```text
/items
/entities
/elements
/objects
/values
/instances
```

这些名称缺乏明确语义，依赖上下文，容易造成误用。

---

### 4. 资源标识符应唯一且适合 URL
资源 ID 应该：

- 唯一；
- 安全；
- 方便放在 URL 中；
- 适合在 Web 环境中使用。

例如：

```text
/users/12345
/movies/abc-456
```

---

## 八、REST API 中的 HTTP 方法

REST API 通常基于 HTTP 实现。  
REST 将常见资源操作映射到 HTTP 方法：

| 操作 | HTTP 方法 | 示例 |
|---|---|---|
| 创建资源 | POST | `POST /users` |
| 更新资源 | PUT | `PUT /users/123` |
| 删除资源 | DELETE | `DELETE /users/123` |
| 获取资源状态 | GET | `GET /users/123` |

如果资源是集合资源，获取它的状态通常意味着获取它的子资源列表。

例如：

```text
GET /movies
```

可能返回电影列表。

---

## 九、HTTP 方法的语义

### 1. GET 是安全的
GET 方法通常不会修改资源状态。

也就是说：

> 只读。

---

### 2. GET、PUT、DELETE 是幂等的
幂等意味着：

> 执行一次和执行多次，对系统状态的影响相同。

例如：

```text
DELETE /users/123
```

第一次调用会删除用户。  
之后再调用，即使资源已经不存在，也不会产生额外的状态变化。

---

### 3. GET 请求通常可缓存
GET 响应默认通常可以被缓存。

POST 响应也可以通过 HTTP 头部设置为可缓存。

---

### 4. POST 和 PUT 可以携带数据
当客户端需要向服务器提交数据时，通常使用：

```json
{
  "name": "Alice",
  "email": "alice@example.com"
}
```

最常见的数据格式是：

> **JSON。**

XML 也可以，但实际中 JSON 更常见。

---

## 十、如何一步步设计 REST API？

课程通过一个电影流媒体服务示例，介绍了设计 REST API 的步骤。

### 第一步：识别系统中的实体
首先找出系统中重要的业务对象。

例如电影流媒体服务中的实体包括：

- 用户；
- 电影；
- 评论；
- 演员。

这些实体将成为 API 中的资源。

---

### 第二步：将实体映射为 URI
根据实体之间的关系，把资源组织成层级结构。

例如：

```text
/users
/movies
/actors
/movies/{movieId}/reviews
```

其中：

- `users`、`movies`、`actors` 是独立集合资源；
- `reviews` 是某部电影的子资源，因为每条评论只属于一部电影。

---

### 第三步：选择资源表示格式
理论上资源可以用任何格式表示，但最常见的是：

> JSON。

例如，电影集合可以表示为：

```json
{
  "movies": [
    {
      "id": "123",
      "name": "Inception"
    },
    {
      "id": "456",
      "name": "Interstellar"
    }
  ]
}
```

单个电影资源可以包含：

```json
{
  "id": "123",
  "name": "Inception",
  "playUrl": "...",
  "reviewsUrl": "/movies/123/reviews",
  "actorsUrl": "/movies/123/actors"
}
```

这些链接体现了 HATEOAS 思想：客户端可以通过响应中的链接发现后续操作。

---

### 第四步：为资源分配 HTTP 方法
根据业务操作，将 HTTP 方法映射到资源上。

例如：

| 操作 | HTTP 方法 | 路径 |
|---|---|---|
| 注册新用户 | POST | `/users` |
| 获取某个用户信息 | GET | `/users/{userId}` |
| 更新用户信息 | PUT | `/users/{userId}` |
| 删除用户 | DELETE | `/users/{userId}` |

对于其他资源，例如电影、评论、演员，也重复类似过程。

---

## 十一、课程总结

本节课主要讲了 REST API 的设计思想：

### 1. REST 是什么？
REST 是一种 Web API 架构风格，不是协议，也不是标准。  
遵循 REST 约束的 API 称为 RESTful API。

### 2. REST 与 RPC 的核心区别
- RPC 面向方法；
- REST 面向资源。

### 3. REST 的关键概念
- 资源；
- 资源状态表示；
- URI；
- HTTP 方法；
- 无状态；
- 可缓存；
- 超媒体链接。

### 4. REST 的优势
REST API 有助于实现：

- 高性能；
- 高可用；
- 可扩展性；
- 易用性。

### 5. 设计 REST API 的步骤
1. 识别系统中的实体；
2. 将实体映射为资源和 URI；
3. 选择资源表示格式，通常是 JSON；
4. 使用合适的 HTTP 方法表达操作。

总体来说，这节课的核心是：  
**REST API 应该围绕资源设计，而不是围绕方法设计；通过清晰的资源命名、合理的层级结构、标准 HTTP 方法、无状态和缓存机制，构建易于使用和扩展的 Web API。**
