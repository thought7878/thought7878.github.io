这段字幕主要讲解：**RPC（Remote Procedure Call，远程过程调用）风格的 API**。内容包括 RPC 的定义、工作原理、组成部分、优缺点，以及什么时候适合使用 RPC。

---

## 一、什么是 RPC？

`RPC` 全称是 **Remote Procedure Call**，即`远程过程调用`，它指的是**客户端程序可以像调用本地方法一样，去调用远程服务器上的某个方法或子程序**。也就是说，**虽然代码实际上是在远程服务器上执行，但对于开发者来说，调用方式看起来和本地函数调用几乎一样**。
这种特性也叫：`Local Transparency（本地透明性）`。

*例如*，客户端开发者写代码时感觉只是调用了一个普通方法，但底层实际上发生了网络请求、数据序列化、远程执行和结果返回。

*很多 RPC 框架还支持多种编程语言，因此不同语言编写的应用之间也可以通过 RPC 通信*。

---

## 二、RPC 的工作原理

***RPC 的核心思想***是：**把远程调用的复杂过程封装起来，让开发者只关心方法调用本身**。

### 1. 使用接口描述语言定义 API
首先，*API 的方法和数据结构*会使用一种特殊的 **接口描述语言** 来定义。

不同的 RPC 框架可能**使用不同的描述语言，但它的作用通常是：**
- 定义*有哪些方法*；
- 定义*方法参数*；
- 定义*返回值类型*；
- 定义*数据结构*；
- 作为客户端和服务端之间的通信契约。

### 2. 自动生成代码
有了接口定义之后，RPC 框架可以**使用代码生成工具生成两部分代码：**

| 生成内容        | 所在端 | 作用                  |
| ----------- | --- | ------------------- |
| Client Stub | 客户端 | 负责*把本地调用转换成网络请求*    |
| Server Stub | 服务端 | 负责*接收请求并调用真正的服务端方法* |

这些自动生成的数据结构通常会被编译成类或结构体，也可以称为 **DTO，Data Transfer Object，数据传输对象。**

---

## 三、RPC 调用的完整流程

**一次 RPC 调用大致经过以下步骤：**
1. 客户端调用看起来像本地方法的 RPC 方法；
2. 客户端 stub 将参数进行编码或序列化；
3. 客户端 stub 建立网络连接，并把数据发送到远程服务器；
4. 服务端 stub 接收到请求；
5. 服务端 stub 对数据进行反序列化；
6. 服务端 stub 调用真正的服务端方法；
7. 服务端方法执行完成，得到结果；
8. 服务端 stub 将结果序列化；
9. 服务端 stub 将响应返回给客户端；
10. 客户端 stub 接收响应并反序列化；
11. 最终结果像本地方法返回值一样返回给调用者。

整个过程对开发者基本透明，开发者不需要手动处理网络通信细节。

---

## 四、RPC 框架中开发者的职责

作为 API 开发者，主要工作通常是：
1. 选择合适的 RPC 框架；
2. 使用框架提供的接口描述语言定义 API；
3. 定义相关数据类型；
4. 发布 API 描述。

之后：
- 服务端可以生成 server stub；
- 客户端可以根据公开的 API 定义生成 client stub；
- 客户端和服务端在实现上相互解耦。

如果 RPC 框架支持多种编程语言，那么：
- 服务端可以选择一种语言实现；
- 客户端也可以选择自己擅长的语言进行调用。

## 五、RPC 的优点

### 1. 使用方便
客户端开发者生成 client stub 后，就可以像调用本地方法一样调用远程服务。

例如：

```text
result = paymentService.debitAccount(userId, amount)
```

从代码上看，它像普通方法调用，但实际执行在远程服务器上。

### 2. 隐藏网络通信细节
RPC 框架会封装：

- 网络连接；
- 数据序列化；
- 数据反序列化；
- 请求发送；
- 响应接收；
- 错误处理。

开发者不需要关心底层通信细节。

### 3. 错误处理类似本地调用
如果远程调用失败，通常会以异常或错误的形式返回给调用方，这与本地方法调用失败的体验类似。

---

## 六、RPC 的缺点

### 1. 比本地调用更慢
本地方法调用通常在进程内完成，速度很快。  
而 RPC 调用需要经过：
- 序列化；
- 网络传输；
- 远程处理；
- 响应返回；
- 反序列化。

因此，RPC 调用的延迟通常远高于本地方法。

问题在于：由于 RPC 的代码看起来像本地方法调用，开发者可能会误以为它也很快，从而导致不必要的性能瓶颈。

### 2. 比本地调用更不可靠
RPC 依赖网络通信，而网络可能不稳定。

例如可能出现：
- 请求丢失；
- 响应丢失；
- 服务器宕机；
- 网络超时；
- 客户端不知道服务端是否执行成功。

这会导致一些复杂情况。

例如，一个在线商店调用信用卡公司的 `debitAccount` 扣款方法，如果调用失败，客户端会面临两难：
- 如果重试，可能重复扣款；
- 如果不重试，可能没有成功扣款。

客户端无法确定失败原因是：
- 服务端没有收到请求；
- 服务端已经执行但响应丢失；
- 网络中途出现问题。

### 3. 如何缓解这些问题？

对于慢操作，可以采用 **异步 API。**

对于不可靠重试问题，可以采用 **幂等操作。**

幂等操作可以保证即使客户端重复调用，也不会产生额外副作用。

---

## 七、什么时候适合使用 RPC？

RPC 比较适合以下场景：

### 1. 后端系统之间的通信
RPC 常用于**两个后端服务之间的调用**。

例如：
- *订单服务调用支付服务*；
- *用户服务调用认证服务*；
- *内部微服务之间互相调用*。

### 2. 提供给其他公司的 API
如果 API 是提供给合作公司或企业客户，而不是直接给浏览器或移动端终端用户使用，RPC 是一个不错选择。

### 3. 大型系统内部组件通信
在大规模系统内部，不同组件之间经常需要高效、强类型的方法调用，RPC 很适合这种场景。

### 4. 希望完全抽象网络通信
如果希望客户端只关心“执行什么操作”，而不关心 HTTP 头、Cookie、网络协议等细节，RPC 比较合适。

---

## 八、什么时候不太适合使用 RPC？

### 1. 面向浏览器或终端用户应用
虽然有些框架支持前端调用 RPC，但*在浏览器场景中，RPC 通常不如 HTTP/JSON 风格的 API 常见*。

### 2. 需要直接利用 HTTP 特性
如果系统设计需要直接使用：
- HTTP 方法；
- HTTP 状态码；
- HTTP headers；
- Cookies；
- REST 风格资源模型；

那么 RPC 可能不是最佳选择。

### 3. 以数据和资源为中心的系统
RPC 更偏向于“动作”或“操作”。

例如：

```text
createUser()
deleteOrder()
updateAddress()
```

如果 API 主要是围绕资源进行简单的增删改查，例如：
- 创建用户；
- 查询用户；
- 更新用户；
- 删除用户；

那么其他 API 风格，例如 REST 风格，可能更合适。

---

## 九、课程总结

本节课主要讲了 RPC 风格 API 的核心内容：

### 1. RPC 的定义
RPC 允许客户端像调用本地方法一样调用远程服务器上的方法。

### 2. RPC 的三个关键组成部分
- **API 定义**：通常使用接口描述语言定义；
- **Client Stub**：客户端代理，负责序列化请求并发送；
- **Server Stub**：服务端代理，负责接收请求并调用真实方法。

### 3. RPC 的优点
- 调用体验像本地方法；
- 隐藏网络通信细节；
- 支持多语言通信；
- 客户端和服务端解耦。

### 4. RPC 的缺点
- 比本地调用慢；
- 比本地调用不可靠；
- 失败后可能难以判断是否应该重试。

### 5. 常见缓解方式
- 对慢操作使用异步 API；
- 对可重试操作设计幂等性。

总体来说，RPC 非常适合后端服务之间、系统内部组件之间，以及企业级系统之间的通信，但在面向浏览器、资源型 API 或需要显式利用 HTTP 特性的场景中，可能不是最佳选择。
