这段字幕文件是关于 **React 底层渲染机制概述（共三部分的第一部分）** 的技术讲座。主要目的是纠正开发者对“渲染（Render）”的常见误解，并**宏观梳理 React 将组件更新到屏幕上的完整生命周期**。

以下是核心内容的结构化总结：

## 核心主旨
React 的“渲染（Render）”与我们通常理解的“在屏幕上显示内容”*完全不同*。`React 的渲染`是**一个纯内部的计算过程，真正的 DOM 更新和视觉变化发生在后续的“提交（Commit）”阶段和浏览器的重绘中**。

---


## 1. 基础概念回顾
* `组件`与`实例`：我们编写组件，React 会根据使用情况创建一个或多个**组件实例**（持有实际的 state 和 props）。
* `React 元素`：调用组件函数会生成 `React.createElement` 调用，进而**产生 React 元素**，这些元素最终会**被转换为真实的 DOM 元素**。

## 2. React 更新屏幕的 4 个完整步骤
*当状态（State）发生变化时，React 会按以下顺序执行：*

![[_posts/后端/课程/终极 React 课程 2025：React、Next.js、Redux 等技术的学习/2.第二部分：中级 React/React 原理/media/a1d3b825b05bc106fc43e46fd89a3bf2_MD5.webp]]

### 1. 触发渲染 (Triggering a Render)
   * `两种方式`：应用的`初始渲染（Initial Render）`，或应用中某处发生状态更新触发的`重新渲染（Re-render）`。
   * `全局性`：渲染过程是为**整个应用（整个组件树）** 触发的，而**不仅仅是发生状态更新的那个单一组件**（尽管在实际表现上，*未变化的部分会被复用，看起来像只更新了局部*）。
   * `调度机制`：状态更新后，渲染**并非绝对立即执行**，而是`被调度（Scheduled）` 到 JavaScript 引擎**有空闲时执行**。多个 setState 调用可能会被**批处理（Batched）** 以优化性能。

### 2. 渲染阶段 (Render Phase) 
⚠️ 核心澄清：*渲染阶段的渲染是指React中的渲染*。
   * `做什么`：React **调用组件函数，计算出为了反映最新的状态，DOM 应该 如何更新**。
   * `不做什么`：**此阶段绝对不会更新真实 DOM，也不会产生任何视觉上的变化。** 它**纯粹是 React 内部的计算过程**。

[[渲染阶段]]

### 3. 提交阶段 (Commit Phase)
   * `做什么`：React 根据 Render Phase 计算出的结果，**真正地对真实 DOM 进行操作**（插入新元素、更新现有元素、删除旧元素）。
   * `意义`：这才是传统意义上我们理解的“渲染（更新屏幕）”实际发生的阶段。

[[提交阶段]]

### 4. 浏览器重绘 (Browser Repaint)
   * `做什么`：*浏览器检测到 DOM 发生了变化，从而重新绘制屏幕，产生用户最终看到的视觉变化*。
   * `注意`：这一步完全*由浏览器负责，已经脱离了 React 的控制范围*。

## 总结
* **认知纠偏**：以前课程中为了方便理解，将“渲染”等同于“屏幕更新”。但从底层机制来看，**屏幕更新 = Render Phase（内部计算） + Commit Phase（DOM 突变） + 浏览器重绘**。
