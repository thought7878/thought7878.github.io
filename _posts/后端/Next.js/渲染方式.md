在 Next.js App Router 中，渲染方式不再是简单的“页面级”选择，而是可以在**组件级别**进行精细控制。下面从“何地、何时、优点、缺点、应用场景”五个维度，详细对比这些渲染方式。

---

## 核心对比总览

| 渲染方式                  | 何地（执行位置）       | 何时（触发时机）           | 优点                     | 缺点                        | 应用场景                 |
| --------------------- | -------------- | ------------------ | ---------------------- | ------------------------- | -------------------- |
| **Server Components** | 仅服务器           | 默认，无需声明            | 减少客户端 JS、直接访问数据源、保护密钥  | 不能使用状态/事件/浏览器 API         | 数据获取、重计算、访问敏感信息      |
| **Client Components** | 浏览器（可预渲染 HTML） | `'use client'` 声明  | 支持交互、状态、Hooks、浏览器 API  | 增加 bundle 体积、需要 hydration | 按钮、表单、模态框、地图等交互组件    |
| **静态渲染 Static**       | 服务器（构建时）       | 构建时或 revalidate 时  | 极快、可 CDN、减少服务器负载、SEO 好 | 数据不实时、每次更新需重新构建           | 博客、文档、营销页、产品页        |
| **动态渲染 Dynamic**      | 服务器（请求时）       | 每次用户请求             | 实时数据、个性化内容、访问请求信息      | 服务器压力大、无法 CDN 缓存          | 仪表盘、用户中心、实时数据页       |
| **流式渲染 Streaming**    | 服务器（渐进式）       | 与 Suspense 边界配合    | 首屏快速呈现、慢数据不阻塞整体        | 搜索引擎可能提前关闭连接、父组件错误会中断流    | 大页面、慢数据源、AI 流式输出     |
| **ISR**               | 服务器（构建 + 后台再生） | 构建时预生成 + 定时/按需再生   | 静态速度 + 内容可更新、减少构建时间    | 可能短暂陈旧数据                  | 电商列表、新闻、CMS 驱动内容     |
| **PPR**               | 服务器（静态壳 + 动态洞） | 构建时生成静态壳，请求时填充动态部分 | 静态壳即时加载、动态内容流式补充       | 实验性，不推荐生产；动态路由兼容性有限       | 个性化首页、混合内容页面         |
| **Edge Runtime**      | 边缘节点           | 请求时在边缘执行           | 极低延迟、全球分布、靠近用户         | 仅支持有限 Node.js API、冷启动可能慢  | 地理位置路由、鉴权、A/B 测试、中间件 |

---

## 各渲染方式详细说明

### 1. Server Components（服务器组件）

**何地**：完全在服务器上执行，不会向客户端发送组件 JavaScript。

**何时**：App Router 中默认所有组件都是 Server Components，无需任何声明。

**优点**：
- 直接从数据库或 API 获取数据，减少客户端请求瀑布。
- 使用密钥、Token 等敏感信息不会暴露给浏览器。
- 大幅减少发送到客户端的 JavaScript 体积，提升 FCP。

**缺点**：
- 不能使用 `useState`、`useEffect`、事件处理器等客户端特性。
- 无法访问 `window`、`localStorage` 等浏览器 API。

**应用场景**：页面级数据获取、重计算逻辑、访问数据库或内部 API、需要保密的业务逻辑。

### 2. Client Components（客户端组件）

**何地**：在浏览器中执行，但 Next.js 会先将其预渲染为 HTML，再进行 hydration。

**何时**：需要交互性或浏览器 API 时，在文件顶部添加 `'use client'` 声明。

**优点**：
- 支持状态管理、事件处理、生命周期逻辑、自定义 Hooks。
- 可使用所有浏览器 API。

**缺点**：
- 增加客户端 bundle 体积，需要 hydration，带来运行时开销。
- 过度使用会抵消 Server Components 的性能优势。

**应用场景**：按钮点击、表单输入、下拉菜单、模态框、地图组件、需要访问 `localStorage` 的功能。


### 3. 静态渲染（Static Rendering）

**何地**：在服务器上于**构建时**生成 HTML，结果被缓存并全局分发。

**何时**：组件不包含任何动态数据源时自动触发；也可通过 `export const dynamic = 'force-static'` 强制启用。

**优点**：
- 页面加载极快，可从 CDN 全球分发。
- 服务器无需为每个请求重新生成内容，减少计算成本。
- 预渲染内容对搜索引擎爬虫友好，利于 SEO。

**缺点**：
- 数据不是实时的，构建后内容固定。
- 任何内容更新都需要重新构建和部署。

**应用场景**：静态博客文章、产品介绍页、文档站点、营销落地页——即内容不常变化、对所有用户相同的页面。


### 4. 动态渲染（Dynamic Rendering）

**何地**：在服务器上**每次请求时**为每个用户单独渲染。

**何时**：当组件使用以下任一动态 API 时自动触发：`cookies()`、`headers()`、`searchParams`、`fetch(..., { cache: 'no-store' })`，或通过 `export const dynamic = 'force-dynamic'` 强制启用。

**优点**：
- 始终提供实时或频繁更新的数据。
- 轻松实现个性化内容，如用户仪表盘、个人资料页。
- 可访问请求时才能知道的信息（cookies、URL 参数）。

**缺点**：
- 服务器需要为每个请求执行渲染，计算压力大。
- 无法利用 CDN 缓存，响应时间受服务器性能影响。

**应用场景**：用户仪表盘、电商购物车、实时数据监控面板、任何需要根据用户身份展示不同内容的页面。


### 5. 流式渲染（Streaming）

**何地**：在服务器上渐进式渲染，通过 HTTP 流将 HTML 分块发送到浏览器。

**何时**：与 `<Suspense>` 边界配合使用，或使用 `loading.tsx` 文件自动启用。

**优点**：
- 静态部分立即呈现，动态部分在就绪后流式补充，显著提升感知加载速度。
- 慢数据源不会阻塞整个页面的渲染。
- Next.js 内置支持，无需额外配置。

**缺点**：
- 搜索引擎爬虫可能提前关闭连接，影响索引。
- 如果父级 Server Component 抛出错误，整个流会中断。
- 生产环境中可能被中间代理缓冲，导致流式效果失效。

**应用场景**：包含多个数据区块的大页面、AI 流式响应、任何有慢数据源但希望快速展示部分内容的场景。


### 6. ISR（增量静态再生）

**何地**：服务器上，构建时预生成，之后在后台按需或定时再生。

**何时**：通过 `export const revalidate = 60`（秒）设置再生间隔，或使用 `revalidatePath()` / `revalidateTag()` 按需触发。

**优点**：
- 兼具静态渲染的速度和动态内容的新鲜度。
- 无需重新构建整个站点即可更新内容。
- 大量内容页面不会导致构建时间过长。

**缺点**：
- 再生间隔内可能返回陈旧数据（stale-while-revalidate 模式）。
- 首次请求未预生成的页面可能会有延迟。

**应用场景**：电商产品列表、新闻文章、CMS 驱动的内容站点——内容需要定期更新但不需要每请求实时。


### 7. PPR（部分预渲染，实验性）

**何地**：服务器上，将静态壳（Shell）在构建时生成，动态“洞”（Holes）在请求时流式填充。

**何时**：通过 `export const experimental_ppr = true` 启用，配合 `<Suspense>` 标记动态边界。

**优点**：
- 静态壳即时从 CDN 返回，动态部分并行流式补充，兼顾速度与个性化。
- 无需将页面拆分为独立路由或客户端 fetch。

**缺点**：
- **实验性功能，不推荐生产使用**。
- 动态路由（带 slug 的路由）与 PPR 的兼容性存在已知限制。
- 如果页面全部内容都是动态的，PPR 没有可预渲染的静态部分，收益为零。

**应用场景**：个性化首页、混合内容页面——页面既有对所有用户相同的静态部分，又有需要个性化的动态部分。


### 8. Edge Runtime（边缘运行时）

**何地**：在靠近用户的边缘节点执行，而非中心化的服务器。

**何时**：通过 `export const runtime = 'edge'` 声明。

**优点**：
- 极低延迟，全球分布执行，用户无论身在何处都能快速响应。
- 适合地理位置相关的逻辑（如根据用户位置路由）。

**缺点**：
- 仅支持有限的 Node.js API（无 `fs`、无 socket）。
- 冷启动可能带来数百毫秒的延迟。
- 不支持静态渲染，动态渲染可用。

**应用场景**：地理位置路由、鉴权中间件、A/B 测试、基于用户位置的个性化内容——需要极低延迟且不需要完整 Node.js 能力的场景。


## 如何选择：决策指南

1. **从 Server Components 开始**——这是 App Router 的默认选择，除非你需要交互性。
2. **只在需要交互时添加 `'use client'`**——尽量将客户端组件包裹在 Server Component 内部，保持边界尽可能靠下。
3. **内容不常变化 → 静态渲染或 ISR**；内容需要实时或个性化 → 动态渲染。
4. **页面有慢数据源 → 用 Suspense 启用流式渲染**，让静态部分先呈现。
5. **需要极低延迟的全球服务 → Edge Runtime**，但要确认不需要完整 Node.js API。
6. **实际生产应用通常是混合模式**——静态/ISR 用于 SEO 关键且稳定的内容，SSR/CSR 仅用于确实需要新鲜度或个性化的部分。

在 App Router 中，静态与动态的边界是**组件级**的，而非路由级。这意味着你可以在同一个页面中，让静态壳立即加载、缓存函数独立再生、动态区块流式补充——无需将任何内容拆分到独立路由或客户端 fetch。
